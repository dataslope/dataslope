# Database IDE & Playground Research

**Date:** 2026-05-11  
**Scope:** Feature gap analysis for the existing SQLite/PostgreSQL playgrounds; DuckDB feasibility; shared architecture proposal.

---

## Executive Summary

The existing dataslope SQLite and PostgreSQL playgrounds are already ahead of the minimal-viable bar: they have multi-tab editors (CodeMirror 6), schema-aware SQL autocomplete, query history, result pagination, multi-format export (CSV / JSON / SQL / Parquet / XLSX), CSV/Parquet import, an ER diagram pane, a structure editor, and a Pragma settings panel. Compared against the 2024–2026 generation of browser IDEs (Neon, Supabase, Hex, Outerbase, sqlime, Datasette), several high-value features are absent or underdeveloped:

1. **No EXPLAIN / query-plan visualization** — the single highest-impact gap for a learning/exploration context.
2. **No saved/bookmarked queries** — history-only is not enough once a user starts returning regularly.
3. **No shareable URL state** — every modern browser playground supports link-sharing; absence is a trust signal problem.
4. **No inline data visualization** — chart rendering after a SELECT is now a baseline expectation.
5. **SQL formatting (Prettier/prettier-plugin-sql)** — trivial to add, significant quality-of-life gain.

For DuckDB, the core editor and result-table components reuse cleanly; the significant new requirements are file-upload UX, an Arrow/Parquet-aware type renderer, and an execution-backend abstraction that can dispatch to either sql.js, a Postgres wire connection, or DuckDB-WASM depending on the playground.

## 2. Feature Gap Analysis

### 2.1 What the Current Playground Has

Based on direct inspection of the codebase (`app/_components/sql/SqlPlayground.tsx`, `PostgresPlayground.tsx`, and their sub-components):

**Editor**
- CodeMirror 6 with SQLite or PostgreSQL dialect
- Bracket matching, auto-close, history (undo/redo), word wrap toggle, font size control
- Schema-aware autocomplete: tables, columns, views, CTEs, SQL keywords with context scoring
- Multi-tab with drag-to-reorder and per-database persistence (localStorage)
- Tab title editing in-place

**Schema sidebar**
- Tables, views, indexes, triggers — all collapsible
- Single-click expand / double-click preview (first 50 rows)
- Modify Structure drawer (GUI DDL editor with FK, constraints, generated columns)
- DDL viewer
- ER diagram (elkjs, orthogonal routing, read-only)
- Context menu: copy name, copy SELECT/INSERT/CREATE snippets

**Results panel**
- Tanstack Table with client-side column sort
- Lazy server-side pagination for large SELECTs (COUNT + LIMIT/OFFSET)
- Configurable page size (25 / 50 / 100 / 250 / 500 / All)
- Cell editing (row UPDATE/DELETE via SQL), row selection with multi-delete
- Right-click context menu: copy cell, copy row as CSV/JSON/SQL
- PK/FK column icons for table previews
- Inferred column type badge (INTEGER / REAL / TEXT / BLOB / NULL)
- Export: CSV, JSON, SQL INSERT, Parquet, XLSX — per-page or all rows

**Import**
- CSV (delimiter detection, header inference, target-table column mapping dialog)
- Parquet (Apache Arrow, parquet-wasm WASM)

**History**
- Read-only CodeMirror preview per entry, success/error status, elapsed time, timestamp
- Clear history button
- Session-only (not persisted across reloads — this is a gap)

**Settings**
- Editor theme (multiple), font size, output font size, word wrap, clear-before-run
- Pragma panel (SQLite only): foreign keys, journal mode, synchronous, page size, automatic index, case-sensitive LIKE
- Runtime info popover

**Navigation**
- Multiple sample databases (Chinook, Northwind, etc.) via URL-driven selector
- DB upload (.sqlite, .db), DB download (sql.js export)

### 2.2 What Is Missing or Weak

#### High-Priority Gaps

These are features that users either expect by default or that noticeably degrade the daily-use experience.

| # | Feature | Why It Matters | Effort |
|---|---|---|---|
| H1 | **SQL formatter ("Prettify")** | One-click `prettier`/`sql-formatter` button normalises indentation, keyword casing, line breaks. Every serious editor has it. Almost zero complexity to add; `sql-formatter` npm package works in-browser. | Low |
| H2 | **Shareable URL / encoded state** | sqlime does this via GitHub Gist. Neon/Supabase do it natively. Without it, users cannot share a reproducible playground state for learning or bug reports. Even a simple `?q=base64(sql)&db=chinook` param covers 90% of the need. | Medium |
| H3 | **Persisted query history** | Current history is session-only (Zustand, not persisted). It disappears on reload. localStorage-backed history with per-DB namespacing (same pattern as tabs) is an obvious improvement. | Low |
| H4 | **Saved / bookmarked queries** | History ≠ saved queries. Users want named, manually saved query snippets they can recall quickly. Supabase and Neon both have this. A simple list in localStorage with a name, SQL, and DB scoping would suffice. | Medium |
| H5 | **EXPLAIN / query plan output** | For a learning playground this is critical. SQLite: `EXPLAIN QUERY PLAN` returns rows parseable into a tree. PostgreSQL: `EXPLAIN (ANALYZE, FORMAT JSON)` returns structured JSON that can be rendered as a tree or flame graph. Neon and Supabase render a text EXPLAIN; DBeaver/DataGrip render trees. Even a formatted text output is vastly better than nothing. | Medium–High |
| H6 | **Result row virtualization** | Current implementation renders up to `pageSize` rows as real DOM nodes. At page-size=500 with 30 columns this is slow. TanStack Virtual (already in the ecosystem since TanStack Table is used) would make "All rows" mode usable even for thousands of rows. | Medium |

#### Medium-Priority Enhancements

| # | Feature | Why It Matters | Effort |
|---|---|---|---|
| M1 | **Inline charts / basic visualization** | After a GROUP BY aggregate query, a bar chart of the result is a natural next step. Hex does this well. Even a simple bar/line/pie from Recharts or Nivo over the result set would be a differentiator for the learning use-case. | High |
| M2 | **Query plan tree (visual EXPLAIN)** | Upgrade from text EXPLAIN (H5) to a node-link diagram. PostgreSQL JSON EXPLAIN has enough structure. SQLite EXPLAIN QUERY PLAN output is tree-shaped (parentid column). | High |
| M3 | **Keyboard shortcut reference panel** | `Ctrl+/` opens a modal listing all keybindings. Very low effort, big perceived professionalism boost. | Low |
| M4 | **Multi-panel / split results** | Some users want to run two queries side-by-side. A vertical split within the results panel (two result sets shown simultaneously) mirrors DBeaver and DataGrip UX. | Medium |
| M5 | **Find-in-schema** | Filter the sidebar table/column list by typing. Essential once a database has >50 tables. The ER diagram's "search" metaphor. | Low–Medium |
| M6 | **AI prompt-to-SQL (native)** | The BYOK AI autocomplete was removed. A simple `?` button that opens a prompt box and calls an AI endpoint (with schema context) to generate SQL is now standard in Neon, Supabase, and Outerbase. | Medium |
| M7 | **History persistence (localStorage)** | Promoted from context above — worth calling out explicitly as a medium-priority for persistence. | Low |
| M8 | **Column statistics / profile** | Right-click a column in the schema sidebar → show `COUNT(*)`, `COUNT(DISTINCT)`, `MIN`, `MAX`, `AVG`. Datasette's "column stats" view. | Medium |

#### Nice-to-Have Features

| # | Feature | Notes |
|---|---|---|
| N1 | Notebook / cell mode | Full cell-by-cell Jupyter-style execution. Large scope; Hex and Observable do it well. Overkill for a playground. |
| N2 | Collaborative editing (CRDT) | Multi-user real-time editing. Needs a backend. Very high effort. |
| N3 | Query diff / version history | Git-style history for saved queries. High effort, rarely used in practice. |
| N4 | DB migration tracking | Schema migrations as SQL scripts. Out of scope for a playground. |
| N5 | Auto-format on run | Format SQL before executing. Useful but also annoying for users with intentional formatting. Keep optional. |
| N6 | Result set comparison | Diff two query results. Interesting for a learning context ("expected vs actual"). |
| N7 | Pivot table from results | Convert flat result to pivot. High implementation cost; better served by inline charts. |
| N8 | Mobile-first layout | Current sidebar+editor+result layout collapses poorly on mobile. Worth a responsive breakpoint pass but not blocking. |

#### Features Likely Not Worth Implementing

| Feature | Reason |
|---|---|
| Full Jupyter notebook integration | Complexity far exceeds gain for a SQL playground; direct users to Hex/Observable |
| SSH tunnel / connection management | Server-side concerns; not applicable to WASM playgrounds |
| Team workspaces / access control | Requires auth, backend, billing — out of scope |
| Complex ERD editing (drag-create-table) | High effort, low learning value vs. the structure editor already present |
| Query scheduler / cron | Backend dependency, not a playground concern |
| Native binary/hex editor for BLOBs | DB Browser for SQLite does this; not a priority for a web playground |

## 3. Browser Playground Workflow Deep Dive

### 3.1 Multi-Tab Queries
**Current state:** Fully implemented — DnD reorder, per-database localStorage persistence, in-place rename.  
**Gap:** Tabs don't survive a full page reload when navigating to a different sample DB and back. The tab store is keyed by database ID, which should work — verify that `saveTabs` / `loadTabs` round-trips correctly after a hard refresh.

### 3.2 Query History
**Current state:** Session-only Zustand list, CodeMirror read-only previews, success/error status, elapsed time.  
**Gap:**
- History is wiped on page reload (not localStorage-backed).
- No "restore to new tab" action from a history entry (users must manually copy and paste).
- No search/filter within history.
- No per-database scoping visible in the UI (only source label).

**Recommendation:** Back history with localStorage (keyed like `sqlite:history:chinook`), cap at 500 entries, add a "Open in new tab" action button per entry, and add a search input that filters by SQL content.

### 3.3 Saved Queries
**Current state:** Absent.  
**Recommendation:** A named snippets panel (localStorage, per-DB scoped) with:
- Name (editable inline)
- SQL (read-only preview, click to load into current tab)
- Created timestamp
- Delete button

Keep it simple: no folders, no tags, no sync. Users can export their snippets as a JSON file if needed.

### 3.4 Schema Navigation
**Current state:** Collapsible tree, double-click preview, context menu for copy snippets.  
**Gap:** No search/filter. With 50+ tables this becomes slow to navigate.  
**Recommendation:** A text input at the top of the schema panel that filters tables and columns by substring match. Highlight matching text.

### 3.5 Autocomplete / IntelliSense
**Current state:** Custom `sqlCompletion.ts` — table/view/CTE names, column names with schema awareness, SQL keywords with keyword-context scoring (primary/secondary/restricted keyword sets). 75ms debounce. CodemMirror 6 autocompletion extension.  
**Gap:**
- No function signatures (e.g., `strftime(format, time, ...)` parameter hints).
- No snippet completions for common patterns like `SELECT * FROM table WHERE id = ?`.
- No cross-database awareness (for future multi-connection Postgres).

**Assessment:** Current implementation is already better than most browser SQL editors. Function parameter hints are a DataGrip-level feature. Not a blocker.

### 3.6 EXPLAIN / Query Plans
**Current state:** Absent.  
**SQLite approach:**  
```sql
EXPLAIN QUERY PLAN SELECT ...
```
Returns rows with columns `(id, parent, notused, detail)`. Parse the tree (`parent` references `id`) and render as an indented list or node-link diagram.

**PostgreSQL approach:**  
```sql
EXPLAIN (ANALYZE, BUFFERS, FORMAT JSON) SELECT ...
```
Returns a JSON tree. Parse `Plan` → `Plans[]` recursively. Each node has `Node Type`, `Actual Rows`, `Actual Total Time`, `Rows Removed by Filter`, etc.

**Minimum viable:** Run `EXPLAIN QUERY PLAN` (SQLite) or `EXPLAIN (FORMAT TEXT)` (Postgres) and display the output in a pre-formatted panel beneath the result. This is ~1 day of work and vastly better than nothing.

**Better:** Render the SQLite plan as an indented tree with cost indicators. Render the Postgres JSON plan as a collapsible tree (see `pev2` open-source Postgres plan visualizer for reference; it is MIT-licensed and embeddable).

### 3.7 Inline Charts / Visualizations
**Current state:** Absent.  
**Pattern from Hex/Datasette:** After a query runs, a "Chart" tab appears next to "Results". The user picks X-axis, Y-axis, and chart type from dropdowns. The chart re-renders reactively.

**Minimum viable:** A second tab in the result panel labeled "Chart" that auto-configures a bar chart when the result has one categorical and one numeric column. Library candidates:
- **Recharts** (already broadly used in Next.js ecosystems, ~150kB gzipped, MIT)
- **Observable Plot** (compact, data-first API, MIT, used in Datasette)
- **Vega-Lite** (declarative, larger bundle but very powerful)

Recharts is the pragmatic choice given the existing React stack.

### 3.8 CSV / JSON Export
**Current state:** Fully implemented — page or all rows, proper CSV escaping, JSON objects array.  
**Gap:** No copy-to-clipboard for the current page (without downloading a file). A "Copy as CSV" / "Copy as JSON" button is a 5-minute addition with enormous ergonomic value.

### 3.9 Keyboard-First UX
**Current state:** CodeMirror default keymaps + `Ctrl/Cmd+Enter` to run, tab reorder via DnD.  
**Known shortcuts (CodeMirror defaults):**
- `Ctrl+Z` / `Ctrl+Y` — undo/redo
- `Ctrl+F` — find
- `Ctrl+H` — find & replace
- `Ctrl+Enter` — run query (custom)
- `Tab` — indent selected (indentWithTab)
- `Ctrl+/` — toggle comment (defaultKeymap)

**Gap:**
- No visible keyboard shortcut reference (pressing `?` could show a modal).
- No keyboard navigation for the schema sidebar (arrow keys through the tree).
- No shortcut to focus the schema filter input or jump between tabs with `Ctrl+Tab`.

### 3.10 Shareable Playground States
**Current state:** Absent.  
**Pattern from sqlime:** Encode the SQL in a GitHub Gist → share the Gist ID in the URL. This requires a network round-trip and a GitHub account.

**Simpler alternative:** Base64-encode `{db: "chinook", sql: "SELECT ..."}` into the URL hash (`#state=...`). Decodes client-side, no backend required. Limit: ~2000 character practical URL length; for longer queries compress with `pako` (gzip in WASM) and encode as base64url.

**Better alternative:** Use a short-URL service backed by a tiny server that stores the state. But this requires a backend.

**Recommendation:** Start with URL-hash encoding. It covers the most common "share this query with a colleague" use case. Document the 2KB limit clearly. Add a "Share" button that copies the hash URL to clipboard and shows a success toast.

### 3.11 Temporary vs Persistent Sessions
**Current state:** SQLite runs entirely in-memory (sql.js). The database state is rebuilt from the sample file on every load. Tabs and settings are localStorage-persisted.

**Gap:** There is no "persistent user database" mode — everything starts fresh. This is intentional for a playground but should be explicitly surfaced in the UI ("Your changes are not saved between sessions unless you download the database file").

**PostgreSQL playground:** Connects to a real server; persistence depends on the server, not the frontend.

### 3.12 AI-Assisted Querying / Debugging
**Current state:** BYOK AI autocomplete was implemented and then removed (`commit fbcd816`).

**What modern tools offer (Neon, Supabase, Outerbase):**
1. A prompt box: "Show me total sales by product category" → generates a SELECT.
2. Error explanation: when a query fails, a "What went wrong?" button sends the error + query to an LLM and returns a plain-English explanation.
3. Schema-aware generation: the schema (table names + column names) is injected into the system prompt.

**Recommendation for a BYOK re-implementation:** The schema context injection pattern is the key. Keep the API key in session memory only (do not persist). Add a "Fix with AI" button to error panels. This is a medium-effort, high-visibility feature that respects user privacy by default.

### 3.13 Notebook-Style Workflows
**Current state:** Absent.  
**Assessment:** Full notebook mode (Jupyter / Hex style) is out of scope for a SQL playground. The multi-tab model is the right primitive for this use case. If notebook UX is desired, the correct path is to integrate the playground as an embeddable component inside a document editor (like Observable), not to rebuild Observable inside the playground.

### 3.14 Result Pagination / Virtualization
**Current state:** Lazy LIMIT/OFFSET pagination for single SELECT statements, configurable page size (25–500+All). React DOM rendering up to `pageSize` rows.

**Gap:** At page-size=500 with wide tables (30+ columns), the DOM row count creates jank. TanStack Virtual (`@tanstack/react-virtual`) is a first-class companion to TanStack Table (already used). Adding row virtualization to `ResultTableBody` would allow "All rows" mode to comfortably handle 5,000–50,000 rows without a page limit.

**Recommendation:** Add `useVirtualizer` from `@tanstack/react-virtual` to `ResultView`. This is a medium-effort change with measurable performance gains for users working with larger result sets.

### 3.15 Large-Result Handling
**Current state:** Lazy pagination caps per-page DOM cost. But the WASM heap holds all rows from a table-preview (not paginated) until the user manually queries.

**Gap:** If a user runs `SELECT * FROM large_table` without a LIMIT and `lazyPagination` is active, they see 25 rows but the full COUNT(*) is computed. If they click "All" as page size, all rows are materialized into the DOM. For multi-MB results this causes browser OOM.

**Recommendation:** Cap "All rows" at 10,000 rows with a hard-coded safety guard and show a warning banner: "Showing first 10,000 rows of N total. Download the full result to access all rows."

### 3.16 Error UX
**Current state:** Errors appear in the result panel with a red tinted background. `getSqliteErrorHint()` maps common SQLite error patterns to plain-English explanations shown beneath the raw message.

**Gap:** PostgreSQL error handling is less developed. Postgres errors include `severity`, `code`, `detail`, `hint`, `position` (character offset into the query) — none of these are currently surfaced as structured fields.

**Recommendation:** For Postgres, parse the error response object and:
1. Highlight the character position in the editor (CodeMirror diagnostic API).
2. Show `detail` and `hint` fields from the Postgres error separately.
3. Map common `code` values (e.g., `42P01` = undefined_table, `23505` = unique_violation) to friendly hints matching what the SQLite playground already does.

### 3.17 Mobile Responsiveness
**Current state:** The three-column layout (schema sidebar | editor | results) is desktop-only. On viewports < 768px it requires horizontal scrolling.

**Assessment:** Mobile SQL editing is genuinely difficult UX regardless of implementation. Given that this is a developer tool, mobile is low priority. A responsive layout that collapses to a stacked view (editor on top, results below, schema in a drawer) would be worth a CSS-only pass, but is not blocking.

## 4. DuckDB Playground Requirements

### 4.1 What DuckDB Is

DuckDB is an analytical (OLAP) SQL engine designed for columnar in-process query execution. The browser target is `@duckdb/duckdb-wasm`, which runs the DuckDB engine entirely in the browser via WebAssembly (no server required). MotherDuck extends this with a hybrid cloud backend.

### 4.2 Capabilities Beyond SQLite/Postgres

| Capability | DuckDB | SQLite (current) | Postgres |
|---|---|---|---|
| Read Parquet directly | `SELECT * FROM 'file.parquet'` | Via WASM import | Extension only |
| Read CSV directly | `SELECT * FROM read_csv_auto('f.csv')` | Via import dialog | COPY FROM |
| Read JSON directly | `SELECT * FROM read_json('f.json')` | ✗ | ✗ |
| Arrow IPC in/out | Native | Via apache-arrow shim | ✗ |
| Multi-file glob | `FROM 'folder/*.parquet'` | ✗ | ✗ |
| Columnar memory layout | Always | ✗ | ✗ |
| PIVOT / UNPIVOT | Built-in SQL | ✗ | ✗ |
| Window functions | Full | Limited | Full |
| Analytical extensions (MEDIAN, MODE, PERCENTILE) | Built-in | Limited | Extension |
| ASOF JOIN | Built-in | ✗ | ✗ |
| MotherDuck cloud backend | Via wasm+token | ✗ | N/A |
| httpfs (read remote files) | Extension (limited in WASM) | ✗ | ✗ |

### 4.3 New UX Requirements Specific to DuckDB

#### File Upload UX
DuckDB-WASM can register in-memory file handles via `duckdb.registerFileBuffer()`. This enables:
- Drag-and-drop a `.parquet`, `.csv`, or `.json` file onto the playground.
- File is registered under a virtual path (e.g., `uploaded_data.parquet`).
- The editor pre-populates: `SELECT * FROM 'uploaded_data.parquet' LIMIT 100;`
- Schema sidebar shows the virtual file's inferred columns.

This is materially different from the SQLite import flow, which maps data into a named table. DuckDB users expect to query the file directly.

#### Schema Sidebar Adaptations
DuckDB has:
- Regular tables (in-memory, from `CREATE TABLE`)
- Views
- External files registered as virtual tables
- MotherDuck-attached databases (multiple database namespaces, e.g., `md:mydb.main.users`)

The schema sidebar needs to show:
- In-memory tables (same as SQLite)
- Registered file handles (new category: "Files")
- Attached databases (new category, expandable namespace)

#### Result Type Rendering
DuckDB returns richer types than SQLite's five storage classes:
- `HUGEINT`, `UBIGINT` — large integers (render as string to avoid JS precision loss)
- `DATE`, `TIME`, `TIMESTAMP`, `TIMESTAMPTZ` — proper temporal types
- `INTERVAL` — duration (render as ISO 8601)
- `LIST<T>` — arrays (render as `[a, b, c]`)
- `STRUCT<k: T>` — nested objects (render as `{k: v}`)
- `MAP<K, V>` — maps (render as `{k: v}`)
- `UNION<T>` — discriminated union types

The current result renderer uses `inferColumnType()` (which only knows INTEGER/REAL/TEXT/BLOB/NULL). For DuckDB, column types are returned by the engine and should be used directly.

#### Analytical Workflow Patterns
DuckDB users (data engineers, analysts) expect:
1. **Multi-file joins**: `SELECT a.*, b.* FROM 'sales/*.parquet' a JOIN 'customers.csv' b ON ...`
   - Requires the file registration UX described above + schema inference across multiple files.
2. **Sampling**: `SELECT * FROM large_table USING SAMPLE 1% (bernoulli);`
   - Common DuckDB pattern; no special UI needed, but autocomplete should know `USING SAMPLE`.
3. **COPY ... TO**: Export to Parquet/CSV with DuckDB syntax.
   - In-browser, this should trigger a download instead of writing to disk.
4. **Dataframe-style operations**: DuckDB's relation API supports chained operations. For a browser playground this is not relevant (users write SQL, not Python).

#### Charting Expectations
DuckDB users working with analytical queries expect charts. A GROUP BY + aggregation is a chart 90% of the time. This reinforces M1 (inline charts) as higher priority for a DuckDB playground than for SQLite.

#### In-Memory Execution and Memory Limits
DuckDB-WASM operates within the browser's WASM heap (~4GB on 64-bit browsers, but practically limited by available RAM). For large local files:
- Files > 200MB will strain the WASM heap.
- DuckDB-WASM streams Parquet columns lazily (it does not load the entire file into memory before querying).
- Show a clear warning for files > 50MB: "Large files may cause slow performance in the browser."
- For very large files, recommend MotherDuck or a local DuckDB binary.

#### MotherDuck Integration
MotherDuck provides a token-based authentication that DuckDB-WASM supports natively:
```javascript
db = await duckdb.createDatabase('md:?motherduck_token=TOKEN');
```
This is a significant scope expansion (auth UI, token storage, connection state). Not an MVP requirement, but the architecture should not preclude it.

## 5. UI Reuse Feasibility

### 5.1 Components That Can Be Fully Shared (No Changes)

| Component | Notes |
|---|---|
| `QueryHistoryPane` | Pure display, receives `history[]` as prop. Engine-agnostic. |
| `ToastList` | Completely generic. |
| `SqlTab` | Tab drag-and-drop, rename, close. No engine coupling. |
| Export helpers (`exportResultTo{Csv,Json,Sql,Parquet,Xlsx}`) | Work on `{columns: string[], rows: unknown[][]}`. Engine-agnostic. |

| CodeMirror editor setup | Switch dialect via `Compartment`; no engine coupling in the editor itself. |
| Pagination UI | Pure UI; page navigation is engine-agnostic. |
| `ErDiagramPane` | Consumes a `{tables, foreignKeys}` schema shape; engine-agnostic. |
| Settings panel (font, theme, word wrap) | Engine-agnostic. |

### 5.2 Components That Require Abstraction

| Component | Required Change |
|---|---|
| **Schema sidebar (`SchemaItem`)** | Currently drives queries like `SELECT * FROM table LIMIT 50` directly through `SqliteEngine`. Needs an `engine.preview(entity)` method on a shared interface. The sidebar item also needs to handle DuckDB's file and attached-DB concepts. |
| **`ResultView` / `ResultTableBody`** | Type rendering is SQLite-specific (`inferColumnType` returns INTEGER/REAL/TEXT/BLOB/NULL). Needs a `columnTypes: string[]` prop fed by the engine, with a renderer that handles DuckDB's richer type vocabulary. |
| **Autocomplete source** | `createSqlCompletionSource` currently takes a `SqlCompletionSchema` built from `SqliteEngine` introspection. Needs a generic schema interface implemented by each engine adapter. DuckDB needs to add `FILES` as a completion entity category. |
| **Import dialogs (CSV/Parquet)** | SQLite import creates a new table via `INSERT INTO`. DuckDB import registers a file handle and generates `FROM 'file.parquet'` syntax. Two different backends with different semantics need the same dialog entry point. Abstract an `engine.importFile(file, options)` method. |
| **Pragma settings tab** | SQLite-specific. Postgres has `SET` variables; DuckDB has `PRAGMA` (different set). Should be replaced by an engine-specific `<EngineSettingsTab>` slot that each engine can optionally fill. |
| **Error hint system (`getSqliteErrorHint`)** | SQLite-specific regex patterns. Postgres errors are structured objects. DuckDB errors have their own format. Abstract to `engine.formatError(err): {message, hint}`. |
| **`ModifyStructureForm` (DDL editor)** | Tightly coupled to `SqliteEngine.rebuildTable`. Postgres DDL works differently (ALTER TABLE). DuckDB is mostly read/analytical — GUI DDL editing is rarely needed. Make this an optional engine capability: `engine.supportsStructureEdit()`. |

### 5.3 DuckDB-Specific UI Concerns

| Concern | Details |
|---|---|
| **File drop zone** | A prominent drag-and-drop target for `.parquet`/`.csv`/`.json` files. No equivalent in SQLite/Postgres playgrounds. Could be a persistent "drop here" area in the schema sidebar under a "Files" section, or a full-screen overlay on drag. |
| **File progress indicator** | Large Parquet files take seconds to register. Need a progress bar or spinner with file size shown. |
| **Virtual file listing** | Registered files appear in the schema sidebar under "Files", showing inferred column names and types. A "Remove file" action should call `duckdb.dropFile()`. |
| **Query-file autocomplete** | When the user types a string literal in SQL context (e.g., `FROM '`), autocomplete should suggest registered file names. This is a DuckDB-specific completion mode. |
| **Type renderer extensions** | LIST, STRUCT, MAP, INTERVAL need custom cell renderers (e.g., collapsed JSON with expand-on-click). |
| **MotherDuck connection UI** | Token input, connection state indicator, database namespace switcher in the toolbar. |
| **COPY TO download** | Intercept DuckDB's `COPY ... TO` output and trigger a browser download instead. |
| **Memory warning** | Monitor WASM heap usage and show a warning when approaching limits. |

### 5.4 Backend-Specific Execution Concerns

| Concern | SQLite (current) | Postgres (current) | DuckDB (proposed) |
|---|---|---|---|
| Execution location | Browser (sql.js WASM) | Server-side, WebSocket or HTTP | Browser (duckdb-wasm) |
| Async execution | Synchronous in WASM thread (blocks) | Async over network | Async (Web Worker or OPFS) |
| Multi-statement support | All statements in one exec() call | Statement-by-statement | Statement-by-statement or batch |
| Schema introspection | `sqlite_master`, `pragma_table_info` | `information_schema` | `duckdb_tables()`, `duckdb_columns()` |
| Error format | Plain string | Structured `{severity, code, message, detail, hint, position}` | `Error` with `errno` + message |
| Transaction model | Auto-commit or explicit | Explicit, supports isolation levels | Auto-commit or explicit |
| File I/O | Not applicable | Not applicable (server handles) | OPFS (persistent) or in-memory |

### 5.5 Recommended Architecture for a Unified Playground System

#### Engine Adapter Interface

Define a `PlaygroundEngine` interface that all three backends implement:

```typescript
interface PlaygroundEngine {
  // Core execution
  exec(sql: string): Promise<ExecResult[]>;
  execPaged(sql: string, pageSize: number, offset: number): Promise<PagedResult>;

  // Schema
  listDatabases(): Promise<string[]>;         // DuckDB: multiple catalogs
  listTables(db?: string): Promise<TableInfo[]>;
  listViews(db?: string): Promise<ViewInfo[]>;
  getColumnInfo(table: string, db?: string): Promise<ColumnInfo[]>;
  getForeignKeys(table: string, db?: string): Promise<ForeignKeyInfo[]>;
  getDdl(table: string, db?: string): Promise<string>;

  // File management (optional capability)
  registerFile?(file: File, name: string): Promise<void>;
  listFiles?(): Promise<FileInfo[]>;
  dropFile?(name: string): Promise<void>;

  // DDL editing (optional capability)
  supportsStructureEdit(): boolean;
  rebuildTable?(tableName: string, spec: TableSpec): Promise<void>;

  // Error formatting
  formatError(err: unknown): { message: string; hint: string | null; position?: number };

  // Settings (optional capability)
  getSettingsPanel?(): React.ReactNode;

  // Export / import
  exportDatabase(): Promise<Uint8Array>;   // .sqlite or .duckdb
  importDatabase(data: Uint8Array): Promise<void>;

  // Lifecycle
  dispose(): void;
}
```

#### Component Architecture

```
SqlPlaygroundShell (engine-agnostic shell)
├── EditorPane          (CodeMirror, dialect via prop)
│   └── AutocompleteSource (engine.listTables/getColumnInfo)
├── SchemaSidebar       (engine.listTables, engine.listViews, engine.listFiles?)
│   ├── TableSection
│   ├── ViewSection
│   └── FilesSection    (DuckDB only, gated by engine.listFiles != null)
├── ResultPanel
│   ├── ResultView      (engine-agnostic, columnTypes prop from engine)
│   └── ChartView       (engine-agnostic, reads result rows)
├── QueryHistoryPane    (engine-agnostic)
├── SavedQueriesPane    (engine-agnostic)
├── ErDiagramPane       (engine-agnostic, receives schema props)
└── EngineSettingsSlot  (engine.getSettingsPanel?.())
```

Each engine (SQLite, Postgres, DuckDB) instantiates `PlaygroundEngine`, mounts `SqlPlaygroundShell`, and passes the engine instance as a prop/context. All shared components read from the interface; none import from `runtime/sqlite.ts` directly.

#### Migration Path

1. **Phase 1 (no breaking changes):** Define the `PlaygroundEngine` interface. Keep `SqliteEngine` as-is. Wrap it in a thin adapter class that implements the interface. No UI changes.
2. **Phase 2:** Thread the engine through a React context (`PlaygroundEngineContext`). Remove direct `engine.*` calls from components that should be engine-agnostic. Replace with `useEngine()` hook calls.
3. **Phase 3:** Implement `DuckDBEngine` adapting `@duckdb/duckdb-wasm`. Add the DuckDB playground route. The shell and all shared components just work.
4. **Phase 4:** Implement `PostgresEngine` wrapping the existing Postgres connection. Consolidate `PostgresPlayground.tsx` to reuse the shared shell instead of its current parallel implementation.

The current `PostgresPlayground.tsx` is a near-fork of `SqlPlayground.tsx` — both share ~70% of their structure but are maintained separately. Unifying them around the engine interface eliminates this duplication.

## 7. Appendix: DuckDB-WASM Integration Notes

### Setup
```bash
npm install @duckdb/duckdb-wasm
```

DuckDB-WASM loads via Web Worker (recommended) or main-thread sync (limited). The Web Worker approach requires a static WASM bundle served from the same origin or a CDN. The library supports automatic bundle selection:

```typescript
import * as duckdb from '@duckdb/duckdb-wasm';
import duckdb_wasm from '@duckdb/duckdb-wasm/dist/duckdb-mvp.wasm?url';
import mvp_worker from '@duckdb/duckdb-wasm/dist/duckdb-browser-mvp.worker.js?url';
import duckdb_wasm_eh from '@duckdb/duckdb-wasm/dist/duckdb-eh.wasm?url';
import eh_worker from '@duckdb/duckdb-wasm/dist/duckdb-browser-eh.worker.js?url';

const MANUAL_BUNDLES: duckdb.DuckDBBundles = {
  mvp: { mainModule: duckdb_wasm, mainWorker: mvp_worker },
  eh: { mainModule: duckdb_wasm_eh, mainWorker: eh_worker },
};

const bundle = await duckdb.selectBundle(MANUAL_BUNDLES);
const worker = new Worker(bundle.mainWorker!);
const logger = new duckdb.ConsoleLogger();
const db = new duckdb.AsyncDuckDB(logger, worker);
await db.instantiate(bundle.mainModule, bundle.pthreadWorker);
```

### File Registration
```typescript
// Register a local File object
const buf = await file.arrayBuffer();
await db.registerFileBuffer(file.name, new Uint8Array(buf));

// Query it directly
const conn = await db.connect();
const result = await conn.query(`SELECT * FROM '${file.name}' LIMIT 100`);
```

### Result Handling
DuckDB-WASM returns Apache Arrow `Table` objects:
```typescript
const arrowTable = await conn.query(sql);
const columns = arrowTable.schema.fields.map(f => f.name);
const columnTypes = arrowTable.schema.fields.map(f => f.type.toString());
const rows = arrowTable.toArray().map(row => columns.map(c => row[c]));
```

Arrow types map to display types: `Int32` → INTEGER, `Float64` → REAL, `Utf8` → TEXT, `List` → LIST, `Struct` → STRUCT, etc.

### Schema Introspection
```sql
-- All tables in the default catalog
SELECT table_name, table_type FROM information_schema.tables 
WHERE table_schema = 'main';

-- Or DuckDB-native:
SELECT table_name FROM duckdb_tables();
SELECT view_name FROM duckdb_views();
SELECT column_name, data_type, is_nullable 
FROM duckdb_columns() WHERE table_name = 'mytable';
```

### COPY TO Download
Intercept COPY TO by pre-processing the SQL before execution:
- Detect `COPY (...) TO 'filename.parquet'` pattern.
- Execute as `COPY (...) TO '/tmp/export.parquet'` in the WASM VFS.
- Read back: `const bytes = await db.copyFileToBuffer('/tmp/export.parquet')`.
- Trigger browser download.
