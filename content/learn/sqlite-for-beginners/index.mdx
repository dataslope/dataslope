Welcome to **SQLite for Beginners**. If the words *database*,
*query*, and *table* feel vague — or if the only place you have
ever organized information is a spreadsheet — you are in exactly
the right place. This course assumes **no programming experience,
no database experience, and no SQL experience.**

Before any theory, here is the most important thing about this
course: **it runs.** Every example on every page executes inside
your browser on a real SQLite engine — no installation, no signup,
no server. The box below is not a screenshot. It is a live database
with a small table of pets already loaded. Click **Run** and watch
it answer.

<SqlCodeBlock
  dialect="sqlite"
  title="Your very first query — click Run"
  initSql={`CREATE TABLE pets (
  name    TEXT,
  species TEXT,
  age     INTEGER
);
INSERT INTO pets (name, species, age) VALUES
  ('Mochi', 'cat', 3),
  ('Pixel', 'dog', 5),
  ('Sunny', 'cat', 2),
  ('Rex',   'dog', 8);`}
  starterCode={`SELECT
  name,
  species,
  age
FROM
  pets
WHERE
  species = 'cat'
ORDER BY
  age DESC;`}
/>

That query says, in almost plain English: *"Show me the name,
species, and age from the pets table, but only the cats, sorted
from oldest to youngest."* You just ran real SQL — the same
language used by banks, airlines, and the phone in your pocket.

Now change something. In the editor above, replace `'cat'` with
`'dog'` and click **Run** again. The answer changes instantly:
same question, different filter. That edit–run–observe loop is how
this entire course works, and it is how you will actually learn —
not by reading about queries, but by running and breaking them.

<Callout type="info" title="How the magic works">
Every SQL block runs on the official `@sqlite.org/sqlite-wasm`
build — SQLite itself, compiled to WebAssembly, executing entirely
in your browser tab. There is no server behind it. The engine you
are practicing on is the genuine article, not a simulation.
</Callout>

## Who this course is for

You will feel at home here if any of these sound like you:

- You have heard colleagues talk about "the database" or "writing a
  query" and quietly wondered what they actually mean.
- You keep information in spreadsheets, but they have started to
  feel slow, fragile, or hard to keep consistent.
- You are curious about data roles — analyst, engineer, scientist —
  and you want to understand the foundation everyone builds on.
- You tried a SQL tutorial once and bounced off a wall of syntax
  with no explanation of *why* any of it exists.

You do **not** need any prior coding experience, any math beyond
everyday arithmetic, or anything installed on your computer.

## What you will be able to do

By the end of the course you will be able to:

- Explain what a database is and *why* software needs one.
- Describe how relational databases organize information into
  **tables** that relate to one another.
- Read and write SQL queries to **select**, **filter**, **sort**,
  and **summarize** data.
- Combine data from multiple tables using **joins**.
- Reason about **primary keys**, **foreign keys**, and
  **relationships** between tables.
- Walk into an unfamiliar database and figure out what it holds.

This is a **foundations** course. It deliberately skips database
administration topics — deployment, replication, tuning, security
hardening — because those make far more sense *after* the ideas
taught here are solid.

## How to study

The course starts with two short pages of ideas — what a database
really is, and why this course uses SQLite — and then you are
writing queries for the rest of the journey. Along the way you
will meet three kinds of interactive elements:

1. **Runnable SQL blocks**, like the one above. Most pre-load
   sample tables for you; edit the query, click *Run*, inspect the
   result.
2. **Challenge cards** — small problems with tests. Write a query,
   run the tests, see which pass. They are designed as quick wins,
   not exams.
3. **Multiple-choice questions** — quick checks that an idea has
   landed, with an explanation for every choice.

The single best study habit: **never just read a code block.** Run
it, predict what a small change will do, make the change, and see
if you were right. Being wrong is the productive part.

<Callout type="info" title="Each SQL block is independent">
Tables you create in one runnable block are **not** visible to the
next block, even on the same page — every block that needs data
sets it up itself. If you want a single long-lived workspace to
experiment in, open the
[SQLite Playground](/playground/sqlite) in a new tab.
</Callout>
