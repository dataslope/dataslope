The in-memory engine needs the data it is working on to fit in RAM.
The **streaming engine** processes a query in batches instead, so
the peak memory is a function of the batch size and the query, not of
the file.

## Turning it on

```python
import polars as pl

q = (
    pl.scan_csv("diamonds.csv")
    .filter(pl.col("carat") > 0.5)
    .group_by("cut")
    .agg(
        pl.len().alias("n"),
        pl.col("price").mean().round(0).alias("avg_price"),
    )
    .sort("cut")
)

print(q.collect(engine="streaming"))
```

<Callout type="info" title="Not runnable in the browser">
The Polars build that ships with Pyodide is compiled without the streaming
engine, so `engine="streaming"` raises here.
The code is correct and works on a normal Polars install; it is shown
here rather than run.
</Callout>


One argument. Everything else about the query is unchanged, which is
the point: you do not write a different program for large data, you
ask for a different engine.

<Callout type="info" title="Streaming needs a lazy query">
`engine="streaming"` is an argument to `collect()`, so it only exists
on a `LazyFrame`. An eager `read_csv` has already put the whole file
in memory before you could ask for anything else.
</Callout>

## sink: never materialize the result at all

`collect()` returns a `DataFrame`, which has to fit in memory. If the
output is also large, sink it straight to a file instead.

```python
import polars as pl

(
    pl.scan_csv("diamonds.csv")
    .filter(pl.col("cut") == "Ideal")
    .select("carat", "cut", "price")
    .sink_parquet("ideal.parquet")
)

# Nothing above ever held the result in memory
print(pl.scan_parquet("ideal.parquet").select(pl.len()).collect())
print(pl.scan_parquet("ideal.parquet").head(3).collect())
```

<Callout type="info" title="Not runnable in the browser">
`sink_parquet` belongs to the streaming engine, which the Polars build that
ships with Pyodide is compiled without.
The code is correct and works on a normal Polars install; it is shown
here rather than run.
</Callout>


`sink_parquet`, `sink_csv`, `sink_ndjson`, and `sink_ipc` all read in
batches and write in batches. A 200 GB file can be filtered and
rewritten on a laptop, at whatever speed the disk allows.

## Many files as one frame

```python
import polars as pl

# Pretend these arrived as a monthly export
for month in range(1, 4):
    pl.DataFrame(
        {"month": [month] * 3, "sales": [100 + month, 200 + month, 300 + month]}
    ).write_parquet(f"sales-2026-{month:02d}.parquet")

# One glob, one lazy frame, all three files
lf = pl.scan_parquet("sales-2026-*.parquet")

print(lf.group_by("month").agg(pl.col("sales").sum()).sort("month").collect())
```

<Callout type="info" title="Not runnable in the browser">
`sink_parquet` belongs to the streaming engine, which the Polars build that
ships with Pyodide is compiled without.
The code is correct and works on a normal Polars install; it is shown
here rather than run.
</Callout>


This is better than concatenating by hand: the optimizer sees all the
files as one source, so projection and predicate pushdown apply to
every one of them, and files whose statistics rule them out are
skipped.

## What streams and what does not

Streaming works by processing batches independently and combining
partial results. Operations that need to see everything at once
cannot do that, so the engine falls back to in-memory for those parts
of the plan.

| Streams well | Needs everything |
| --- | --- |
| `filter`, `select`, `with_columns` | `pivot` (eager only anyway) |
| `group_by().agg()` (partial aggregates merge) | a sort of the whole frame |
| joins (build side must fit) | `rank` over the whole frame |
| `sink_*` | anything needing a global order |

A `sort` is the one that catches people: sorting is inherently global,
so a full sort of a larger-than-memory frame is expensive whatever the
engine. Sorting *after* an aggregation is fine, because the
aggregated result is small.

```python
import polars as pl

# Good: aggregate first (small), then sort the small result
good = (
    pl.scan_csv("diamonds.csv")
    .group_by("cut")
    .agg(pl.col("price").mean().round(0).alias("avg"))
    .sort("avg", descending=True)
)
print(good.collect(engine="streaming"))

# Expensive: sorting the whole frame just to take five rows.
# top_k does the same job without the global order.
print(
    pl.scan_csv("diamonds.csv")
    .top_k(5, by="price")
    .select("carat", "cut", "price")
    .collect(engine="streaming")
)
```

## Keeping memory down without streaming

Three habits help regardless of engine:

- **Narrow the types.** `UInt32` instead of `Int64` halves a column;
  `Categorical` collapses a repeated string column to a byte or two
  per row.
- **Read fewer columns.** With `scan_*` this is automatic; it is the
  reason to prefer it.
- **Store Parquet, not CSV.** Smaller on disk, typed, and its
  statistics let whole row groups be skipped.

## Practice

Try it yourself before reading on. Scan `diamonds.csv` lazily, keep the
diamonds over 1.0 carat, select `cut`, `carat` and `price`, and sink the result
to `big.parquet` without ever collecting it. Then count the rows with a lazy
scan rather than by reading the file in, and build a per-`cut` summary with the
streaming engine.

```python
import polars as pl

(
    pl.scan_csv("diamonds.csv")
    .filter(pl.col("carat") > 1.0)
    .select("cut", "carat", "price")
    .sink_parquet("big.parquet")
)

n_rows = pl.scan_parquet("big.parquet").select(pl.len()).collect().item()

summary = (
    pl.scan_parquet("big.parquet")
    .group_by("cut")
    .agg(pl.len().alias("n"))
    .sort("cut")
    .collect(engine="streaming")
)

print(n_rows)   # 17502
print(summary)  # one row per cut grade, five in all
```

Nothing above ever holds the filtered data in memory: the sink writes as it
reads, and the count comes from the file's own metadata.

</Callout>

  > No ordering requirement exists; batches are processed in whatever order they are read.

<MultipleChoice
  markdown={`Which operation is genuinely hard to stream?

- Filtering rows on a column value
  > Each batch can be filtered independently with no knowledge of any other batch.
- Computing a grouped mean
  > Partial sums and counts merge across batches, which is exactly how streaming aggregation works.
- Adding a column computed from two others
  > This is row-local: every row's value depends only on that row.
- [o] Sorting the entire frame
  > Ordering is inherently global, so a full sort of a larger-than-memory frame is expensive whatever the engine.

Aggregate first and sort the small result, or use \`top_k\` when you only want the extremes.`}
