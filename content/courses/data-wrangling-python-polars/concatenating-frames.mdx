A join matches rows by key. Concatenation just puts frames next to
each other: vertically (more rows) or horizontally (more columns).

## Vertical: more rows

<CodeBlock
  adapter="python"
  files={[
    {
      filename: "main.py",
      starterCode: `import polars as pl

jan = pl.DataFrame({"day": [1, 2], "sales": [100, 120]})
feb = pl.DataFrame({"day": [1, 2], "sales": [95, 130]})

display(pl.concat([jan, feb]))                       # vertical is the default
print(pl.concat([jan, feb], how="vertical").height)
`,
    },
  ]}
/>

Plain `vertical` demands identical schemas: the same column names, in
the same order, with the same dtypes. That strictness is the point.
It catches the case where last month's export gained a column.

<Figure
  slug="pl-concatenating-frames-vertical-more-rows-inline-cutout"
  alt="Two boards of equal width stacked one onto the other, the join line barely visible"
  caption="Vertical concat needs identical schemas, and that strictness catches drift."
/>

## The relaxed strategies

| `how` | Behaviour |
| --- | --- |
| `vertical` | schemas must match exactly |
| `vertical_relaxed` | same columns, dtypes are widened to a common type |
| `diagonal` | union of columns; missing ones become null |
| `diagonal_relaxed` | both of the above |
| `horizontal` | side by side, padded with nulls to the longest |
| `align` | join on the common columns, keeping row order |

<CodeBlock
  adapter="python"
  files={[
    {
      filename: "main.py",
      starterCode: `import polars as pl

# Different dtypes for the same column
a = pl.DataFrame({"x": [1, 2]})                 # Int64
b = pl.DataFrame({"x": [3.5, 4.5]})             # Float64

try:
    pl.concat([a, b])
except Exception as error:
    print("vertical:", type(error).__name__)

display(pl.concat([a, b], how="vertical_relaxed"))
`,
    },
  ]}
/>

Mismatched dtypes are one way a concat goes wrong. Mismatched *columns*
are the other, and `how="diagonal"` is the answer to it:

<CodeBlock
  adapter="python"
  files={[
    {
      filename: "main.py",
      starterCode: `import polars as pl

jan = pl.DataFrame({"day": [1, 2], "sales": [100, 120]})
feb = pl.DataFrame({"day": [1], "sales": [95], "region": ["N"]})

# diagonal takes the union of columns and fills the gaps with null
display(pl.concat([jan, feb], how="diagonal"))
`,
    },
  ]}
/>

`diagonal` is convenient and it is also how a typo becomes a column.
If `region` arrives as `Region` next month, you get two columns, each
half null, and no error. Reach for it when schemas genuinely differ,
not as a way to avoid thinking about them.

## Horizontal: more columns

<CodeBlock
  adapter="python"
  files={[
    {
      filename: "main.py",
      starterCode: `import polars as pl

left = pl.DataFrame({"a": [1, 2, 3]})
right = pl.DataFrame({"b": ["x", "y"]})

display(pl.concat([left, right], how="horizontal"))
`,
    },
  ]}
/>

Horizontal concatenation pairs rows **by position**, which is a
strong assumption. The shorter frame is padded with nulls rather than
raising, so a mismatch is silent. If the two frames share a key
column, join on it instead: a join states the relationship, a
horizontal concat assumes it.

## Adding rows to an existing frame

<CodeBlock
  adapter="python"
  files={[
    {
      filename: "main.py",
      starterCode: `import polars as pl

df = pl.DataFrame({"id": [1, 2], "v": [10, 20]})
new = pl.DataFrame({"id": [3], "v": [30]})

display(df.vstack(new))       # cheap, leaves the frame chunked
display(df.extend(new))       # appends into the existing buffers

# A frame in many chunks reads more slowly; rechunk consolidates it
combined = pl.concat([df, new, new]).rechunk()
print(combined.n_chunks())
`,
    },
  ]}
/>

<Callout type="info" title="Do not concatenate in a loop">
Appending inside a loop is the classic slow pattern, in every
DataFrame library. Collect the frames in a list and call
`pl.concat(frames)` once. One call can allocate the result correctly;
a thousand calls copy the accumulated data a thousand times.
</Callout>

<CodeBlock
  adapter="python"
  files={[
    {
      filename: "main.py",
      starterCode: `import polars as pl

# The right shape for reading many files
def load_month(month: int) -> pl.DataFrame:
    return pl.DataFrame({"month": [month], "sales": [100 + month]})

frames = [load_month(m) for m in range(1, 13)]
year = pl.concat(frames)

display(year.head(3))
print("rows:", year.height, "chunks:", year.n_chunks())
`,
    },
  ]}
/>

For files specifically, Polars will do this for you: `scan_csv()` and
`scan_parquet()` accept a glob and read every match as one lazy frame,
which is both shorter and faster than concatenating by hand.

  caption="Stacking frames adds rows; the columns have to match up first."
/>

## Deduplicating after a concat

<CodeBlock
  adapter="python"
  files={[
    {
      filename: "main.py",
      starterCode: `import polars as pl

a = pl.DataFrame({"id": [1, 2, 3], "v": ["a", "b", "c"]})
b = pl.DataFrame({"id": [3, 4], "v": ["c", "d"]})

stacked = pl.concat([a, b])
print("stacked:", stacked.height)

display(stacked.unique())                                   # whole-row duplicates
display(stacked.unique(subset="id", keep="last").sort("id"))  # by key
`,
    },
  ]}
/>

`keep` takes `"first"`, `"last"`, `"any"`, and `"none"`. Use
`"none"` when a duplicate key means the data is broken and you want
to see which rows are involved.

## Check your understanding

<MultipleChoice
  markdown={`Why is plain \`how="vertical"\` strict about matching schemas?

- Relaxing it would make the concatenation much slower
  > The relaxed strategies cost very little; the strictness is about catching mistakes, not about speed.
- Polars cannot represent a frame whose columns have mixed types
  > A frame's columns each have one type, and the relaxed strategies widen them precisely so a union is representable.
- [o] A mismatch usually means a file changed shape, which you want to hear about
  > Silently unioning the schemas turns a broken export into a half-null column nobody notices.
- Only the first frame's schema is read, so later frames must match it
  > Every frame's schema is inspected; the comparison is what produces the error.

Use \`diagonal\` when schemas genuinely differ, not to avoid thinking about why they differ.`}
/>

<MultipleChoice
  markdown={`Two frames of 3 and 2 rows are concatenated with \`how="horizontal"\`. What happens?

- An error, because the frames have different heights
  > Horizontal concatenation pads rather than raising, which is exactly what makes the mismatch easy to miss.
- The result has 2 rows, truncated to the shorter frame
  > No rows are discarded; the longer frame's rows all survive.
- The result has 5 rows, one frame stacked after the other
  > Stacking rows is vertical concatenation; horizontal adds columns instead.
- [o] The result has 3 rows and the shorter frame's column is padded with nulls
  > Rows are paired by position, which is a strong assumption; a shared key column and a join state the relationship instead.

The silence is the problem: a length mismatch usually means the positional assumption was wrong.`}
/>

<MultipleChoice
  markdown={`What is wrong with \`for f in files: df = pl.concat([df, read(f)])\`?

- \`pl.concat\` cannot be called more than once on the same frame
  > It can be called freely; the objection is to how much work the repetition adds up to.
- The result ends up in the wrong row order
  > Row order comes out correct. The cost is time, not correctness.
- [o] Each iteration copies everything accumulated so far, so the work grows quadratically
  > Collect the frames in a list and call \`pl.concat(frames)\` once, or pass a glob to \`scan_parquet()\`.
- Intermediate frames are never freed, so memory grows without bound
  > Python releases each intermediate as it is replaced; the problem is the repeated copying, not a leak.

For files, a glob passed to a \`scan_*\` function is shorter still and lets the optimizer see all of them at once.`}
/>
