Text arrives dirty. Trailing spaces, inconsistent case, a phone
number with three different separators, a category spelled four ways.
Polars puts every string operation behind the `.str` namespace, and
all of them are vectorized.

## Cleaning

<CodeBlock
  adapter="python"
  files={[
    {
      filename: "main.py",
      starterCode: `import polars as pl

df = pl.DataFrame({"city": ["  Oslo ", "LISBON", "bergen  ", "Reykjavík"]})

print(
    df.with_columns(
        stripped=pl.col("city").str.strip_chars(),
        lower=pl.col("city").str.to_lowercase(),
        title=pl.col("city").str.strip_chars().str.to_titlecase(),
        length=pl.col("city").str.len_chars(),
        bytes=pl.col("city").str.len_bytes(),
    )
)
`,
    },
  ]}
/>

`len_chars` and `len_bytes` differ for anything outside ASCII:
"Reykjavík" is 9 characters and 10 bytes. Use `len_chars` when you
mean "how long is this word" and `len_bytes` when you mean "how much
memory does it take".

## The canonical cleaning chain

<CodeBlock
  adapter="python"
  files={[
    {
      filename: "main.py",
      starterCode: `import polars as pl

raw = pl.DataFrame(
    {"category": ["  Books ", "BOOKS", "books", "Book s", "Music", " music"]}
)

print(
    raw.with_columns(
        clean=pl.col("category").str.strip_chars().str.to_lowercase()
    )["clean"].value_counts(sort=True)
)
`,
    },
  ]}
/>

Six raw values collapse to three real ones, and `"Book s"` stays
separate because it is a genuinely different typo that needs a human
decision rather than a lowercase.

## Matching and testing

<CodeBlock
  adapter="python"
  datasets={[{ path: "palmer-penguins.csv", stageAs: "penguins.csv" }]}
  files={[
    {
      filename: "main.py",
      initCode: `import polars as pl
penguins = pl.read_csv("penguins.csv", null_values=["NA"])`,
      starterCode: `species = pl.col("species")

print(
    penguins.select("species")
    .unique()
    .with_columns(
        starts_a=species.str.starts_with("A"),
        ends_o=species.str.ends_with("o"),
        has_in=species.str.contains("in"),
        # A regex: two vowels in a row
        two_vowels=species.str.contains(r"[aeiou]{2}"),
    )
    .sort("species")
)
`,
    },
  ]}
/>

`contains` takes a regex by default. Pass `literal=True` when the
needle contains regex metacharacters you mean literally, such as a
dot in a filename.

<Figure
  slug="pl-working-with-strings-inline-cutout"
  alt="A full column of letter ribbons passing under one wide blade that trims every ribbon in the same stroke"
/>

<Callout type="warn" title="Polars regexes are not Python regexes">
Polars uses Rust's `regex` crate, which guarantees linear-time
matching by leaving out the two features that make backtracking
possible: **backreferences** (`(.)\1`) and **lookaround**
(`(?=...)`, `(?<=...)`). Both raise a `ComputeError` rather than
silently misbehaving. The trade is that no pattern you write can
blow up into catastrophic backtracking on a hostile input. When you
genuinely need one of them, extract the candidates first and do the
final test in Python on the much smaller result.
</Callout>

## Extracting

<CodeBlock
  adapter="python"
  files={[
    {
      filename: "main.py",
      starterCode: `import polars as pl

logs = pl.DataFrame(
    {
        "line": [
            "2026-03-01 ERROR disk full",
            "2026-03-02 WARN  retrying",
            "2026-03-02 INFO  ok",
        ]
    }
)

print(
    logs.with_columns(
        date=pl.col("line").str.extract(r"^(\\d{4}-\\d{2}-\\d{2})"),
        level=pl.col("line").str.extract(r"(ERROR|WARN|INFO)"),
        # extract_all returns every match, as a list
        numbers=pl.col("line").str.extract_all(r"\\d+"),
    )
)
`,
    },
  ]}
/>

`extract` takes the first capture group by default and returns null
when nothing matches, which is exactly the behaviour you want for
messy input: no exception, and the failures are countable.

## Splitting

<CodeBlock
  adapter="python"
  files={[
    {
      filename: "main.py",
      starterCode: `import polars as pl

people = pl.DataFrame(
    {"full_name": ["Ada Lovelace", "Grace Hopper", "Alan Turing"]}
)

# Into a list column
print(people.with_columns(parts=pl.col("full_name").str.split(" ")))

# Into separate columns, via a struct
print(
    people.with_columns(
        pl.col("full_name")
        .str.split_exact(" ", 1)
        .struct.rename_fields(["first", "last"])
        .alias("name")
    ).unnest("name")
)
`,
    },
  ]}
/>

## Replacing

<CodeBlock
  adapter="python"
  files={[
    {
      filename: "main.py",
      starterCode: `import polars as pl

phones = pl.DataFrame(
    {"phone": ["+47 22 33 44 55", "(+351) 21-123-4567", "+354 555 1234"]}
)

print(
    phones.with_columns(
        # replace changes the first match, replace_all changes every match
        first_only=pl.col("phone").str.replace(r"\\s", ""),
        digits=pl.col("phone").str.replace_all(r"[^0-9]", ""),
    )
)
`,
    },
  ]}
/>

<Callout type="warn" title="replace is not replace_all">
`str.replace` changes only the *first* match. Reaching for it when
you meant `replace_all` produces output that looks almost right,
which is worse than output that looks wrong.
</Callout>

## Padding, slicing, and joining

<CodeBlock
  adapter="python"
  files={[
    {
      filename: "main.py",
      starterCode: `import polars as pl

df = pl.DataFrame({"code": ["7", "42", "1234"], "word": ["alpha", "beta", "gamma"]})

print(
    df.with_columns(
        padded=pl.col("code").str.pad_start(5, "0"),
        head=pl.col("word").str.slice(0, 3),
        tail=pl.col("word").str.slice(-2),
    )
)

# Concatenating columns
print(df.select(pl.concat_str("code", "word", separator=":").alias("joined")))

# Concatenating down a column
print(df.select(pl.col("word").str.join(", ").alias("all_words")))
`,
    },
  ]}
/>

Note the two directions: `concat_str` joins several columns within a
row, `str.join` joins one column's values down the rows.

## Check your understanding

<MultipleChoice
  markdown={`\`str.extract(r"(\\d+)")\` is applied to a row containing no digits. What happens?

- The row is dropped from the result
  > Expressions never change a frame's height; \`filter\` is the only thing that removes rows.
- [o] That row gets null
  > No exception, and the failures are countable with \`null_count()\`, which is what you want for messy input.
- An exception is raised for the whole column
  > Raising on the first non-matching row would make the method useless on real data.
- An empty string is returned for that row
  > An empty string would be indistinguishable from a genuine match of zero length; null says "no match" unambiguously.

Count the nulls afterwards to find out how much of your input did not fit the pattern.`}
/>

<MultipleChoice
  markdown={`What is the difference between \`str.replace\` and \`str.replace_all\`?

- \`replace\` takes a literal string and \`replace_all\` takes a regex
  > Both accept a regex by default, and both take \`literal=True\` when you want the pattern treated literally.
- \`replace\` returns a new column while \`replace_all\` modifies in place
  > Nothing in Polars modifies in place; both return a new column.
- [o] \`replace\` changes only the first match in each value
  > Output that is almost right is worse than output that is obviously wrong, which is what makes this one costly.
- \`replace\` works on one column and \`replace_all\` across every column
  > Which columns are affected is decided by the expression they are attached to, not by the method name.

Stripping non-digits from a phone number with \`replace\` leaves all but the first separator in place.`}
/>

<MultipleChoice
  markdown={`Which pair joins values *across columns within a row*, and which joins them *down a column*?

- Both operate down a column, and only their separators differ
  > They produce different shapes: one returns a value per row, the other a single value for the whole column.
- Both operate across a row, and only the argument type differs
  > \`str.join\` reduces a column to one string, which is a down-the-column operation by definition.
- \`str.join\` works across a row, \`concat_str\` works down a column
  > This has the two the wrong way around.
- [o] \`concat_str\` works across a row, \`str.join\` works down a column
  > One returns a column the same height as the frame; the other returns a single value.

The distinction matters because their outputs have different shapes.`}
/>
