Everything so far has been eager: each method ran when Python reached
it. Polars has a second mode where methods build a *plan* and nothing
executes until you ask.

## The two objects

```python
import polars as pl

eager = pl.read_csv("penguins.csv", null_values=["NA"])
lazy = pl.scan_csv("penguins.csv", null_values=["NA"])

print(type(eager).__name__)
print(type(lazy).__name__)

# A lazy chain returns another LazyFrame. No data has moved.
plan = lazy.filter(pl.col("body_mass_g") > 4000).select("species", "body_mass_g")
print(type(plan).__name__)

# collect() is what runs it
print(plan.collect().head(3))
```

<Callout type="info" title="Not runnable in the browser">
The Polars build that ships with Pyodide is compiled without the streaming
engine, so `engine="streaming"` raises here.
The code is correct and works on a normal Polars install; it is shown
here rather than run.
</Callout>


| | Eager | Lazy |
| --- | --- | --- |
| Built by | `pl.read_csv`, `pl.DataFrame` | `pl.scan_csv`, `df.lazy()` |
| Runs | immediately, step by step | at `.collect()` |
| Optimized | no | yes, over the whole query |
| Can inspect the plan | no | `.explain()` |
| Intermediate results | materialized | often never exist |

The API is otherwise the same. Nearly every method you have learned
works identically on both.

Read the plan from the bottom up. Polars pushed the column selection
and the filter down into the CSV reader itself: `PROJECT 3/10 COLUMNS`
says three of the ten columns are parsed, and `SELECTION` says the
filter is applied while parsing rather than afterwards.

Three, not two, is the detail worth noticing. You asked for `carat`
and `price`, but the filter needs `cut`, so the optimizer works out
that it must read that column too and then drop it. The other seven
are never materialized at all.

## Moving between the two

```python
import polars as pl

df = pl.read_csv("penguins.csv", null_values=["NA"])

# Eager to lazy, to get the optimizer on an in-memory frame
result = (
    df.lazy()
    .group_by("species")
    .agg(pl.col("body_mass_g").mean().round(0))
    .sort("species")
    .collect()
)
print(result)

# Lazy to eager
back = pl.scan_csv("penguins.csv", null_values=["NA"]).collect()
print(type(back).__name__)
```

<Callout type="info" title="Not runnable in the browser">
The Polars build that ships with Pyodide is compiled without the streaming
engine, so `engine="streaming"` raises here.
The code is correct and works on a normal Polars install; it is shown
here rather than run.
</Callout>


`df.lazy()` is free: it wraps the frame you already have in a plan.
Worth doing for any chain of more than two or three steps, even when
the data is already in memory.

## When eager is the right choice

Lazy is the default recommendation, not a rule. Prefer eager when:

- **You are exploring interactively.** Seeing each intermediate frame
  is the point, and `collect()` on every line is noise.
- **The next step depends on a value you have to look at.** If a
  Python `if` needs the row count, you have to materialize it.
- **You need `pivot`.** Its output schema depends on the data, so it
  is eager-only.
- **The data is small.** Below a few thousand rows the optimizer has
  nothing meaningful to save.

<Callout type="info" title="collect() once, at the end">
The common mistake is collecting in the middle of a chain, which
throws away the optimizer's view of everything downstream. If you
need the same intermediate result twice, that is what
`pl.collect_all` is for: it runs several plans together and shares
the common work.
</Callout>

<CodeBlock

## Check your understanding

<MultipleChoice
  markdown={`\`pl.scan_csv("big.csv").filter(pl.col("a") > 5)\` is assigned to a variable. How much of the file has been read?

- The whole file, since the filter has to examine every row
  > The filter is part of the plan, not an action; nothing examines anything until \`collect()\`.
- Enough rows to determine the schema, then reading pauses
  > Schema inference happens at scan time for CSV, but the point here is that no *filtering* work has begun.
- [o] None of it: the variable holds a plan, not data
  > That is the whole distinction, and it is what lets the optimizer rewrite the plan before it runs.
- One row group, so the filter can be tested for selectivity
  > No sampling for selectivity happens, and CSV has no row groups to sample.

The plan is a value you can inspect, extend, and pass around before any I/O occurs.`}
/>

<MultipleChoice
  markdown={`Why is calling \`collect()\` in the middle of a chain usually a mistake?

- \`collect()\` may only be called once per LazyFrame
  > It can be called as often as you like; each call runs the plan again.
- It converts the frame to pandas, which is slow
  > It produces a Polars \`DataFrame\`; pandas is not involved unless you ask for it.
- [o] The optimizer can no longer see the downstream steps, so it cannot push filters or drop columns
  > Collect once, at the end, and use \`pl.collect_all\` when you genuinely need two results from a shared source.
- The intermediate result is discarded, so the later steps recompute it
  > The collected frame is kept and reused; what is lost is planning information, not the data.

Everything after the \`collect()\` is planned in isolation from everything before it.`}
/>

<MultipleChoice
  markdown={`Which of these genuinely requires eager mode?

- Grouping by two columns and aggregating
  > Grouped aggregation is fully supported lazily and is one of the operations the optimizer helps most.
- Reading a CSV larger than memory
  > That is lazy mode's strongest case, especially with the streaming engine.
- Joining two frames on a key
  > Joins work lazily, and the optimizer can reorder and push filters through them.
- [o] \`pivot\`, whose output column names come from the data
  > Its schema cannot be known before execution, so it is a \`DataFrame\` method only.

Collect first, then pivot; it is the one operation the lazy API cannot express.`}
/>
