The optimizer is why expressions were worth the indirection. It takes
the plan you described and rewrites it into an equivalent plan that
does less work.

## Reading a plan

`explain()` prints two plans. `optimized=False` shows what you wrote;
the default shows what will actually run.

<CodeBlock
  adapter="python"
  datasets={[{ path: "diamonds.csv", stageAs: "diamonds.csv" }]}
  files={[
    {
      filename: "main.py",
      initCode: `import polars as pl`,
      starterCode: `q = (
    pl.scan_csv("diamonds.csv")
    .with_columns((pl.col("price") / pl.col("carat")).alias("per_carat"))
    .filter(pl.col("cut") == "Ideal")
    .filter(pl.col("carat") > 1.0)
    .select("cut", "carat", "per_carat")
)

print("── as written")
print(q.explain(optimized=False))
print("── optimized")
print(q.explain())
`,
    },
  ]}
/>

Plans read bottom-up: the leaf is the data source, each line above it
consumes the one below. Compare the two and you can see the rewrites.

## The main rewrites

### Projection pushdown

Polars works out which columns the query actually needs and tells the
reader to parse only those. On a wide Parquet file this is often the
single biggest saving, because an unread column costs nothing at all.

### Predicate pushdown

Filters move as close to the source as possible. A filter that
reaches the scan is applied while parsing, so rejected rows are never
built into a frame. With Parquet it goes further: row groups whose
statistics prove no row can match are skipped without decompression.

<Chart slug="predicate-pushdown-rows" />

### Slice pushdown

`head(10)` at the end of a chain becomes "stop reading after enough
rows" at the source, rather than "read everything, then take ten".

### Common subexpression elimination

An expression written twice is computed once.

<CodeBlock
  adapter="python"
  datasets={[{ path: "diamonds.csv", stageAs: "diamonds.csv" }]}
  files={[
    {
      filename: "main.py",
      initCode: `import polars as pl`,
      starterCode: `per_carat = pl.col("price") / pl.col("carat")

q = pl.scan_csv("diamonds.csv").select(
    cheap=(per_carat < 2000),
    expensive=(per_carat > 8000),
    ratio=per_carat.round(0),
)

print(q.explain())
print(q.head(3).collect())
`,
    },
  ]}
/>

This is why "repeat the expression rather than splitting into two
`with_columns` calls" is sound advice in a lazy query: the repetition
is free.

### Filters merge, projections collapse

Two consecutive `filter` calls become one conjunction. Two
consecutive `select` calls collapse into one. Writing a chain in
readable steps costs nothing.

## Showing the saving

<CodeBlock
  adapter="python"
  datasets={[{ path: "diamonds.csv", stageAs: "diamonds.csv" }]}
  files={[
    {
      filename: "main.py",
      initCode: `import time
import polars as pl`,
      starterCode: `def timed(label, fn):
    start = time.perf_counter()
    value = fn()
    print(f"{label:<24} {(time.perf_counter() - start) * 1000:7.1f} ms -> {value}")

# Optimizations on
timed(
    "optimized",
    lambda: pl.scan_csv("diamonds.csv")
    .filter(pl.col("cut") == "Ideal")
    .select(pl.col("price").mean().round(0))
    .collect()
    .item(),
)

# The same query with the optimizer turned off
timed(
    "no pushdown",
    lambda: pl.scan_csv("diamonds.csv")
    .filter(pl.col("cut") == "Ideal")
    .select(pl.col("price").mean().round(0))
    .collect(optimizations=pl.QueryOptFlags(projection_pushdown=False, predicate_pushdown=False))
    .item(),
)
`,
    },
  ]}
/>

Same answer, different amount of work. `QueryOptFlags` exists mostly
for debugging: if a lazy query gives a different answer from the
eager one, turning optimizations off one at a time is how you find
out which rewrite the bug is hiding behind.

## What the optimizer cannot do

<CodeBlock
  adapter="python"
  datasets={[{ path: "diamonds.csv", stageAs: "diamonds.csv" }]}
  files={[
    {
      filename: "main.py",
      initCode: `import polars as pl`,
      starterCode: `# A Python function is opaque: Polars cannot see inside it, so it
# cannot be reordered, pushed down, or parallelized.
opaque = (
    pl.scan_csv("diamonds.csv")
    .with_columns(
        pl.col("price").map_elements(lambda p: p * 2, return_dtype=pl.Int64)
    )
    .select("price")
)

print(opaque.explain())
`,
    },
  ]}
/>

Three things block the optimizer, and all three are worth avoiding:

1. **`map_elements` with a Python callable.** Opaque, row-at-a-time,
   and it holds the interpreter lock. Almost always replaceable with
   an expression.
2. **A `collect()` in the middle of a chain.** Everything after it is
   planned separately from everything before it.
3. **Converting to and from another library mid-pipeline.** A
   `to_pandas()` round trip ends the plan.

## Writing optimizer-friendly queries

- **Start from `scan_*`, not `read_*`.** Pushdown into a file is the
  biggest single win, and it is only available if Polars owns the
  read.
- **Filter early in the text, but do not agonize.** The optimizer
  moves filters anyway; writing them early is for the reader.
- **Prefer Parquet.** Its row-group statistics let predicate pushdown
  skip data without decompressing it, which CSV cannot do.
- **Select what you need.** Even with pushdown, an explicit `select`
  documents the query's real inputs.
- **Keep expressions expressions.** Anything expressible with
  `when/then`, `str`, `dt`, or arithmetic will be faster and visible
  to the planner than the same logic in Python.

## Check your understanding

<MultipleChoice
  markdown={`On a 200-column Parquet file, a query uses 4 columns. What does projection pushdown save?

- Nothing: Parquet files must be read in full before columns can be selected
  > Parquet is columnar precisely so a reader can fetch individual columns; that is the format's main advantage.
- Only memory, since all 200 columns are still decompressed
  > Unread columns are neither fetched nor decompressed, so the saving is in I/O and CPU as well.
- [o] The other 196 columns are never fetched or decompressed at all
  > This is usually the single biggest saving on a wide file, and it is what \`scan_*\` exists to enable.
- It reorders the columns so the four appear first, speeding up access
  > No reordering occurs; the reader simply skips the column chunks the query does not name.

An unread column in a columnar file costs nothing, which is what makes wide tables cheap.`}
/>

<MultipleChoice
  markdown={`Why does writing the same subexpression twice cost nothing in a lazy query?

- Polars caches the result of every expression it has evaluated before
  > No cross-query cache exists; the saving comes from analysing this plan, not from remembering earlier ones.
- The second occurrence is silently dropped from the plan
  > Both occurrences remain in the output; what is shared is the computation behind them.
- [o] Common subexpression elimination computes it once and reuses the result
  > Which is why repeating an expression beats splitting a chain into two \`with_columns\` calls.
- Expressions are lazy, so neither occurrence is ever evaluated
  > They are certainly evaluated; laziness postpones the work rather than avoiding it.

You can write for readability and let the planner remove the duplication.`}
/>

<MultipleChoice
  markdown={`Which of these stops the optimizer from seeing through your query?

- Chaining five \`with_columns\` calls in a row
  > Consecutive projections collapse into one, so the chain costs nothing beyond its readability benefit.
- Writing two \`filter\` calls instead of one \`&\` expression
  > Consecutive filters merge into a single conjunction during optimization.
- [o] \`map_elements\` with a Python lambda
  > Opaque to the planner, row-at-a-time, and it holds the interpreter lock.
- Sorting before a \`group_by\`
  > A sort is a normal plan node the optimizer understands and can sometimes even remove.

If a lazy query is unexpectedly slow, look for a Python callable in the plan first.`}
