Before you compute anything on a new dataset, you look at it. This
page is the checklist, and it is worth running every single time. The
number of analyses that quietly produce a wrong answer because nobody
noticed a duplicated key or a column of strings where numbers were
expected is very large.

`schema` is a mapping from column name to dtype. Reading it first is
a habit worth building: half of all "why is this not working"
questions are answered by noticing that a column is `String` when you
assumed `Int64`.

## head, tail, sample

<CodeBlock
  adapter="python"
  datasets={[{ path: "palmer-penguins.csv", stageAs: "penguins.csv" }]}
  files={[
    {
      filename: "main.py",
      initCode: `import polars as pl
penguins = pl.read_csv("penguins.csv", null_values=["NA"])`,
      starterCode: `print(penguins.head(3))
print(penguins.tail(2))

# A random sample is the one that catches sorted-by-something files
print(penguins.sample(3, seed=0))
`,
    },
  ]}
/>

`head` on a file that arrived sorted by date shows you January and
nothing else. `sample` with a fixed `seed` gives you a reproducible
look at the middle.

## glimpse, for wide tables

When a table has forty columns, printing it is useless: the output
wraps and you see nothing. `glimpse` transposes the problem, one
column per line.

<CodeBlock
  adapter="python"
  datasets={[{ path: "diamonds.csv", stageAs: "diamonds.csv" }]}
  files={[
    {
      filename: "main.py",
      initCode: `import polars as pl
diamonds = pl.read_csv("diamonds.csv")`,
      starterCode: `diamonds.glimpse()
`,
    },
  ]}
/>

Every column, its dtype, and its first few values, on one line each.
For anything wider than about eight columns this is the better first
look.

Unlike its pandas namesake, Polars' `describe` covers *every* column,
including strings, and puts `null_count` right there in the table.
Read down that row first. Two missing bill lengths is a note; two
hundred is a different analysis.

`value_counts` on a categorical column is the fastest way to find

categories the moment you look.

## Checking for duplicates

This is the check people skip and then regret, because a duplicated
key silently multiplies rows in a later join.

<CodeBlock
  adapter="python"
  files={[
    {
      filename: "main.py",
      starterCode: `import polars as pl

orders = pl.DataFrame(
    {
        "order_id": [1, 2, 2, 3, 4, 4],
        "amount": [10, 20, 20, 30, 40, 41],
    }
)

print("fully duplicated rows:", orders.is_duplicated().sum())
print("duplicate order_ids  :", orders["order_id"].is_duplicated().sum())
print(orders.filter(pl.col("order_id").is_duplicated()))
`,
    },
  ]}
/>

Note the difference: order 2 is duplicated *entirely*, while order 4
appears twice with different amounts. The second case is the
dangerous one, because deduplicating rows will not fix it and you
have to decide which amount is right.

## An inspection routine

Put together, the first thing to run on an unfamiliar file:

<CodeBlock
  adapter="python"
  datasets={[{ path: "diamonds.csv", stageAs: "diamonds.csv" }]}
  files={[
    {
      filename: "main.py",
      initCode: `import polars as pl`,
      starterCode: `def inspect(df: pl.DataFrame, name: str = "frame") -> None:
    print(f"── {name}: {df.height:,} rows x {df.width} columns")
    summary = pl.DataFrame(
        {
            "column": df.columns,
            "dtype": [str(dt) for dt in df.dtypes],
            "nulls": df.null_count().row(0),
            "distinct": [df[c].n_unique() for c in df.columns],
        }
    )
    print(summary)

inspect(pl.read_csv("diamonds.csv"), "diamonds")
`,
    },
  ]}
/>

A column whose `distinct` count equals the row count is a candidate
key. A column whose `distinct` count is 1 carries no information and
can usually be dropped.

## Check your understanding

<MultipleChoice
  markdown={`Why is \`sample(3, seed=0)\` often more informative than \`head(3)\`?

- Sampling is faster than reading the first rows of a frame
  > Reading the first three rows is the cheaper operation; sampling has to reach across the frame.
- \`head\` returns a lazy view while \`sample\` returns real data
  > Both return an ordinary DataFrame here. The difference is which rows you see, not how they are computed.
- [o] Files often arrive sorted, so the first rows are unrepresentative
  > A file sorted by date shows you January in \`head\` and nothing about the rest of the year.
- \`head\` skips rows containing nulls, which hides missing data
  > Neither method filters nulls; \`head\` gives the first rows exactly as they are, nulls included.

The \`seed\` keeps the sample reproducible so a colleague sees the same rows you did.`}
/>

<MultipleChoice
  markdown={`\`orders["order_id"].is_duplicated().sum()\` returns 4, but \`orders.is_duplicated().sum()\` returns 2. What does that tell you?

- Two rows have a null \`order_id\`, which is counted differently by each method
  > Nulls would appear in both counts the same way; the gap here is about which columns each method compares.
- The frame contains exactly two duplicate rows and four unique ones
  > The second count is of rows involved in duplication, not of unique rows, so this reading does not follow from the numbers.
- [o] Some IDs repeat with *different* values in the other columns
  > Deduplicating rows will not fix those, because the rows genuinely differ. You have to decide which record is correct.
- The frame is sorted by \`order_id\`, which makes the two counts disagree
  > Row order has no effect on either count; both compare values rather than positions.

The key-duplicated-but-row-different case is the one that silently multiplies rows in a later join.`}
/>

<MultipleChoice
  markdown={`In a profile table, a column's distinct count equals the number of rows. What does that suggest?

- The column is constant and carries no information
  > A constant column has a distinct count of 1, which is the opposite end of the range.
- The column contains only null values throughout
  > An all-null column has a distinct count of zero or one, not one per row.
- The column must be numeric rather than text
  > Distinct counts say nothing about type; a string column of unique identifiers behaves the same way.
- [o] It is a candidate key: every row has its own value
  > Useful for spotting an ID column, and for spotting that a supposed ID column is *not* one.

The other end of the range is just as useful: a distinct count of 1 means the column can usually be dropped.`}
/>
