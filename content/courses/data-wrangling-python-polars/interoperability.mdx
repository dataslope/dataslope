Polars does not have to be the only thing in your stack. Because it
stores Arrow, several of these crossings are close to free; because
some libraries want their own layout, others are not.

## pandas, both directions

<CodeBlock

      starterCode: `pdf = penguins.to_pandas()
print(type(pdf).__name__, pdf.shape)

print(type(back).__name__, back.shape)
print(back.schema)
`,
    },
  ]}
/>

<Callout type="info" title="use_pyarrow_extension_array avoids a copy">
`to_pandas()` converts each column into a NumPy array, which is a
copy and which turns an integer column with nulls into a float one.
`to_pandas(use_pyarrow_extension_array=True)` gives pandas
Arrow-backed columns instead: no copy of the values, and nulls stay
nulls without changing the dtype.
</Callout>

```python
import polars as pl

df = pl.DataFrame({"n": [1, 2, None, 4]})

numpy_backed = df.to_pandas()
arrow_backed = df.to_pandas(use_pyarrow_extension_array=True)

print("numpy-backed dtype:", numpy_backed["n"].dtype)
print("arrow-backed dtype:", arrow_backed["n"].dtype)
print(numpy_backed["n"].tolist())
```

<Callout type="info" title="Not runnable in the browser">
pandas records whether pyarrow is importable when it is first imported, and
caches the answer. In this runtime pandas loads with the page and pyarrow is
fetched later, on the first call that needs it, so pandas has already decided
Arrow is unavailable. Re-importing pandas to refresh that check changes how
`read_csv()` handles explicit dtypes and broke unrelated lessons, so the block is
shown rather than run.
</Callout>

The integer column became `float64` on the NumPy path, because that
is the only way NumPy can carry a missing value. This is the pandas
null problem from the comparison chapter, arriving through the back
door.

## NumPy

<CodeBlock
  adapter="python"
  datasets={[{ path: "palmer-penguins.csv", stageAs: "penguins.csv" }]}

    {
      filename: "main.py",

import polars as pl

      starterCode: `# One column
masses = penguins["body_mass_g"].drop_nulls().to_numpy()

X = penguins.select("bill_length_mm", "bill_depth_mm").drop_nulls().to_numpy()

# And back
display(pl.from_numpy(X, schema=["length", "depth"]).head(3))
`,
    },
  ]}
/>

A single numeric column with no nulls converts without copying,
because Arrow's values buffer already has NumPy's layout. Nulls, or
any string column, force a copy.

## Arrow

<CodeBlock
  adapter="python"
  datasets={[{ path: "palmer-penguins.csv", stageAs: "penguins.csv" }]}
  files={[
    {
      filename: "main.py",
      initCode: `import polars as pl
penguins = pl.read_csv("penguins.csv", null_values=["NA"])`,
      starterCode: `table = penguins.to_arrow()
print(type(table).__name__, table.num_rows, "rows")
print(table.schema)

back = pl.from_arrow(table)
print(type(back).__name__, back.shape)
`,
    },
  ]}
/>

This is the cheap one. Polars already stores Arrow, so `to_arrow()`
hands over the same buffers. Any library speaking Arrow (DuckDB,
PyArrow, DataFusion, an Arrow Flight client) can take a Polars frame
without a serialization step.

## SQL, against a Polars frame

<CodeBlock
  adapter="python"
  datasets={[{ path: "palmer-penguins.csv", stageAs: "penguins.csv" }]}
  files={[
    {
      filename: "main.py",
      initCode: `import polars as pl
penguins = pl.read_csv("penguins.csv", null_values=["NA"])`,
      starterCode: `display(
    pl.sql(
        """
        SELECT species, COUNT(*) AS n, ROUND(AVG(body_mass_g)) AS avg_mass
        FROM penguins
        WHERE body_mass_g IS NOT NULL
        GROUP BY species
        ORDER BY avg_mass DESC
        """
    ).collect()
)
`,
    },
  ]}
/>

`pl.sql` resolves table names from frames in scope and returns a
`LazyFrame`, so the result goes through the same optimizer. Useful
for a query that is genuinely easier to read as SQL, and for porting
one that already exists.

## The dataframe interchange protocol

<CodeBlock
  adapter="python"
  files={[

# Standard protocol: any library implementing it can be consumed with

display(pl.from_dataframe(pdf))
`,
    },
  ]}
/>

Worth knowing about if you write a library: accepting anything with
`__dataframe__` means you accept Polars, pandas, cuDF, and Vaex
without depending on any of them.

## What each crossing costs

| Crossing | Cost |
| --- | --- |
| `to_arrow()` / `from_arrow()` | close to free, shared buffers |
| `to_pandas(use_pyarrow_extension_array=True)` | close to free |
| `to_pandas()` | a copy per column, and integer columns with nulls become floats |
| `to_numpy()`, one numeric column, no nulls | free |
| `to_numpy()`, anything else | a copy |
| `to_dicts()`, `to_list()` | a copy, plus a Python object per value |
| `pl.sql` | none, it is the same engine |

`to_dicts()` is the expensive one people reach for without thinking:
it builds a Python dictionary per row. On a million rows that is a
million dictionaries, which is slower than the query that produced
them.

## Practice

Try it yourself before reading on. Convert the frame to pandas twice, once
with the default NumPy-backed conversion and once with
`use_pyarrow_extension_array=True`, and compare what happened to the integer
column that contains a null.

```python
import polars as pl
import pandas as pd

df = pl.DataFrame({"n": [1, 2, None, 4], "label": ["a", "b", "c", "d"]})

naive = df.to_pandas()
arrow = df.to_pandas(use_pyarrow_extension_array=True)

print("naive :", naive["n"].dtype)  # float64
print("arrow :", arrow["n"].dtype)  # int64[pyarrow]
```

The default conversion has to widen `n` to `float64`, because a NumPy integer
array has no way to represent a missing value. The Arrow-backed conversion
keeps it an integer and carries the null alongside, which is the whole reason
to reach for it when types matter downstream.

<Callout type="info" title="Not runnable in the browser">
`int64[pyarrow]` needs pandas to have found pyarrow when pandas itself was
imported, and pandas is imported before any lesson code runs. The code is
correct on a normal install; it is shown rather than run.
</Callout>

- Arrow tables are lazy, so nothing is materialized until used
  > Arrow tables hold real data; laziness is not part of the format.
- Arrow compresses the data, so there is less of it to move
  > In-memory Arrow is uncompressed. The saving comes from not moving the data at all.
- [o] Polars already stores Arrow, so the buffers are handed over rather than converted
  > \`to_pandas()\` by default converts each column into a NumPy array, which is a copy.
- \`to_arrow()\` returns only the schema, deferring the values
  > The full table is returned; only the copying is avoided.

Arrow interchange is the reason a Polars frame can reach DuckDB or PyArrow without a serialization step.`}

<MultipleChoice
  markdown={`An \`Int64\` column with one null becomes \`float64\` after \`to_pandas()\`. Why?

- Polars casts every column to float on the way out for consistency
  > Columns without nulls keep their integer dtype; the widening is caused specifically by the missing value.
- pandas does not support 64-bit integers
  > It supports them fine. What a NumPy-backed integer array cannot carry is a missing value.
- [o] The default conversion is NumPy-backed, and NumPy needs a float to represent the missing value
  > \`use_pyarrow_extension_array=True\` gives Arrow-backed columns instead, and the dtype survives.
- The null was converted to NaN, which pandas then rounds
  > No rounding occurs; the dtype change happens because NaN is a float and forces the whole array to be floats.

This is the pandas null problem arriving through the back door of a conversion.`}
