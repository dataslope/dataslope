`filter()` keeps the rows where a Boolean expression is true. That
sentence hides one detail that causes more bugs than any other in
this course: a null is not true, and it is not false either.

## Combining conditions

Several arguments to `filter()` are combined with AND. For anything
else, use the operators.

<Figure
  slug="pl-filtering-rows-combining-conditions-inline-cutout"
  alt="Two masks laid one over the other above a stack of rows, only the squares open in both letting a row through"
  caption="Stacked conditions pass only the rows that satisfy every one of them."
/>

| Logic | Operator |
| --- | --- |
| and | `&` |
| or | `\|` |
| not | `~` |

<CodeBlock
  adapter="python"
  datasets={[{ path: "palmer-penguins.csv", stageAs: "penguins.csv" }]}
  files={[
    {
      filename: "main.py",
      initCode: `import polars as pl
penguins = pl.read_csv("penguins.csv", null_values=["NA"])`,
      starterCode: `# AND, the readable way
print(penguins.filter(
    pl.col("species") == "Adelie",
    pl.col("body_mass_g") > 4000,
).height)

# OR needs the operator, and parentheses around each side
print(penguins.filter(
    (pl.col("species") == "Gentoo") | (pl.col("body_mass_g") > 5000)
).height)

# NOT
print(penguins.filter(~(pl.col("island") == "Biscoe")).height)
`,
    },
  ]}
/>

<Callout type="warn" title="Python's and / or / not do not work here">
`pl.col("a") > 1 and pl.col("b") < 2` raises, because Python's `and`
calls `__bool__` on the expression and an expression has no truth
value. This is a hard error rather than a silent wrong answer, which
is the good outcome. Use `&`, `|`, `~`, with parentheses.
</Callout>

## The null trap

This is the page's real lesson. Comparing anything with null gives
null, and `filter()` keeps only rows that are *true*. So a null row is
dropped by a condition **and** by its negation.

<CodeBlock
  adapter="python"
  files={[
    {
      filename: "main.py",
      starterCode: `import polars as pl

df = pl.DataFrame({"x": [1, None, 10]})

print("x > 5      :", df.filter(pl.col("x") > 5).height)
print("x <= 5     :", df.filter(pl.col("x") <= 5).height)
print("total rows :", df.height)   # 1 + 1 != 3

# The comparison itself shows why
display(df.with_columns(gt=pl.col("x") > 5, le=pl.col("x") <= 5))
`,
    },
  ]}
/>

One plus one does not make three. The null row vanished from both
halves of what looked like an exhaustive split. If you need it, say
so:

<CodeBlock
  adapter="python"
  files={[
    {
      filename: "main.py",
      starterCode: `import polars as pl

df = pl.DataFrame({"x": [1, None, 10]})

# Keep the null rows explicitly
print(df.filter((pl.col("x") <= 5) | pl.col("x").is_null()).height)

# Or decide up front what a missing value counts as
print(df.filter(pl.col("x").fill_null(0) <= 5).height)
`,
    },
  ]}
/>

This is not a Polars quirk. It is SQL's three-valued logic, and
pandas behaves the same way. Polars makes it visible sooner because
it does not conflate null with `NaN` or with zero.

## Filtering by a computed value

The expression can reference aggregations of the same frame.

<CodeBlock
  adapter="python"
  datasets={[{ path: "palmer-penguins.csv", stageAs: "penguins.csv" }]}
  files={[
    {
      filename: "main.py",
      initCode: `import polars as pl
penguins = pl.read_csv("penguins.csv", null_values=["NA"])`,
      starterCode: `# Heavier than average
print(penguins.filter(
    pl.col("body_mass_g") > pl.col("body_mass_g").mean()
).height)

# Heavier than their own species' average, using a window
print(penguins.filter(
    pl.col("body_mass_g") > pl.col("body_mass_g").mean().over("species")
).height)
`,
    },
  ]}
/>

The second one is a preview of window expressions, which get their
own page. `.over("species")` makes the mean a per-species mean while
keeping one value per row.

## Filtering groups rather than rows

Sometimes the unit you want to keep or drop is a whole group.

<Figure
  slug="pl-filtering-rows-inline-cutout"
  alt="A stack of rows dropping through a mask laid over them, only the rows aligned with open squares getting through"
  caption="Sometimes the unit you keep is a whole group rather than a single row."
/>

<CodeBlock
  adapter="python"
  datasets={[{ path: "palmer-penguins.csv", stageAs: "penguins.csv" }]}
  files={[
    {
      filename: "main.py",
      initCode: `import polars as pl
penguins = pl.read_csv("penguins.csv", null_values=["NA"])`,
      starterCode: `# Keep only islands with more than 100 penguins
display(
    penguins.filter(pl.len().over("island") > 100)
    .group_by("island")
    .agg(pl.len())
    .sort("island")
)
`,
    },
  ]}
/>

## Check your understanding

<MultipleChoice
  markdown={`A frame has 100 rows and 5 nulls in \`x\`. How many rows do \`filter(x > 0)\` and \`filter(x <= 0)\` return between them?

- 100, since every row satisfies exactly one of the two conditions
  > That holds only when \`x\` is never null; a null satisfies neither condition.
- 105, because the null rows are returned by both filters
  > A null comparison is null rather than true, so those rows are returned by neither filter.
- [o] 95, because the 5 null rows satisfy neither condition
  > Add \`| pl.col("x").is_null()\` to whichever side should own them.
- It depends on whether the nulls are stored as NaN or as null
  > Polars keeps the two distinct, and a genuine null behaves this way regardless of what a float NaN would do.

Two conditions that look exhaustive are not exhaustive when nulls are present.`}
/>

<MultipleChoice
  markdown={`Why does \`filter(pl.col("a") > 1 and pl.col("b") < 2)\` raise rather than silently misbehave?

- Polars inspects the source code and rejects the \`and\` keyword
  > No source inspection happens; the failure comes from ordinary Python semantics on an object that refuses to be coerced.
- \`and\` is valid only inside \`when/then\` chains in Polars
  > It is not valid anywhere in an expression; \`&\` is the operator for conjunction in every context.
- [o] Python's \`and\` asks the expression for a truth value, and an expression refuses to give one
  > \`__bool__\` raising is deliberate: returning an arbitrary answer would produce a silently wrong filter.
- The two comparisons produce different column names, which cannot be combined
  > Names play no part here; the error occurs before any frame or column naming is involved.

Use \`&\`, \`|\`, and \`~\`, and parenthesise each comparison.`}
/>

<MultipleChoice
  markdown={`What does \`filter(pl.len().over("island") > 100)\` do?

- Keeps the first 100 rows of each island
  > Taking the first rows per group is \`head()\` inside a \`group_by()\`; this expression compares group sizes instead.
- [o] Keeps every row belonging to an island that has more than 100 rows
  > \`over()\` computes the group's size and broadcasts it to each of that group's rows, so the filter acts group-wise.
- Keeps islands whose name is longer than 100 characters
  > \`pl.len()\` counts rows in the window; string length would be \`str.len_chars()\`.
- Returns one row per island, with those over 100 rows kept
  > Filtering never collapses a frame; every surviving row of a qualifying island is returned.

Filtering on a windowed aggregate is how you keep or drop whole groups without leaving the row level.`}
/>
