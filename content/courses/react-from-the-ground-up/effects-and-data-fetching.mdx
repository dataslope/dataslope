Rendering should be **pure**: given the same props and state, a
component returns the same JSX and touches nothing else. But real apps
need to reach *outside* the component too, fetch data, start a timer,
subscribe to something. Those are **side effects**, and `useEffect()` is
where they belong.

## useEffect basics

The second argument is the whole of the API: it decides *when* the effect runs again.

<SyntaxBreakdown
  parts={[
    { text: "useEffect(" },
    { text: "() => { ... }", label: "the effect, run after render" },
    { text: ", [userId]", label: "re-run only when this changes; [] means once" },
    { text: ")" },
  ]}
/>

`useEffect(fn, deps)` runs `fn` *after* the component renders. The
**dependency array** controls how often:

| Deps | Effect runs |
| --- | --- |
| `[]` (empty) | once, after the first render (on "mount") |
| `[a, b]` | after mount, and whenever `a` or `b` changes |
| *omitted* | after **every** render (rarely what you want) |

This timer starts once on mount and cleans itself up, note the
returned function, React calls it to tear the effect down:

<CodeBlock
  adapter="react"
  files={[
    {
      filename: "main.tsx",
      starterCode: `import { useState, useEffect } from "react";
import { createRoot } from "react-dom/client";

function Clock() {
  const [seconds, setSeconds] = useState(0);

  useEffect(() => {
    const id = setInterval(() => setSeconds((s) => s + 1), 1000);
    return () => clearInterval(id); // cleanup on unmount
  }, []); // [] → set up the interval once

  return (
    <main style={{ fontFamily: "system-ui", margin: 24 }}>
      <h1>{seconds}s elapsed</h1>
    </main>
  );
}

createRoot(document.getElementById("root")!).render(<Clock />);
`,
    },
  ]}
/>

The clock below is live and ticking right now. Its effect starts one
`setInterval()` on mount and returns a cleanup that clears it, exactly the
shape above:

<ReactPreview
  code={`function Clock() {
  const [now, setNow] = useState(() => new Date());

  useEffect(() => {
    const id = setInterval(() => setNow(new Date()), 1000);
    return () => clearInterval(id);   // cleanup on unmount
  }, []);

  return <time>{now.toLocaleTimeString()}</time>;
}`}
>
  <ClockDemo />
</ReactPreview>

<Callout type="warn" title="Cleanup prevents leaks">
If your effect starts something ongoing, an interval, a subscription,
an event listener, return a function that stops it. React runs that
cleanup before re-running the effect and when the component unmounts.
Forget it and you'll stack up duplicate timers and listeners.
</Callout>

Effects also let you *subscribe* to the browser. This one adds a
`resize` listener on mount and removes it in cleanup, resize your
window and the number tracks it live:

<ReactPreview
  code={`function WindowWidth() {
  const [width, setWidth] = useState(window.innerWidth);

  useEffect(() => {
    const onResize = () => setWidth(window.innerWidth);
    window.addEventListener("resize", onResize);
    return () => window.removeEventListener("resize", onResize);
  }, []);

  return <div>{width}px</div>;
}`}
>
  <WindowWidthDemo />
</ReactPreview>

## Fetching data on mount

The classic use of `useEffect([])` is loading data when a component
first appears. The shape is always the same: a `loading` flag, a
`data` state, and an effect that fetches and fills them in.

<Figure
  slug="rx-effects-and-data-fetching-inline-cutout"
  alt="A panel that lights up on the left, sending a cord out to a server drum in the middle, and filling one of its own slots when the parcel returns"
  caption="An effect reaches outside React, and fills state in when the answer arrives."
/>

```tsx
useEffect(() => {
  let active = true;
  fetch("/api/posts")
    .then((res) => res.json())
    .then((data) => { if (active) setPosts(data); });
  return () => { active = false; }; // ignore a late response
}, []);
```

The `active` flag is a common guard: if the component unmounts (or the
inputs change) before the request finishes, you skip the now-stale
`setState`. Below, a stand-in `loadPosts()` resolves local data so it
runs offline, but the effect is identical to a real `fetch()`:

<CodeBlock
  adapter="react"
  files={[
    {
      filename: "main.tsx",
      starterCode: `import { useState, useEffect } from "react";
import { createRoot } from "react-dom/client";

// Stand-in for a network request; resolves after a tick.
function loadPosts(): Promise<string[]> {
  return new Promise((resolve) =>
    setTimeout(() => resolve(["Hello world", "React is fun", "Effects!"]), 300),
  );
}

function Feed() {
  const [posts, setPosts] = useState<string[] | null>(null);

  useEffect(() => {
    loadPosts().then(setPosts);
  }, []);

  if (posts === null)
    return <p style={{ fontFamily: "system-ui" }}>Loading…</p>;

  return (
    <ul style={{ fontFamily: "system-ui", margin: 24 }}>
      {posts.map((p, i) => (
        <li key={i}>{p}</li>
      ))}
    </ul>
  );
}

createRoot(document.getElementById("root")!).render(<Feed />);
`,
    },
  ]}
/>

Run it: "Loading…" shows first, then the effect resolves and the list
appears. That "null means loading, array means loaded" pattern covers
most data-fetching UIs.

The live version below makes the loading state visible: click "Another
fact" and watch it flip to "Loading…" and back as the effect refetches.
Changing `index` is what re-runs the effect (it's in the dependency
array):

<ReactPreview
  code={`function RandomFact() {
  const [index, setIndex] = useState(0);
  const [fact, setFact] = useState<string | null>(null);

  useEffect(() => {
    let active = true;
    setFact(null);                       // show "Loading…" while we fetch
    fetchFact(index).then((f) => { if (active) setFact(f); });
    return () => { active = false; };    // ignore a stale response
  }, [index]);                            // re-run whenever index changes

  return (
    <div>
      <p>{fact === null ? "Loading…" : "💡 " + fact}</p>
      <button onClick={() => setIndex((i) => i + 1)} disabled={fact === null}>
        Another fact
      </button>
    </div>
  );
}`}
>
  <DataFetchDemo />
</ReactPreview>
