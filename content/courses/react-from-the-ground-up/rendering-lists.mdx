Most UIs are lists: rows of products, messages, search results. In
React you render a list by **mapping an array to elements**, ordinary
JavaScript `array.map`, right inside your JSX.

## `map` turns data into UI

<CodeBlock
  adapter="react"
  files={[
    {
      filename: "main.tsx",
      starterCode: `import { createRoot } from "react-dom/client";

const LANGUAGES = ["HTML", "CSS", "JavaScript", "TypeScript"];

function App() {
  return (
    <main style={{ fontFamily: "system-ui", margin: 24 }}>
      <h1>Languages I know</h1>
      <ul>
        {LANGUAGES.map((lang) => (
          <li key={lang}>{lang}</li>
        ))}
      </ul>
    </main>
  );
}

createRoot(document.getElementById("root")!).render(<App />);
`,
    },
  ]}
/>

The `{...}` holds an array of `<li>` elements, and React renders each
one. Change the array and the list changes, you never touch the DOM.

<Figure
  slug="rx-rendering-lists-inline-cutout"
  alt="A tray of three data blocks on the left, each one stamped into an identical card by a small press, the finished cards standing in a row on the right"
/>

Here an array of objects becomes a list of rows, live. Each row is one
`.map` iteration returning JSX:

## Why `key` matters

Each element in a mapped list needs a **`key`**, a stable, unique
identifier. React uses keys to tell items apart between renders, so
when the list changes it can update, insert, or remove just the items
that actually changed instead of rebuilding everything.

<Callout type="warn" title="Don't use the array index as a key (usually)">
It's tempting to write `key={index}`. That works only if the list
never reorders, inserts, or removes items from the middle. As soon as
it does, index keys make React associate the wrong DOM with the wrong
data, causing subtle bugs in inputs and animations. Prefer a stable id
from your data.
</Callout>

The cost is easiest to see on an insert at the front, where stable ids let
every existing element match itself and index keys renumber all of them:

## Mapping objects and rendering nothing

Real data is usually objects, and sometimes the list is empty. Handle
both:

<CodeBlock
  adapter="react"
  files={[
    {
      filename: "main.tsx",
      starterCode: `import { createRoot } from "react-dom/client";

interface Task {
  id: number;
  title: string;
  done: boolean;
}

const TASKS: Task[] = [
  { id: 1, title: "Learn map()", done: true },
  { id: 2, title: "Add keys", done: true },
  { id: 3, title: "Ship the list", done: false },
];

function TaskList({ tasks }: { tasks: Task[] }) {
  if (tasks.length === 0) {
    return <p>No tasks yet, nice work.</p>;
  }
  return (
    <ul style={{ fontFamily: "system-ui" }}>
      {tasks.map((task) => (
        <li key={task.id}>
          {task.done ? "✅" : "⬜"} {task.title}
        </li>
      ))}
    </ul>
  );
}

createRoot(document.getElementById("root")!).render(<TaskList tasks={TASKS} />);
`,
    },
  ]}
/>

That early `return` for the empty case is a common React idiom: guard
the edge case first, then render the normal path.

Lists get interesting when the array is *derived* from state. Type in
the box below: the visible list is `fruits.filter(...)` recomputed on
every render, and when nothing matches, the empty-state guard kicks in:

<ReactPreview
  code={`function FilterList() {
  const [query, setQuery] = useState("");
  const fruits = ["Apricot", "Blackberry", "Blueberry", "Cherry", "Fig", "Mango"];
  const shown = fruits.filter((f) =>
    f.toLowerCase().includes(query.toLowerCase()),
  );

  return (
    <div>
      <input
        value={query}
        onChange={(e) => setQuery(e.target.value)}
        placeholder="Filter fruit…"
      />
      {shown.length === 0 ? (
        <p>No matches.</p>
      ) : (
        <ul>{shown.map((f) => <li key={f}>{f}</li>)}</ul>
      )}
    </div>
  );
}`}
>
  <FilterListDemo />
</ReactPreview>
