## Three places it bites

1. **Cost.** Every token in and out is billed. This is the obvious one
   and the one people plan for.
2. **The context limit.** A request that exceeds the window fails, or
   silently loses its earliest content depending on the system around
   it.
3. **Latency.** Output tokens are produced one at a time, so response
   time is roughly proportional to output length. Input is processed
   in parallel and contributes far less.

<Figure
  slug="llm-token-counts-in-practice-inline-cutout"
  alt="A set of scales with a paper ribbon coiled on one pan and a stack of small chips balancing it on the other"
/>

That third point has a practical consequence people miss: **asking for
a shorter answer makes it arrive faster**, while shortening the prompt
mostly saves money rather than time.

## Measuring compression across text types

<CodeBlock
  adapter="python"
  files={[
    {
      filename: "main.py",
      starterCode: `# Characters-per-token varies a lot by content type. These
# multipliers are approximations of measured behavior.
RATIOS = {
    "english prose": 4.0,
    "python code":   3.0,
    "json data":     2.5,
    "base64 blob":   1.5,
    "non-latin script": 1.5,
}

sample = "The model reads the text. " * 40
n_chars = len(sample)

print(f"{n_chars} characters, encoded as:")
print()
for kind, ratio in RATIOS.items():
    tokens = round(n_chars / ratio)
    print(f"  {kind:<20} ~{tokens:5d} tokens  ({ratio} chars/token)")

print()
print("Same information, up to 2.7x the cost, depending on encoding.")
`,
    },
  ]}
/>

The JSON row is worth dwelling on. Wrapping data in JSON roughly
doubles its token cost compared with a compact tabular format, because
every key is repeated on every record and every brace and quote is a
token. If you are sending many records to a model, CSV is markedly
cheaper than JSON for identical content.

<CodeBlock
  adapter="python"
  files={[
    {
      filename: "main.py",
      starterCode: `import json

records = [
    {"customer_id": 1001, "region": "north", "amount": 249.99},
    {"customer_id": 1002, "region": "south", "amount": 89.50},
    {"customer_id": 1003, "region": "north", "amount": 512.00},
]

as_json = json.dumps(records, indent=2)
as_csv = "customer_id,region,amount\\n" + "\\n".join(
    f"{r['customer_id']},{r['region']},{r['amount']}" for r in records
)

print("JSON:", len(as_json), "chars ~", round(len(as_json) / 2.5), "tokens")
print("CSV: ", len(as_csv), "chars ~", round(len(as_csv) / 3.5), "tokens")
print()
print("--- CSV ---")
print(as_csv)
print()
print("Ratio:", round((len(as_json) / 2.5) / (len(as_csv) / 3.5), 1), "x")
`,
    },
  ]}
/>

Scale that to ten thousand records and the format choice is a real
budget line.

## Estimating a conversation

Remember from the previous course: **the entire history is resent on
every turn.** So the total tokens billed across a conversation is not
the length of the conversation, it is the sum of every prefix.

<CodeBlock
  adapter="python"
  files={[
    {
      filename: "main.py",
      starterCode: `# Total input tokens billed across a multi-turn conversation.
system_prompt = 2000       # a schema, pasted once
per_user_turn = 100
per_reply     = 400

total_input = 0
history = system_prompt

for turn in range(1, 11):
    history += per_user_turn          # your message joins the history
    total_input += history            # the WHOLE history is sent
    history += per_reply              # the reply joins it too
    if turn in (1, 5, 10):
        print(f"turn {turn:2d}: context={history:6d}  cumulative input={total_input:7d}")

print()
print(f"Conversation is {history} tokens long.")
print(f"You were billed for {total_input} input tokens, "
      f"{round(total_input / history, 1)}x that.")
`,
    },
  ]}
/>

Ten turns, and you paid for roughly five times the conversation's
length. Twenty turns and the multiplier keeps climbing. This quadratic
growth is why prompt caching exists, and why starting a fresh
conversation is a cost decision as well as an accuracy one.
