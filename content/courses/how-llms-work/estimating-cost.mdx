Cost surprises come almost entirely from two places: the conversation
resend, and forgetting that thinking tokens are output tokens. Both are
easy to model.

## A single request

<CodeBlock
  adapter="python"
  files={[
    {
      filename: "main.py",
      initCode: `PRICES = {
    "opus":   {"in": 5.00, "out": 25.00, "cached": 0.50},
    "sonnet": {"in": 3.00, "out": 15.00, "cached": 0.30},
    "haiku":  {"in": 1.00, "out":  5.00, "cached": 0.10},
    "lite":   {"in": 0.25, "out":  1.50, "cached": 0.025},
}

def cost(model, input_tokens=0, output_tokens=0, cached_tokens=0):
    """USD for one request. Cached tokens are billed instead of, not
    in addition to, the same tokens at the input rate."""
    p = PRICES[model]
    return (input_tokens / 1e6 * p["in"]
            + output_tokens / 1e6 * p["out"]
            + cached_tokens / 1e6 * p["cached"])`,
      starterCode: `# 'cost' and 'PRICES' come from the initialization code above.

# One support-bot request: 1,200-token prompt, 300-token answer.
for model in PRICES:
    c = cost(model, input_tokens=1200, output_tokens=300)
    print(f"{model:>7}: \${c:.6f} per request  "
          f"= \${c * 100_000:,.2f} per 100k requests")

print()
print("Same task, same tokens, 20x cost spread across tiers.")
`,
    },
  ]}
/>

Note the second column. Per-request costs look negligible until you
multiply by production volume, at which point the tier choice becomes a
budget decision rather than a technical one.

## A conversation, with the resend

This is where estimates go wrong. Every turn resends everything.

<Figure
  slug="llm-estimating-cost-conversation-resend-inline-cutout"
  alt="A growing stack of ribbons where each new exchange re-feeds every earlier ribbon through the machine again"
  caption="Every turn resends the whole conversation, so cost grows with its length."
/>

<Chart slug="token-cost-stack" />

<CodeBlock
  adapter="python"
  files={[
    {
      filename: "main.py",
      initCode: `PRICES = {
    "opus":   {"in": 5.00, "out": 25.00, "cached": 0.50},
    "sonnet": {"in": 3.00, "out": 15.00, "cached": 0.30},
    "haiku":  {"in": 1.00, "out":  5.00, "cached": 0.10},
    "lite":   {"in": 0.25, "out":  1.50, "cached": 0.025},
}

def conversation_cost(model, turns, system=2000, user=150, reply=400, cached=False):
    p = PRICES[model]
    total, history = 0.0, system
    for _ in range(turns):
        history += user
        if cached:
            # The stable system prefix is cached; the rest is fresh.
            total += (system / 1e6 * p["cached"]
                      + (history - system) / 1e6 * p["in"])
        else:
            total += history / 1e6 * p["in"]
        total += reply / 1e6 * p["out"]
        history += reply
    return total`,
      starterCode: `# 'conversation_cost' is defined above.
print(f"{'turns':>6} {'no cache':>10} {'cached':>10} {'saved':>8}")
for turns in [1, 5, 10, 20, 40]:
    plain = conversation_cost("sonnet", turns)
    cached = conversation_cost("sonnet", turns, cached=True)
    print(f"{turns:>6} \${plain:>9.4f} \${cached:>9.4f} {1 - cached/plain:>7.0%}")

print()
print("Cost grows faster than turn count, because each turn")
print("resends everything before it.")
`,
    },
  ]}
/>

Doubling the turns more than doubles the cost. That is the quadratic
term, and it is why a 40-turn conversation can cost more than eight
separate 5-turn ones covering the same ground.

## Thinking tokens

Reasoning output is billed as output, at the output rate, and it is
usually several times longer than the visible answer.

<CodeBlock
  adapter="python"
  files={[
    {
      filename: "main.py",
      initCode: `PRICES = {"opus": {"in": 5.00, "out": 25.00}, "sonnet": {"in": 3.00, "out": 15.00}}

def request_cost(model, in_tok, visible_out, thinking_out=0):
    p = PRICES[model]
    return in_tok / 1e6 * p["in"] + (visible_out + thinking_out) / 1e6 * p["out"]`,
      starterCode: `IN, VISIBLE = 2000, 400

print(f"{'thinking':>9} {'cost':>10} {'vs none':>9}")
base = request_cost("sonnet", IN, VISIBLE, 0)
for thinking in [0, 500, 2000, 8000, 20000]:
    c = request_cost("sonnet", IN, VISIBLE, thinking)
    print(f"{thinking:>9} \${c:>9.5f} {c / base:>8.1f}x")

print()
print("The visible answer never changed length.")
print("Reasoning effort is the whole difference.")
`,
    },
  ]}
/>

## Putting it together: a monthly estimate

<CodeBlock
  adapter="python"
  files={[
    {
      filename: "main.py",
      initCode: `PRICES = {
    "opus":   {"in": 5.00, "out": 25.00, "cached": 0.50},
    "sonnet": {"in": 3.00, "out": 15.00, "cached": 0.30},
    "haiku":  {"in": 1.00, "out":  5.00, "cached": 0.10},
    "lite":   {"in": 0.25, "out":  1.50, "cached": 0.025},
}

def monthly(workloads):
    total = 0.0
    rows = []
    for name, w in workloads.items():
        p = PRICES[w["model"]]
        per = (w["in"] / 1e6 * p["in"] + w["out"] / 1e6 * p["out"])
        month = per * w["per_day"] * 30
        rows.append((name, w["model"], per, month))
        total += month
    return rows, total`,
      starterCode: `workloads = {
    "ticket classification": {"model": "lite",   "in": 800,   "out": 20,   "per_day": 40_000},
    "support replies":       {"model": "haiku",  "in": 2_000, "out": 350,  "per_day": 6_000},
    "document summaries":    {"model": "sonnet", "in": 12_000,"out": 800,  "per_day": 900},
    "code review":           {"model": "opus",   "in": 20_000,"out": 2_000,"per_day": 200},
}

rows, total = monthly(workloads)
print(f"{'workload':<24}{'model':<9}{'per req':>10}{'per month':>13}")
for name, model, per, month in rows:
    print(f"{name:<24}{model:<9}\${per:>9.5f}\${month:>12,.2f}")
print(f"{'-' * 56}")
print(f"{'TOTAL':<33}\${total:>12,.2f} / month")

print()
print("Try moving 'document summaries' to haiku, or 'code review' to sonnet,")
print("and watch which line actually moves the total.")
`,
    },
  ]}
/>

Run it, then change one model assignment. The exercise teaches
something no price list does: which workload dominates your bill is
usually not the one you would guess, because volume and token count
multiply.
