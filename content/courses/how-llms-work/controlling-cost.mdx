Now that you can measure cost, here is what to do about it. The levers
are ordered by typical impact, which is not the order people usually
try them in.

## 1. Route to the cheapest model that passes

The spread between tiers is roughly 25x. No amount of prompt trimming
competes with that.

The mistake is choosing one model for everything, usually the best one,
because it is the one that passed the hardest test case. Most
production traffic is not the hardest test case.

**Route by task.** Classification, extraction, formatting, and
routing itself go to a small model. Reserve the expensive tier for
work that genuinely needs it, and measure which is which rather than
guessing.

<CodeBlock
  adapter="python"
  files={[
    {
      filename: "main.py",
      starterCode: `PRICE = {"lite": (0.25, 1.50), "haiku": (1.00, 5.00),
         "sonnet": (3.00, 15.00), "opus": (5.00, 25.00)}

def month(model, in_tok, out_tok, per_day):
    pin, pout = PRICE[model]
    return (in_tok / 1e6 * pin + out_tok / 1e6 * pout) * per_day * 30

# 50,000 classifications a day, 600 tokens in, 15 out.
print("Same classification workload on each tier:")
for m in PRICE:
    print(f"  {m:>7}: \${month(m, 600, 15, 50_000):>9,.2f} / month")

everything_on_opus = month("opus", 600, 15, 50_000)
routed = month("lite", 600, 15, 50_000)
print()
print(f"Saving from routing this one workload: \${everything_on_opus - routed:,.2f}/month")
`,
    },
  ]}
/>

Serving a smaller version of the *same* model is the other half of that
lever. Quantization trades bits per weight for memory, and the quality
cost is not linear in the saving.

## 2. Cache the stable prefix

If a long system prompt, schema, or document repeats across requests,
caching cuts it to about a tenth.

<Figure
  slug="llm-controlling-cost-2-cache-stable-inline-cutout"
  alt="A long ribbon whose first stretch is clamped under a cover and reused, only its tail being fed through the machine"
  caption="A stable prefix can be cached, so only the changing tail is paid for in full."
/>

The requirement is that the prefix be **byte-identical**. That means:

* Put stable content first, volatile content last.
* No timestamps, request ids, or user names near the top.
* Serialize any structured content deterministically. An unsorted
  dictionary is a different prefix every time.

<CodeBlock
  adapter="python"
  files={[
    {
      filename: "main.py",
      starterCode: `import json

config = {"role": "analyst", "dataset": "orders", "version": 3}

# Unsorted serialization: key order can vary between runs and
# between processes, which silently breaks the cache.
unstable = json.dumps(config)

# Deterministic: same bytes every time.
stable = json.dumps(config, sort_keys=True)

print("unstable:", unstable)
print("stable:  ", stable)
print()
print("Same content, and only one of them reliably produces")
print("an identical prefix on every request.")
print()

bad_prompt = f"Session started 2026-08-03T14:22:01Z\\n\\n{'SCHEMA ' * 10}"
good_prompt = f"{'SCHEMA ' * 10}\\n\\nSession started 2026-08-03T14:22:01Z"
print("Timestamp first  -> nothing after it can be cached")
print("Timestamp last   -> everything before it can be cached")
`,
    },
  ]}
/>

## 3. Cut output, not input

Output costs 5 to 6 times more per token, so a token saved on the
output side is worth five or six saved on the input side.

* Ask for the answer only, not the explanation, when you do not need
  the explanation.
* Use structured output so the model returns fields rather than prose
  wrapping fields.
* Cap `max_tokens` at what you actually need. This also bounds the
  worst case when something goes wrong.

## 4. Lower the reasoning effort

Thinking tokens are output tokens. If your task does not have
verifiable intermediate structure, reasoning effort is pure cost. Set
it to the lowest level that passes your evaluation.

## 5. Batch anything not interactive

Roughly 50% off for accepting asynchronous processing. Nightly
classification, backfills, bulk enrichment, and evaluation runs are all
natural fits. Interactive traffic is not.

## 6. Then optimize the prompt

Worth doing, and last on the list because it usually saves the least.
An exception: if you are pasting a large document on every turn when
three paragraphs would do, that is a retrieval problem rather than a
prompt-length problem, and it belongs at the top of this list.

<Callout type="info" title="Measure before optimizing">
Instrument token counts per workload before changing anything. The
monthly-estimate exercise in the previous chapter usually surprises
people: the line dominating the bill is rarely the one that felt
expensive.
</Callout>

<MultipleChoice
  markdown={`Why must a cached prefix be byte-identical?

- Because tokenization is non-deterministic for varying text.
  > Tokenization is deterministic.
- Because the cache stores a hash of the full request.
  > It matches on the prefix rather than the whole request.
- [o] Because matching is on the exact prefix, so any change invalidates it.
  > A single differing character means the stored processed state cannot be reused from that point onward.
- Because providers charge per unique cache entry.
  > Entries are not billed individually.

Exact matching is what makes deterministic serialization a cost issue.`}

<MultipleChoice
  markdown={`Why is a token saved on output worth more than one saved on input?

- Input tokens are often cached and therefore already discounted.
  > Caching applies only to repeated prefixes and does not explain the general rule.
- Output tokens are counted twice by most providers.
  > They are counted once.
- [o] Output is priced at 5 to 6 times the input rate.
  > The ratio means one output token saved equals five or six input tokens saved.
- Output tokens are larger on average.
  > Token size does not differ by side.

The pricing ratio directly sets the relative value of each saving.`}

<MultipleChoice

<MultipleChoice
  markdown={`You paste an entire 200-page manual on every request when three paragraphs would do. What kind of problem is this?

- A prompt-length problem, solved by more concise instructions.
  > The instructions are not the bulk.
