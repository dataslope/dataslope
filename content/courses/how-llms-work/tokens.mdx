A model cannot process text. It processes numbers. **Tokenization** is
the step that turns one into the other, and it is responsible for more
surprising behavior than any other single component.

## What a token is

A token is a chunk of text that the vocabulary assigns a single id to.
Not a character, not a word, something in between:

* Common words are usually one token: `the`, `data`, `model`.
* Uncommon words split: `tokenization` might be `token` + `ization`.
* Rare words shatter: a surname might become four or five pieces.
* **Leading spaces belong to the token.** `" the"` and `"the"` are
  different tokens with different ids.
* Numbers split unpredictably. `2026` might be one token or two.

      starterCode: `# A hand-built vocabulary, to show how ids and text relate.
# Real vocabularies are learned from data (next chapter).
vocab = {
    "the": 464, " the": 262, " model": 2746, " reads": 9743,
    " token": 11241, "ization": 1634, ".": 13,
}

text_pieces = [" the", " model", " reads", " token", "ization", "."]
ids = [vocab[p] for p in text_pieces]

print("Text: ", "".join(text_pieces))
print("Pieces:", text_pieces)
print("Ids:   ", ids)
print()
print("Characters:", len("".join(text_pieces)))
print("Tokens:    ", len(ids))
`,
    },
  ]}
/>

Note the two entries for `the`. The leading space is part of the
token, which is why prompts sometimes behave differently depending on
whether they end with a space.

## What this explains

### Counting letters

Ask a model how many `r`s are in "strawberry" and it may get it wrong.
Not because it cannot count to three, but because it never received
the letters. It received two opaque ids. Answering requires it to
recall facts *about* the spelling, which is a different and less
reliable operation than looking.

  slug="llm-tokens-token-inline-cutout"

  caption="A token may be a whole word or a fragment, and the model only sees the ids."
/>

### Arithmetic being uneven

`2 + 2` is reliable. Multiplying two six-digit numbers is not. Digit
grouping in the tokenizer means the model does not see clean columns
of digits, so column-wise arithmetic has to be reconstructed from
patterns rather than performed.

### Non-English text costing more

Tokenizers are trained on corpora that are mostly English, so English
compresses well. Other languages, particularly those not using Latin
script, fragment into many more tokens for the same meaning. The same
sentence in Japanese or Thai can take two to three times as many
tokens as in English, and you pay per token.

### Reversal and anagrams being hard

Reversing a string requires character access. The model has chunks.

<Callout type="info" title="A useful mental image">
Imagine reading a language written entirely in words you recognize by
overall shape, never by letter. You could read fluently, discuss the
content, and write convincingly. You could not reliably say how many
times the letter "e" appears on the page. That is roughly the model's
relationship to text.
</Callout>

## The rough conversion rate

For English prose, one token is about four characters or about 0.75
words. So:

* 1,000 tokens is roughly 750 words, or about 1.5 pages.
* 100,000 tokens is roughly a 300-page book.
* 1,000,000 tokens is a small library.

Code is denser in tokens than prose, because whitespace, punctuation,
and identifiers fragment. Estimate code at about three characters per
token.

<CodeBlock
  adapter="python"
  files={[
    {
      filename: "main.py",
      starterCode: `# Rough token estimation, useful for capacity and cost planning.
def estimate_tokens(text, kind="prose"):
    chars_per_token = 4.0 if kind == "prose" else 3.0
    return round(len(text) / chars_per_token)

prose = "The quick brown fox jumps over the lazy dog. " * 20
code = "def f(x):\\n    return [i ** 2 for i in range(x) if i % 3 == 0]\\n" * 20

print(f"prose: {len(prose):5d} chars -> ~{estimate_tokens(prose):4d} tokens")
print(f"code:  {len(code):5d} chars -> ~{estimate_tokens(code, 'code'):4d} tokens")
print()

# Try your own text:
mine = "Paste something here and see roughly how many tokens it is."
print(f"yours: {len(mine):5d} chars -> ~{estimate_tokens(mine):4d} tokens")
`,
    },
  ]}
/>

These estimates are approximations. For anything where the number
matters (a budget, a context-limit check) use the provider's own token
counting endpoint, which is exact and usually free.

The rate is not the same for every language, and the reason starts one
level below tokens: the same sentence costs a different number of *bytes*
depending on the script it is written in.
