A *join* asks: given two tables and a shared key, what should
happen to rows that don't match? Pandas's `merge` answers this
with the `how` parameter.

<Figure
  slug="pandas-merging-and-joining-cutout"
  alt="Merging and joining, an isometric illustration"
/>

## The four join types

| `how=` | What you get |
| --- | --- |
| `inner` | Only rows whose key appears in **both** tables |
| `left` | All rows from the **left** table; right columns are `NaN` where no match exists |
| `right` | All rows from the **right** table; left columns are `NaN` where no match exists |
| `outer` | Every row from **either** table; `NaN` wherever the other side has no match |

## Setting the stage

<CodeBlock
  adapter="python"
  files={[
    {
      filename: "main.py",
      starterCode: `import pandas as pd

employees = pd.DataFrame(
    {
        "emp_id": [1, 2, 3, 4, 5],
        "name": ["Aiko", "Bilal", "Chen", "Diego", "Esra"],
        "dept_id": [10, 20, 10, 30, 99],  # 99 has no matching department
    }
)

departments = pd.DataFrame(
    {
        "dept_id": [10, 20, 30, 40],  # 40 has no employees
        "dept_name": ["Engineering", "Sales", "Marketing", "HR"],
    }
)

print(employees)
print()
print(departments)
`,
    },
  ]}
/>

## Inner join

Only rows where the key is present in both. This is the
default.

<CodeBlock
  adapter="python"
  files={[
    {
      filename: "main.py",
      starterCode: `inner = employees.merge(departments, on="dept_id", how="inner")
print(inner)
`,
    },
  ]}
/>

Esra (dept 99) and HR (dept 40) both vanish. **Inner = strict
intersection.**

## Left join

Keep all rows from the left side; fill missing right-side
columns with NaN.

<CodeBlock
  adapter="python"
  files={[
    {
      filename: "main.py",
      starterCode: `left = employees.merge(departments, on="dept_id", how="left")
print(left)
`,
    },
  ]}
/>

Esra is preserved with `dept_name = NaN`. Left joins are by far
the most common in everyday analytics, "I have my entities,
enrich them with extra info if available."

## Right join

The mirror image. Rarely used in practice, most analysts
prefer to swap the arguments and use a left join, which reads
more naturally.

<CodeBlock
  adapter="python"
  files={[
    {
      filename: "main.py",
      starterCode: `right = employees.merge(departments, on="dept_id", how="right")
print(right)
`,
    },
  ]}
/>

HR appears with NaN employee columns.

## Outer join

Keep everything from both sides.

<CodeBlock
  adapter="python"
  files={[
    {
      filename: "main.py",
      starterCode: `outer = employees.merge(departments, on="dept_id", how="outer")
print(outer)
`,
    },
  ]}
/>

Both Esra (no department) and HR (no employees) are present.
Great for spotting *what doesn't match*.

## The indicator trick, diagnose join coverage

<CodeBlock
  adapter="python"
  files={[
    {
      filename: "main.py",
      starterCode: `check = employees.merge(departments, on="dept_id", how="outer", indicator=True)
print(check)
print()
print(check["_merge"].value_counts())
`,
    },
  ]}
/>

`indicator=True` adds a `_merge` column showing where each row
came from (`left_only`, `right_only`, `both`). This is one of
the most valuable debugging tools in Pandas, always reach for
it when a join produces surprising row counts.

## Different column names

When the join key is named differently in each table:

<CodeBlock
  adapter="python"
  files={[
    {
      filename: "main.py",
      starterCode: `import pandas as pd

orders = pd.DataFrame(
    {"order_id": [1, 2, 3], "cust": [10, 11, 12], "amount": [50, 80, 30]}
)
customers = pd.DataFrame(
    {"customer_id": [10, 11, 12], "name": ["Aiko", "Bilal", "Chen"]}
)

joined = orders.merge(customers, left_on="cust", right_on="customer_id")
print(joined)
`,
    },
  ]}
/>

## Many-to-many, the row-count surprise

If the key is **not unique on one side**, the join multiplies
rows. If it's not unique on **both** sides, you get the Cartesian
product per key value, often a disaster.

<CodeBlock
  adapter="python"
  files={[
    {
      filename: "main.py",
      starterCode: `import pandas as pd

a = pd.DataFrame({"k": [1, 1, 2], "x": ["a1", "a2", "a3"]})
b = pd.DataFrame({"k": [1, 1, 3], "y": ["b1", "b2", "b3"]})

# Each key=1 row in a matches both key=1 rows in b → 2 × 2 = 4 rows
print(a.merge(b, on="k", how="inner"))
`,
    },
  ]}
/>

Pandas can warn you about unexpected cardinalities:

<CodeBlock
  adapter="python"
  files={[
    {
      filename: "main.py",
      starterCode: `import pandas as pd

a = pd.DataFrame({"k": [1, 2, 3], "x": ["a", "b", "c"]})
b = pd.DataFrame({"k": [1, 2, 3], "y": ["X", "Y", "Z"]})

# Assert that the join is one-to-one
result = a.merge(b, on="k", validate="one_to_one")
print(result)
`,
    },
  ]}
/>

`validate=` accepts `"one_to_one"`, `"one_to_many"`,
`"many_to_one"`, or `"many_to_many"` and raises if the actual
data doesn't match.

## Suffixes when column names collide

<CodeBlock
  adapter="python"
  files={[
    {
      filename: "main.py",
      starterCode: `import pandas as pd

a = pd.DataFrame({"id": [1, 2], "value": [10, 20]})
b = pd.DataFrame({"id": [1, 2], "value": [100, 200]})

print(a.merge(b, on="id"))  # default suffixes _x / _y
print()
print(a.merge(b, on="id", suffixes=("_yr1", "_yr2")))
`,
    },
  ]}
/>

Always give meaningful suffixes, `_x` and `_y` are a recipe for
confusion six months later.

## A bigger walkthrough

<CodeBlock
  adapter="python"
  files={[
    {
      filename: "main.py",
      initCode: `import pandas as pd

orders = pd.DataFrame({
    "order_id":   [101,102,103,104,105],
    "customer":   [1,1,2,3,99],
    "amount":     [50, 30, 80, 25, 60],
})

customers = pd.DataFrame({
    "customer":   [1,2,3,4],
    "name":       ["Aiko","Bilal","Chen","Diego"],
    "country":    ["JP","PK","CN","MX"],
})`,
      starterCode: `# How many orders have no matching customer record?
check = orders.merge(customers, on="customer", how="left", indicator=True)
print(check)
print()
print("Orders missing a customer:", (check["_merge"] == "left_only").sum())
print()
print("Customers with no orders:")
all_check = orders.merge(customers, on="customer", how="outer", indicator=True)
print(all_check[all_check["_merge"] == "right_only"])
`,
    },
  ]}
/>

This is the everyday detective work of joining real datasets:
first check coverage, then narrow down what's missing and why.

## Check your understanding

<MultipleChoice
  markdown={`Your join produces 3× more rows than the left table. The most likely cause is:

- A network issue
  > Network issues affect data loading, not the row-matching logic of an in-memory merge.
- A bug in pandas
  > Row-count multiplication from duplicate keys is correct, documented merge behavior, not a Pandas defect.
- The dtypes are different
  > Mismatched dtypes on the key column prevent rows from matching and would produce *fewer* rows (or no matches), not 3× more.
- [o] The join key is duplicated in the right-hand table, each left row matches multiple right rows
  > Always check key uniqueness with \`.duplicated()\` or \`validate="one_to_many"\` before joining.

Cardinality blow-ups are by far the most common merge bug.`}
/>

<MultipleChoice
  markdown={`Which join is best for "every employee row, with department info attached if available, but I don't want to lose any employees"?

- inner
  > An inner join drops employees who have no matching department, violating the requirement to keep every employee row.
- outer
  > An outer join keeps every row from both tables, including departments that have no employees, more rows than needed.
- right
  > A right join keeps all department rows and only the employees that match, losing employees with no department record.
- [o] left (employees on the left)
  > Left join keeps all employees and adds dept info where it matches.

Left joins are the workhorse of enrichment workflows.`}
/>

<MultipleChoice
  markdown={`The most useful diagnostic flag for understanding a merge is:

- copy=False
  > \`copy=False\` is a memory-efficiency hint that has no effect on the diagnostic information returned by the merge.
- on="*"
  > \`on="*"\` is not valid Pandas syntax; the \`on\` parameter requires an explicit column name or list of column names.
- sort=True
  > \`sort=True\` reorders rows by the join key, which helps with display but does not reveal coverage issues.
- [o] indicator=True, adds a \`_merge\` column showing which rows are left-only, right-only, or matched in both
  > Always reach for this when row counts surprise you.

\`indicator=True\` should be in every data analyst's debugging toolbox.`}
/>

<MultipleChoice
  markdown={`What's the safest way to **guarantee** your merge is one-to-one before producing results?

- Use a SQL database instead
  > SQL can also validate cardinality, but switching tools is not necessary; \`pd.merge(..., validate=)\` provides the same protection inline.
- [o] Pass \`validate="one_to_one"\` to \`merge\`, Pandas raises an error if the data violates that assumption
  > Encoding your assumptions in the code catches problems immediately, instead of letting silent bugs propagate.
- Manually count rows after the merge
  > Comparing row counts after the merge can detect a problem but does not prevent it or tell you which key caused it; \`validate=\` raises immediately with details.
- Hope for the best
  > Relying on luck is not a safeguard; silent cardinality bugs are exactly what the \`validate=\` parameter was designed to catch.

The \`validate=\` parameter turns implicit assumptions into explicit, testable contracts.`}
