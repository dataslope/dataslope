Most people meet SQL inside an **application**: a website saves a user's
order, then reads it back on the "My Orders" page. That is real, useful
SQL, but it is a *different job* from what an analyst does, even though
both use the word `SELECT`. This page makes the difference precise,
because almost every habit you build in this course flows from it: the
shape of analytical questions, and the kind of engine that answers them
fast.

## Two jobs, one language

Think of a busy online store.

- The **application** asks tiny, sharply targeted questions, millions of
  times a day: *"What is in cart #84213?"*, *"Save this new order."*,
  *"Mark order #91 as shipped."* Each touches a handful of rows and must
  return in milliseconds.
- The **analyst** asks broad, exploratory questions, a few times a day:
  *"Which product categories grew fastest last quarter?"*, *"Do
  first-time buyers spend less than returning ones?"* Each sweeps across
  *millions* of rows to produce a *small* summary.

Same keywords, opposite shape. An application query is a **needle**: find
this one row, fast. An analytical query is a **net**: drag it across the
whole ocean and weigh the catch. These two patterns have formal names,
**OLTP** (*Online Transaction Processing*, the needle) and **OLAP**
(*Online Analytical Processing*, the net). You will not be quizzed on the
acronyms, but what each workload *demands* explains everything that
follows.

A one-line way to remember it: **OLTP records what happened; OLAP explains
what it means.** Every order an OLTP system saves becomes a row that, much
later, an OLAP query sweeps up to find a trend.

| Dimension | OLTP (transactional) | OLAP (analytical) |
| --- | --- | --- |
| Typical operation | Insert / update / point read | Large aggregating read |
| Rows touched per query | A few | Thousands to billions |
| Columns touched | Most of the row | A few of many |
| Acceptable latency | Milliseconds | Seconds |
| Concurrency | Many users at once | Few analysts at once |
| Goal | Run the business | Understand the business |

This course lives entirely on the OLAP side of that table.

## What the analyst is really doing

When you write SQL for analysis you are not maintaining the data, you are
**interrogating** it. A typical analytical query **reads** data but rarely
changes it; it **touches many rows to produce few** (a thousand orders
become one average); and it **cares about columns, not rows** ("average
`amount`" reads one column across every row). It is also *exploratory*,
you rarely know the final query in advance, so you run one, look, and let
the result suggest the next.

The query below is deeply analytical: it reads *every* diamond in a remote
53,940-row file but returns just **one summarizing line per cut**. No
single diamond is the answer; the *pattern across diamonds* is.

<SqlCodeBlock
  dialect="duckdb"
  title="A net, not a needle, 53,940 diamonds, five lines out"
  starterCode={`SELECT
  cut,
  COUNT(*) AS n,
  ROUND(AVG(carat), 2) AS avg_carat,
  ROUND(AVG(price), 0) AS avg_price
FROM
  read_parquet(
    'https://cdn.jsdelivr.net/gh/dataslope/datasets@f7f08485960fe4a774359a43d1eb50a84514daf2/diamonds.parquet'
  )
GROUP BY
  cut
ORDER BY
  avg_price DESC;`}
/>

Notice there is no "find diamond #5" here. We deliberately *forgot* about
individual stones to see the shape of the whole.

## Why the *physical* shape differs: rows vs. columns

Here is the idea that ties everything together, and the reason a tool
like DuckDB feels fast for analysis. A database can store a table two ways.

- **Row storage** keeps all of a row's values together. Perfect for OLTP:
  "give me everything about order #4821" reads one contiguous chunk.
- **Column storage** keeps all values of *one column* together. Perfect
  for OLAP: "average `price` over 53,940 diamonds" reads just the `price`
  column and skips everything else.

Row store (good for OLTP) keeps each row's values together on disk:

```text
[id1 cut1 price1 carat1] [id2 cut2 price2 carat2] [id3 cut3 price3 carat3]
```

Column store (good for OLAP) keeps each column together instead:

```text
[id1 id2 id3] [cut1 cut2 cut3] [price1 price2 price3] [carat1 carat2 carat3]
```

When the diamonds query needed only `cut`, `carat`, and `price`, a column
store reads *only* those stripes, never the columns it does not touch. On
a wide table that can mean reading a small fraction of the data instead of
all of it. That single design choice is most of why purpose-built
analytical engines crush row-oriented databases on summary queries.

Put a number on it and the argument stops being architectural taste. The
analyst's query touches a few columns of a wide table; the row store has
to read every one of them to get there.

## Vectorized execution: the second half of the speed

Storing data by column is only half the story. The other half is how the
engine *processes* it. A traditional database often walks one row at a
time, evaluating the whole query for each row, a lot of bookkeeping per
value. A modern analytical engine instead processes a **batch** of values
from a column at once, in a tight loop the CPU can run efficiently. This
is called **vectorized execution**, and column storage is what makes it
natural: the values are already lined up together, ready to stream through
in chunks.

Column storage plus vectorized execution is the lineage of decades of
column-store research, notably **MonetDB**, built at the CWI research
institute in Amsterdam, and the **C-Store** project associated with
Michael Stonebraker. DuckDB, which this course runs on, inherits exactly
this design, and it was created at the very same Amsterdam institute that
produced MonetDB. (More on DuckDB's origins on the next page.)

<Callout type="info" title="You write the same SQL either way">
Reassuringly, you do **not** change your SQL to get these benefits. You
write the same `SELECT ... GROUP BY` you already know; the engine's
columnar storage and vectorized execution do the rest. The lesson is not
"write different SQL for OLAP", it is that the *questions* you ask, and
the *engine* you ask them on, are tuned for analysis.
</Callout>

  > That is the opposite of the benefit; column stores let queries *avoid* unneeded columns.

  > Storage layout does not change the SQL you write; you still use \`GROUP BY\`.
- [o] A query that needs only a few columns can read just those columns and skip the rest of each row.

<MultipleChoice
  markdown={`What is **vectorized execution**, and why does it suit OLAP?

- [o] Processing a batch of column values at a time in a tight loop, instead of evaluating the whole query one row at a time.
  > Batching values cuts per-row overhead, and column storage lines the values up ready to stream, together they make scans fast.
- Converting SQL into spreadsheet formulas.
  > Vectorization is an engine technique for fast batch processing, unrelated to spreadsheets.
- Running each query on a separate CPU core.
  > That describes parallelism across cores; vectorization is about processing batches of values per operation, regardless of core count.

  > That is closer to row storage; vectorized execution is about *processing* batches, and pairs with column storage.
