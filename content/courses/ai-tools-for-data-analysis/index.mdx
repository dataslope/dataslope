## What this course is, and is not

This is **not** a course about which assistant is best. Model rankings
change every few months, and a course organized around them would be
wrong by the time you finished it.

It is a course about a skill that does not expire: **working with a
collaborator who is fast, fluent, tireless, widely read, and wrong
roughly one time in five without ever sounding like it.**

That last property is the whole problem. A junior analyst who is
unsure says so. A language model that is unsure produces the same
crisp, well-formatted, confident answer it produces when it is
certain. The 2026 benchmark picture is blunt about this: on zero-shot
text-to-SQL, even leading models land around 78% execution accuracy.
Roughly one query in five is wrong, and most of those wrong queries
run without raising a single error.

<Callout type="warn" title="The failure mode that matters">
The dangerous AI mistake is not the one that crashes. It is the one
that returns a number. A query that errors out costs you thirty
seconds. A query that silently drops a third of your rows and returns
a plausible average can cost you a decision.
</Callout>

## Try one right now

Here is the kind of judgment this course trains. You asked an
assistant for the average order value per customer. It gave you this:

<MultipleChoice
  markdown={`\`\`\`sql
SELECT c.name, AVG(o.amount) AS avg_order_value
FROM customers c
JOIN orders o ON c.id = o.customer_id
GROUP BY c.name;
\`\`\`

The query runs without error and returns sensible-looking numbers.
What is the most likely problem with it?

- \`AVG\` cannot be combined with \`GROUP BY\` in standard SQL.
  > \`AVG\` with \`GROUP BY\` is the normal way to compute a per-group average, so this is not the issue.
- Nothing, the query is correct as written.
  > It runs and returns numbers, but running is not the same as being right.
- The \`JOIN\` should be a \`LEFT JOIN\`, so the query is definitely wrong.
  > This changes the answer only if you want customers with zero orders included, which is a question about intent rather than a defect you can see from the code.
- [o] Grouping by \`name\` merges any two customers who share a name.
  > Two different people called "J. Smith" collapse into one row, and their orders are averaged together. Grouping should use \`c.id\`, the key that is actually unique.

Grouping on a display label rather than a key is one of the most
common defects in generated SQL, and one of the hardest to notice,
because the output looks completely normal.`}
/>

Nothing about that query looks wrong. It is well formatted, it uses a
sensible alias, it runs. Catching it takes a specific habit, and that
habit is what you are here to build.

## What you will learn

* **How the tools actually see your data.** Pasted text, uploaded
  files, sandboxed code execution, and connected databases are four
  very different situations with four different risk profiles.
* **How to ask well.** The single biggest lever on output quality is
  how you describe the data, not how you phrase the request.
* **The five failure modes.** Invented columns, broken joins,
  aggregation traps, silent null handling, and misplaced confidence.
* **Two review checklists**, one for generated Pandas and one for
  generated SQL, that you can run in under a minute.
* **Where AI genuinely wins**, which is a longer list than skeptics
  expect, and **where it is genuinely risky**, which is a longer list
  than enthusiasts expect.
* **The practical envelope**: context, cost, privacy, and the
  connected-tool setups that are becoming standard.

## Who this is for

You should be comfortable reading (not necessarily writing) basic
Pandas or SQL. If you can look at `df.groupby("region")["sales"].sum()`
and say roughly what it does, you have enough.

You do not need a paid subscription to any assistant. Every idea here
applies to the free tiers, and the exercises are all reasoning
exercises rather than tool walkthroughs.

<Callout type="info" title="How this course is exercised">
Every chapter ends in a set of multiple-choice questions, and many of
them show you a snippet of generated code and ask what is wrong with
it. That is deliberate. The skill this course teaches is *reading and
judging*, not typing, so the exercises drill reading and judging.
</Callout>

## A note on shelf life

Model names, prices, and feature lists in this course are marked with
the date they were accurate. Treat those specifics as illustrations of
a *shape* rather than as facts to memorize. The shape (output tokens
cost several times input tokens, cached input is roughly a tenth of
the price, benchmarks saturate and then get replaced) has been stable
for years and will outlive any particular model name.
