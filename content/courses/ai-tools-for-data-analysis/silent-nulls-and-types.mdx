The previous three failure modes are about structure. This one is
about the values themselves, and it is the hardest to catch by reading
code, because the defect is not in the code at all. The code is
correct. The data is shaped differently than the code assumes.

## Nulls disappear differently everywhere

The single most confusing thing about missing data is that every
operation treats it differently, and none of them announce it.

| Operation | Null behavior |
| --- | --- |
| SQL `SUM`, `AVG`, `COUNT(col)` | Skips nulls silently |
| SQL `COUNT(*)` | Counts the row anyway |
| SQL `GROUP BY` | Nulls form their own group, or vanish from output |
| SQL `WHERE col != 'x'` | Excludes nulls, which surprises everyone |
| Pandas `sum()`, `mean()` | Skips nulls by default |
| Pandas `groupby()` | Drops null keys by default |
| Pandas `merge` | Nulls do not match each other |

Look at row four. `WHERE status != 'cancelled'` does **not** return
rows with a null status, because `NULL != 'cancelled'` evaluates to
unknown rather than true. Analysts expect "everything that is not
cancelled" and receive "everything that is known and not cancelled".
If 4% of rows have a null status, 4% of your data just left without
comment.

<Callout type="warn" title="Two different meanings of missing">
Null can mean "we do not know" or it can mean "not applicable". These
require opposite handling. A null `discount` that means "no discount"
should become 0. A null `income` that means "not disclosed" must not
become 0, because that would drag the average down with fabricated
poverty. No tool can tell these apart. Only you can.
</Callout>

## Pandas drops null group keys by default

This one deserves its own mention because it is so quiet:

```python
df.groupby("region")["revenue"].sum()
```

Rows where `region` is null are **excluded from the result entirely**.
Not shown as a null group, not raised as a warning. They are simply
absent, and the total of the output is less than the total of the
column. This is the mechanism behind the "parts do not sum to the
whole" discrepancy from the verification chapter.

Passing `dropna=False` includes them as a null group.

## Type coercion

Types cause a smaller number of bugs but sharper ones:

* **Numbers stored as text.** `"1,200"` and `"$45.00"` do not sum;
  they concatenate or error. Worse, a column that is mostly numeric
  with a few text entries reads as `object` dtype and sorts
  lexicographically, so `"9"` comes after `"10"`.
* **Dates as strings.** String dates sort correctly only in ISO
  format. `"03/04/2025"` is ambiguous across locales and a wrong
  parse shifts data by months.
* **Integer division.** In some contexts `7 / 2` is 3, silently
  truncating.
* **Floating point.** Summing money as floats accumulates error.
  Comparing a float total for exact equality against an expected value
  fails for reasons that have nothing to do with your data.

## What to ask for

Two additions to any generated cleaning step:

```text
Report the null count for every column before and after
cleaning, and state what you assumed each null means.
Show the dtype of every column after loading.
```

The dtype list catches numbers-as-text immediately. The null counts
catch every silent drop.

<MultipleChoice
  markdown={`In SQL, which rows does \`WHERE status != 'cancelled'\` return?

- [o] Only rows with a known status that is not 'cancelled'.
  > Comparing null to a value yields unknown rather than true, so null-status rows fail the condition and disappear.
- Only rows where status is null.
  > Nulls are excluded rather than selected.
- All rows whose status differs from 'cancelled', including nulls.
  > This is the common expectation and it is not what happens.
- All rows, since the comparison is always true for non-matching values.
  > Rows with status 'cancelled' are correctly excluded, so it is not all rows.

Three-valued logic means "not equal" quietly also means "and not
missing".`}

<MultipleChoice
  markdown={`\`df.groupby("region")["revenue"].sum()\` produces a total lower than \`df["revenue"].sum()\`. Why?

  > No sampling occurs.
- \`groupby\` applies a default row limit.
  > No such limit exists.
- \`sum()\` behaves differently inside a groupby.
  > The summation behavior is the same.
- [o] Rows with a null \`region\` were excluded from the grouped result.
  > Pandas drops null group keys by default, so those rows contribute to the column total but to no group.

The default \`dropna=True\` on groupby is the single most common cause

<MultipleChoice
  markdown={`A \`discount\` column has nulls meaning "no discount applied". An \`income\` column has nulls meaning "declined to answer". How should they be handled?

- Both should be replaced with the column mean.
  > Mean-filling the discount invents discounts that were never given.
- [o] \`discount\` can become 0; \`income\` must stay missing.
  > "Not applicable" has a genuine zero value, while "unknown" does not and must not be invented.
- Both should be dropped, since nulls are unreliable.
  > Dropping income respondents biases the sample; dropping the discount rows removes most of your data.
- Both should be filled with 0 for consistency.
  > Filling income with 0 fabricates data and biases the average downward.

Identical null representations can carry opposite meanings, and only
domain knowledge separates them.`}
/>

<MultipleChoice
  markdown={`A numeric-looking column sorts with "9" after "10". What is the cause?

- [o] The column is text, so it sorts lexicographically.
  > Character-by-character comparison puts "10" before "9" because "1" precedes "9".
- The values are stored in descending order in the source file.
  > Source ordering does not affect an explicit sort.
- The sort used an unstable algorithm.
  > Stability affects ties among equal values, not ordering of distinct ones.
- Nulls in the column disrupted the comparison.
  > Nulls sort to one end and do not reorder the other values.

A single non-numeric entry is enough to make the whole column text,
after which every numeric operation misbehaves.`}
/>

<MultipleChoice
  markdown={`Why do nulls fail to match each other in a join?

- Because nulls are stored as empty strings internally.
  > Nulls and empty strings are distinct, and empty strings do match each other.
- [o] Because comparing two unknowns yields unknown, not true.
  > Equality between nulls is not true under three-valued logic, so no match is produced.
- Because most engines strip null keys before joining.
  > Rows are not removed prior to matching; the comparison simply fails.
- Because join keys must be indexed and nulls cannot be indexed.
  > Nulls can be indexed in most engines.

Two missing values are not evidence of being the same value, which is
exactly what the logic encodes.`}
/>

<MultipleChoice
  markdown={`Summing a money column stored as floats and comparing the total to an expected value with \`==\` fails. Why?

- Money columns are always stored as strings.
  > They are commonly stored as floats, which is what creates this problem.
- The expected value was computed with a different filter.
  > Possible in general, but there is a well-known numeric cause here.
- [o] Floating-point addition accumulates small representation errors.
  > Values like 0.1 have no exact binary representation, so a long sum drifts slightly from the exact decimal result.
- The data contains hidden null values.
  > Nulls would be skipped rather than cause an exact-comparison failure.

This is a property of binary floating point, not of your data, and it
