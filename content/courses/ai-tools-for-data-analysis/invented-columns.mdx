---
title: Failure Mode 1, Invented Columns
description: Schema hallucination is the most common defect in generated data code, and the easiest to prevent.
---

The model needs a column name. It does not have your schema. It
produces the name that tables like yours usually have. This is called
**schema hallucination**, and in surveys of generated-code defects it
is consistently the most frequent category.

## What it looks like

You mention an `orders` table. The generated query contains:

```sql
SELECT customer_id, order_date, total_amount, status
FROM orders
WHERE status = 'completed'
```

Every one of those four column names is a reasonable guess. Perhaps
three of them exist. Perhaps your status column is called `state`, or
your amount column is `amount_cents`, or your status values are
`COMPLETE` rather than `completed`.

## The two severities

**Loud version:** the column does not exist, the query errors, you fix
it in ten seconds. Annoying and harmless.

**Quiet version:** the column exists but means something else. This is
the one that costs you.

* `amount` exists, but it is the pre-discount amount and `net_amount`
  is what you bill.
* `created_at` exists, but it is when the record was written, not when
  the order was placed (`ordered_at`).
* `status` exists on both `orders` and `shipments`, and the query
  picked the wrong one.

The quiet version runs perfectly and returns a number that is wrong in
a way no error message will ever mention.

<Callout type="warn" title="Value hallucination too">
Names are not the only thing invented. A filter like
`WHERE status = 'completed'` also invents a *value*. If your data uses
`'COMPLETED'` or `'complete'` or the integer `3`, this filter matches
zero rows and returns an empty result or a total of zero, which reads
as a real finding.
</Callout>

## Why "it ran" is not evidence

A query referencing a real column with the wrong meaning runs exactly
as smoothly as one referencing the right column. Execution feedback,
which eliminates the loud version entirely, does nothing at all for
the quiet version.

This is worth internalizing, because sandboxed execution creates a
false sense of safety. It moved the whole error class from "obvious"
to "silent" without reducing how often the model guesses.

## Prevention

Ranked by effectiveness:

1. **Paste the schema.** `df.dtypes`, `DESCRIBE table`, or the DDL.
   This removes almost the entire category.
2. **Paste the distinct values** of any column you filter on. One
   `SELECT DISTINCT status FROM orders` prevents every value
   hallucination in that column.
3. **Connect the assistant** to the real schema, if that is available
   to you.
4. **Read every identifier** in the generated code and confirm you
   recognize it. This is the fallback, and it is worth doing anyway.

## Detection

If you did not prevent it, catch it:

* Scan the generated code for identifiers and check each one exists.
* Watch for an empty result or a zero total, which is the classic
  signature of a value hallucination in a filter.
* Compare the row count after a filter against the unfiltered count.
  A filter that removes 100% of rows or 0% of rows both deserve a
  second look.

<MultipleChoice
  markdown={`Which single query most efficiently prevents value hallucination in a status filter?
