Aggregation is where a correct row set becomes a wrong number. These
defects are subtle because the code is short, the syntax is valid, and
the result is a single plausible figure with nothing to compare it
against.

## The wrong denominator

"Conversion rate" is a ratio, and the numerator is rarely the problem.
The denominator is.

Conversions divided by *what*? Sessions, visitors, unique visitors,
eligible visitors, visitors who reached the checkout page? Each gives
a different number, all of them are called "conversion rate", and the
model will pick whichever one the surrounding text suggests.

The same applies to "average revenue per user" (all users, or active
users?), "churn rate" (of accounts at the start of the period, or of
accounts ever?), and nearly every rate metric in business analytics.

<Callout type="warn" title="The definition lives in your company">
There is a right answer to "which denominator", and it is a fact about
your organization's reporting conventions. It is not recoverable from
the data, and it is not in the model's training corpus. If you do not
specify it, you get a guess with the same name as the metric you
wanted.
</Callout>

## Average of averages

You have average order value per region. You want the overall average
order value. The model writes:

```python
overall = by_region["avg_order_value"].mean()
```

This is wrong unless every region has exactly the same number of
orders. A region with 12 orders counts as much as a region with
40,000. The correct calculation weights by count, or better, goes back
to the raw rows and averages those.

This error is extremely common because the incorrect version reads
like the obviously right thing to do.

## Double counting

Any time an entity can appear more than once, an aggregate over it
overcounts:

* A customer in two segments counted once per segment, then summed to
  a "total customers" that exceeds the real headcount.
* An order with three lines counted three times (the fan-out from the
  previous chapter, arriving here as a wrong total).
* A user with two devices counted as two users in a "daily active
  users" metric.

The signature is a total that is larger than a number you know cannot
be exceeded. Total customers greater than total accounts. Segment
percentages summing above 100%.

## WHERE versus HAVING

`WHERE` filters rows before grouping. `HAVING` filters groups after.
They are not interchangeable and the model sometimes swaps them.

```sql
-- Regions whose completed orders total over 100k
SELECT region, SUM(amount) AS total
FROM orders
WHERE status = 'completed'      -- filters rows first: correct
GROUP BY region
HAVING SUM(amount) > 100000;    -- filters groups after: correct
```

Move `status = 'completed'` into `HAVING` and it either errors or, in
permissive engines, silently changes which rows contributed to the sum.
Move the total condition into `WHERE` and it errors, since the
aggregate does not exist yet.

## Count star, count column, count distinct

Three different questions:

* `COUNT(*)` counts rows.
* `COUNT(col)` counts rows where `col` is not null.
* `COUNT(DISTINCT col)` counts distinct non-null values.

"How many customers ordered?" is `COUNT(DISTINCT customer_id)`. Using
`COUNT(*)` answers "how many orders", which is a different and larger
number wearing the same label.

<MultipleChoice
  markdown={`What does \`WHERE\` do that \`HAVING\` does not?

- Apply only to the first table in a join.
  > \`WHERE\` applies to the whole joined row set.
- Filter using aggregate functions such as \`SUM\`.
  > That is what \`HAVING\` does; \`WHERE\` cannot reference aggregates.
- [o] Remove rows before grouping, so they never enter any aggregate.
  > \`WHERE\` runs first, so excluded rows contribute nothing to sums or counts, while \`HAVING\` filters the groups afterwards.
- Guarantee that no null values reach the result.
  > Neither clause has any special null behavior of that kind.

The distinction is timing: before grouping versus after.`}
