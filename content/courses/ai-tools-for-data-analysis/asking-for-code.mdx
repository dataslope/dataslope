---
title: Asking for Code You Can Check
description: How you phrase a code request determines how hard the result is to review. Ask for reviewable code, not clever code.
---

Once the data is described, the request itself has one job: produce
something you can **check quickly**. A dense one-liner and a
seven-step pipeline can compute the same number, but only one of them
can be reviewed in thirty seconds.

## Ask for steps, not one-liners

Models will happily produce a single chained expression:

```python
result = (df[df.status.isin(["shipped","delivered"])]
          .assign(rev=lambda d: d.qty*d.price)
          .groupby(df.region.fillna("unknown"))
          .rev.sum().sort_values(ascending=False))
```

That is correct-looking and genuinely hard to audit. There is a
`fillna` buried in a `groupby` argument, and a filter whose effect on
row count you cannot see. Compare:

```python
shipped = df[df["status"].isin(["shipped", "delivered"])]
print("rows after status filter:", len(shipped))

shipped = shipped.assign(revenue=shipped["qty"] * shipped["price"])
shipped["region"] = shipped["region"].fillna("unknown")

by_region = shipped.groupby("region")["revenue"].sum()
print(by_region.sort_values(ascending=False))
```

Same answer. Every intermediate step is inspectable, and the row count
after the filter is printed, which is the number most likely to reveal
a mistake.

So: **ask for it that way.**

```text
Write this as separate steps with intermediate variables.
Print the row count after each filter. No method chaining
longer than two calls.
```

## Ask for the assumptions to be stated

This one is underused and unusually effective:

```text
After the code, list every assumption you made about the
data that you could not verify from what I gave you.
```

The list you get back is a ready-made checklist of exactly the things
that could be wrong. Models are generally good at this, because
identifying gaps in a specification is a different task from resisting
the urge to fill them.

A typical response might include: "I assumed `status` values are
lowercase", "I assumed one row per order", "I assumed refunds are
excluded from `amount`". Each of those is a question you can go answer
in your warehouse in about a minute.

## Ask for the sanity checks

```text
Also write the checks you would run to confirm this is right.
```

You will typically get row counts before and after each filter, a
check that group totals sum to the ungrouped total, a null count on
the key columns, and a look at the min and max of the date range.
These are the checks an experienced analyst runs by reflex, and having
them written out means you actually run them.

<Callout type="info" title="The three-part request">
Schema and grain, then: **steps not one-liners**, **state your
assumptions**, **write the sanity checks**. Those three phrases
convert an unreviewable answer into a reviewable one, and they work
identically across every assistant.
</Callout>

## Ask it to do less

A request that spans loading, cleaning, joining, aggregating, and
plotting produces a long block in which one wrong line is easy to miss.
Split it. Get the load and clean step, check it, then ask for the join.

This is slower per step and much faster overall, because you localize
any defect to the step you just added rather than hunting through
forty lines.

<MultipleChoice
  markdown={`Why is a long method chain a poor thing to request, even when it is correct?

- [o] Intermediate results are invisible, so a defect has nowhere to show itself.
  > You cannot see the row count after a filter or the shape after a join, which are the observations that catch mistakes.
- Chains cannot include \`groupby\` operations.
  > \`groupby\` chains fine; that is not a limitation.
- Chained expressions run more slowly than step-by-step equivalents.
  > Performance is essentially identical, and this is not the concern.
- Method chaining is not idiomatic Pandas.
  > Chaining is perfectly idiomatic; readability for review is the issue.

Reviewability, not correctness or speed, is what a chain costs you.`}

<MultipleChoice
  markdown={`What is the main value of asking the model to list its unverifiable assumptions?

- [o] It produces a checklist of the specific things that could be wrong.
  > Each stated assumption is a concrete claim you can go verify against your actual data.
- It causes the model to refuse questions it cannot answer.
  > It does not gate the answer; you still get the code.
- It reduces the number of tokens in the response.
  > It adds output, which increases cost slightly.
- It guarantees the generated code contains no errors.
  > Listing assumptions does not certify the code; it only surfaces what was assumed.

The assumption list converts vague unease into a short list of
verifiable questions.`}
/>
