Once you have an entity like `customer`, the next question is: *what
facts do we need to remember about each customer?* Those facts are
**attributes**.

<Figure
  slug="db-attributes-and-domains-cutout"
  alt="Attributes and their domains, an isometric illustration"
/>

Attributes become columns. But good columns are not just names, they
also have **domains**, the set of values that are allowed to appear.

## Attributes describe an entity

An **attribute** is a property of an entity. A customer might have a
name, email address, signup date, and loyalty status. An order might
have an order date, status, and total amount.

```mermaid
flowchart TB
    Customer["Entity: customer"] --> Name["Attribute: name"]
    Customer --> Email["Attribute: email"]
    Customer --> Joined["Attribute: <code>joined_on</code>"]
    Customer --> Status["Attribute: status"]
```

In a table, each attribute usually becomes one column. Each row then
stores the values for one real entity. A `customers` table might have
the columns `id`, `name`, `email`, `joined_on`, and `status`.

## Domains say what values are allowed

A **domain** is the set of valid values for an attribute. In SQL, the
domain is partly expressed by the column's data type and partly by
rules such as `NOT NULL`, `CHECK`, and `UNIQUE`.

```mermaid
flowchart TB
    Status["Attribute: status"] --> Domain["Domain: allowed values"]
    Domain --> Pending["pending"]
    Domain --> Paid["paid"]
    Domain --> Shipped["shipped"]
    Domain --> Cancelled["cancelled"]
    Domain -. rejects .-> Bad["banana"]
```

The point is not just neatness. A narrow domain protects meaning. If
`status` can contain anything, your application must guess what
`sent`, `shipped`, `SHIP`, and `done` mean.

<SqlCodeBlock
  dialect="postgres"
  title="Types and checks define a column's domain"
  initSql={`CREATE TABLE orders (
  id          INTEGER PRIMARY KEY,
  status      TEXT NOT NULL CHECK (status IN ('pending', 'paid', 'shipped', 'cancelled')),
  total_cents INTEGER NOT NULL CHECK (total_cents >= 0),
  placed_on   DATE NOT NULL
);
INSERT INTO orders VALUES
  (1, 'pending', 2599, DATE '2025-01-10'),
  (2, 'paid',    1200, DATE '2025-01-11');`}
  starterCode={`-- Try changing 'paid' to 'banana' or total_cents to -5.
INSERT INTO
  orders (id, status, total_cents, placed_on)
VALUES
  (3, 'shipped', 3499, DATE '2025-01-12');

SELECT
  *
FROM
  orders
ORDER BY
  id;`}
/>

A good design lets PostgreSQL reject values that do not belong. That
makes bad data harder to create in the first place.

## The danger of "obvious" attributes

Choosing attributes feels easy because the obvious ones come from
everyday life: a person has a first name and a last name, an address
has a house number and a street, a phone number has ten digits. The
trouble is that almost every one of those "obvious" facts is false
for someone, somewhere.

There is a whole genre of programming essays about this, started by
Patrick McKenzie's widely shared 2010 post "Falsehoods Programmers
Believe About Names." Its list of wrong assumptions, that everyone
has exactly one full name, that names have a first and last part in
that order, that names do not change, that names fit in ASCII, has
since been joined by similar lists for addresses, phone numbers, time
zones, and calendars. Each list is really a catalog of schema designs
that hurt real users: the mononymous person who cannot pass a form
that requires a "last name," the rural address with no street name,
the customer whose legal name will not fit in `VARCHAR(20)`.

The design lesson is not "never structure anything." It is that an
attribute and its domain are *claims about the world*, and you should
make claims you can defend. `NOT NULL` on `family_name` claims every
person has one. `VARCHAR(20)` claims no name is longer. A `CHECK`
that statuses come from a fixed list claims the business will warn
you before inventing a new status. Some of those claims are solid;
others quietly exclude real people and real cases. The strongest
designers are not the ones with the strictest constraints, they are
the ones who know *which* facts the system genuinely guarantees.

<Callout type="info" title="When in doubt, constrain what you control">
Values your own system generates, statuses, roles, internal codes,
deserve tight domains, because you control the full list. Values that
come from the outside world, names, addresses, deserve more
humility and looser domains. Required versus optional is still worth
deciding; pretending to know the format often is not.
</Callout>

## Atomic values: one value per cell

A column should usually hold one value, not a list packed into a
single cell. This is called **atomicity**. It is the core idea behind
first normal form, which we will study later.

```mermaid
flowchart LR
    Bad["One cell:<br/>red, blue, green"] --> Problem["Hard to search,<br/>sort, validate, or reference"]
    Good["Separate rows<br/>or separate attributes"] --> Better["Each cell has<br/>one clear value"]
```

A `phone_numbers` value like `'555-1111, 555-2222'` may look simple,
but it hides multiple facts in one cell. If you later need to verify,
label, or delete one phone number, the design fights you.

- [o] The set of valid values for that attribute, often enforced by types and constraints.
  > A domain combines data type and rules, such as allowed statuses or nonnegative amounts.
- The table where the column appears.
  > The table gives context, but the domain is about which values are allowed.
- The number of rows currently in the table.
  > Row count changes over time and is not the domain of a column.
- The order in which columns are displayed.
  > Display order is not a data rule.

A domain is the allowed meaning-space for a column.`}

## Attribute or its own entity?

Some facts are simple properties. Others deserve their own table. The
question is not "is it a noun?" but "does this thing have its own
identity, attributes, or relationships?"

```mermaid
flowchart TB
    Q{"Does it have its own details<br/>or many rows?"} -->|"no"| Attr["Keep as attribute"]
    Q -->|"yes"| Entity["Model as entity"]
    Attr --> Email["<code>customer.email</code>"]
    Entity --> Address["addresses table"]
```

For example, `customer.email` is often a simple attribute. But
`address` might become an entity if a customer can have many addresses,
if orders ship to saved addresses, or if addresses need their own
validation and history.

```mermaid
flowchart TD
    Customer["Customer"] --> Simple["email<br/>single value"]
    Customer --> Complex["addresses<br/>many saved places"]
    Complex --> AddressEntity["Address entity"]
```

<Callout type="warn" title="Do not model everything as a separate table">
A table has a cost: keys, relationships, joins, and rules. Make a new
entity when the thing has independent meaning, repeated instances, or
relationships of its own, not just because it is a noun.
</Callout>

## Attributes should be named for meaning

Good attribute names describe what the value means. `created_at` is
clearer than `date`. `total_cents` is clearer than `amount` when the
unit matters.

```mermaid
flowchart TB
    Vague["amount"] --> Question["Dollars? cents?<br/>subtotal? total?"]
    Clear["<code>total_cents</code>"] --> Meaning["Integer number of cents"]
```

The name, type, and constraints work together. A column called
`total_cents` with type `INTEGER` and a nonnegative check is much
harder to misunderstand.
