## What you've built up

The course moved deliberately from "why" to "how" to "how to think":

1. **What databases are and where SQL came from**, the five
   nightmares, Codd's idea, and PostgreSQL's lineage.
2. **Relational foundations**, tables, keys, types.
3. **Querying data**, `SELECT`, `WHERE`, `ORDER BY`.
4. **Expressions and functions**, `CASE`, text, numbers and casting,
   dates.
5. **Summarizing data**, aggregates, `GROUP BY`, `HAVING`, `FILTER`
   and `ROLLUP`.
6. **Connecting tables**, foreign keys, joins, many-to-many, set
   operations.
7. **Data modeling**, entities, entity relationship diagrams,
   normalization.
8. **Composing queries**, subqueries, common table expressions,
   recursion.
9. **Window functions**, `OVER`, ranking, running totals, frames,
   `LAG` and `LEAD`, top N per group, and the execution order that
   explains where they run.
10. **Changing data**, upserts, views, transactions.

And if you skipped the **Interesting discussions** pages,
[Spreadsheets vs. Databases](/courses/intro-sql-postgres/spreadsheets-vs-databases)
and [How Applications Use
Databases](/courses/intro-sql-postgres/how-applications-use-databases),
now is a lovely time to read them. They land differently once you
can write the queries yourself.

Each layer rested on the one before it. Joins only made sense once
keys did; normalization only made sense once you felt the pain of
duplication; window functions only made sense once aggregates had
shown you what gets lost when rows collapse; and the execution order
tied the whole querying story together.

## The big ideas worth keeping

If you remember only a handful of things, make it these:

- **A database stores each fact once, in a structured place**, that
  is what separates it from a spreadsheet and prevents data from
  contradicting itself.
- **Keys connect tables.** A primary key names a row; a foreign key
  points to one. Everything relational grows from this.
- **Joins recombine what normalization split apart.** You store data
  cleanly in separate tables, then join to view it together.
- **SQL is declarative.** You describe *what* you want; the database
  figures out *how*. The logical execution order explains the rest.
- **`OVER` is the difference between summarizing and comparing.** An
  aggregate collapses rows; a window function computes across them
  and leaves every row standing.
- **Model before you build.** Naming entities and relationships first
  saves you from tangled tables later.

<Callout type="info" title="You can now read real queries">
Pick almost any SQL query in the wild and you can now decode it:
identify the tables in `FROM`, the row filter in `WHERE`, the groups,
the joins, and the columns. That literacy is exactly what this course
set out to give you.
</Callout>

## Practice to make it stick

Concepts solidify by *doing*. A few ways to keep going:

- **Re-solve the examples from memory.** Close the page, then rebuild
  a join or a `GROUP BY` query from scratch in the
  [PostgreSQL Playground](/playground/postgres).
- **Model something you know.** Sketch tables and an ER diagram for a
  hobby, a sports league, or your music library. Ask: what are the
  entities and relationships?
- **Ask questions of data.** You met the Chinook music store in the
  aggregate and join chapters, go back to those blocks, write five
  questions of your own about its artists and tracks, and answer each
  with a query. Counts, averages, filters, joins, windows: it can
  take them all.

## Where to go from here

This was a *foundations* course, focused on SQL and relational
thinking. When you are ready to go further, natural next topics
include:

- **Indexes and performance**, how databases find rows quickly, when
  to add an index, and how to read a query plan. (You met the *why*;
  the *how* is a deep field.)
- **Designing larger schemas**, modeling real applications with many
  related entities. The
  [Database Design with PostgreSQL](/courses/database-design-postgresql)
  course picks up exactly there.
- **Analytical SQL at scale**, the same window functions and grouping
  sets against columnar data. The
  [SQL for Data Analysis with DuckDB](/courses/sql-analytics-duckdb)
  course covers that ground.
- **Using databases from code**, how applications connect to
  PostgreSQL and run the queries you now understand.

But there is no rush. The relational way of thinking you have built
here is the foundation everything else stands on. Keep asking
questions of data, keep writing queries, and the rest will follow.

Welcome to working with databases.
