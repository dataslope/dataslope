---
title: Sizing a Task
description: Why a task you can review in ten minutes beats one that takes an afternoon, and how to cut a big change into steps an agent can finish one at a time.
---

The size of a task decides two things: how likely the agent is to
finish it, and how likely you are to review it properly. Both get worse
as the task grows, and the second is the one that is easy to forget,
because the agent's half of the work gets faster while yours does not.

## Review effort grows with the diff

An agent can produce a 600-line diff in a few minutes. Reading it
properly takes far longer than that. The work in a large task
does not disappear when an agent does the typing: it moves into the
review, which is the half of the job that stays yours.

Small diffs get read. Large ones get skimmed, because the reviewer's
attention runs out before the diff does, and a skimmed diff is an
unreviewed one. Two widely cited sources on code review put rough
numbers on it. Google's guide for its own engineers says 100 lines is
usually a reasonable size for a change and 1,000 lines is usually too
large, and gives among its reasons that small changes are reviewed more
quickly and more thoroughly and are simpler to roll back.[^google] A
SmartBear study of a programming team at Cisco recommends reviewing no
more than 200 to 400 lines at a time, and reports that past 400 lines
the ability to find defects diminishes.[^smartbear]

Both were written about changes made by people. Nothing about an agent
being the author makes a long diff quicker to read, and the agent's own
odds get worse with size too: a bigger task means more files opened and
more tool output piling into its context, where a constraint you gave
at the start has more to compete with (see
[What the Agent Sees](/courses/working-with-coding-agents/what-the-agent-sees)).

## One concern per session

A bug fix and a refactor in one session produce one diff, and in that
diff you cannot tell which change did what. If a test starts failing,
was it the fix or the rename? If the fix is wrong, can you keep the
refactor without it? Google's guide gives the same advice for human
changes: refactorings go in a separate change from feature work and bug
fixes.[^google]

The running example has a small case of it. The request was a discount,
and the session's third commit, "Tidy up formatting helpers", renamed a
function across two files that have nothing to do with discounts. It
landed in a commit of its own and in files the discount never touched,
which is why undoing it takes a single command (see
[Undoing Changes](/courses/working-with-coding-agents/undoing-changes)).
Had the agent made the rename in `pricing.py` while adding the discount,
the two would have been one change.

One concern per session also keeps the context about one thing.
Everything a session reads stays in its context until the window fills,
so the files opened for one job are still there, competing for
attention, while the agent works on the next. When a task is finished,
start the next one in a fresh session.

## Cutting a feature into steps

"Add CSV export" sounds like one task. For the shop, it is at least
three, and each can be its own request, its own review and its own
commit:

| Step | The request | Done when |
| --- | --- | --- |
| 1 | Add `items_to_csv(items)` to a new `export.py`: a header row, then one row per item with name, qty, price and line total, in cents. Add tests. | Its tests pass, including one for a name that contains a comma. |
| 2 | Add a command, `python export.py order.json`, that reads an order from a JSON file and prints its CSV using `items_to_csv`. Change no other file. | Run on a sample order, it prints the same rows the step 1 tests expect. |
| 3 | Document the command in `README.md`. | The example in the README runs as written. |

Every step leaves the code working. After step 1 nothing calls
`items_to_csv` yet, but it exists, it is tested, and every old test
still passes; you could stop there and lose nothing. After step 2 the
feature works. After step 3 someone else can find it. If step 2 goes
badly, you throw away step 2 and keep step 1.

The order runs from the inside out. The formatting function holds the
edge cases (a comma inside a name, a line total that has to multiply by
the quantity), so it goes first, in a diff small enough to read line by
line. Once it exists, the command around it is thin. The documentation
comes last because it should describe what was built, not what was
planned.

Each step ends at a commit, made after you have reviewed it. That
commit is the point you return to when the next step goes wrong, and it
keeps one step's diff from blurring into the next one's.

One assertion is enough to say step 1 is done, and it is short enough
to check against the request by eye. "Add CSV export" as a single
request has no test like that. Its test for done is all three rows of
the table at once, and a session that did all three would hand you one
diff to check against every row together.

## Signs the task is too big

None of these is a rule, but each one is cheap to notice before the
session starts:

* **You cannot write the test for done in one sentence.** If done needs
  a paragraph, the task is several tasks.
* **The request needs "and" more than once.** "Add CSV export and a JSON
  export and email the file every night" is three requests sharing a
  sentence.
* **You would not review the same change from a colleague in one
  sitting.** The agent's diff deserves the same reading a colleague's
  would get, and it is no shorter.
* **You cannot say which files it should touch.** Asking for a plan will
  tell you (see
  [Plan Before Code](/courses/working-with-coding-agents/plan-before-code)),
  and a plan that lists a dozen files is a sign of its own.

When one of these fires, look for the smallest piece that is useful on
its own and can be tested on its own, usually the thing every later step
depends on. Ask for that first.

The opposite mistake exists too. If writing the request takes longer
than making the change, make the change yourself;
[When to Take Over](/courses/working-with-coding-agents/when-to-take-over)
has more on that call.
