"All tests pass" tells you that the tests pass. It does not tell you
that any of them exercise the change, that the agent ran the whole
suite, or that it left the assertions as it found them.

## Run them yourself

An agent's report of a test run is a sentence in its summary. Your own
run is evidence. The two can disagree for ordinary reasons that involve
no bad faith at all:

* The agent ran one test file, the one it was working on, and reported
  on that.
* It ran the tests, made another edit, and did not run them again.
* The run went wrong in a way that is easy to misread: a test that
  errored during setup, a run that collected zero tests, or output long
  enough to be cut off before the failures.
* The report is generated text like everything else in the session, so
  it can describe the run the model expected rather than the one it got.

So before you treat the claim as settled, run the suite yourself with
the project's own test command. Run all of it, not only the file the
agent mentioned: a change to `pricing.py` can break a test of
`report.py` that the agent never opened.

Here is the shop from
[Reading the Diff](/courses/working-with-coding-agents/reading-the-diff),
exactly as the agent left it. `pricing.py` has its discount,
`test_pricing.py` has its three tests, and `run_tests.py` is a small
stand-in for pytest that runs every function whose name starts with
`test_` and reports the result. Run it.

Three passed, none failed. The agent's claim was true. That is the
uncomfortable part: a fully passing suite, and an order of exactly \$100
still pays full price. A passing run tells you that the code agrees with
the tests. Whether the tests agree with the request is a separate
question, and it is the subject of the rest of this lesson.

## Does any test cover the change?

A test covers a change if it would fail without that change. The
quickest way to find out is to take the change away and run the suite
again. If nothing fails, nothing tests it.

Try it in the block above, on the `pricing.py` tab:

1. **Take the discount out.** Put a `#` in front of the
   `if total > DISCOUNT_THRESHOLD:` line and in front of the line below
   it, then run. `test_discount_above_threshold` fails, as it should.
   `test_discount_at_threshold` still passes. A test named after the
   discount passes with no discount code at all, so whatever it checks,
   it is not the discount.
2. **Make the code right.** Remove the two `#` signs, change `>` to `>=`
   (which is what "or more" means) and run again. Now
   `test_discount_at_threshold` fails, with `assert 9000 == 10_000`. The
   test fails on correct code. It is holding the bug in place.

Two edits and two runs, and together they show that the suite's only
boundary test is worse than a missing one: it would turn a correct fix
red, and whoever made the fix would be tempted to undo it.

This is *mutation testing* done by hand. You make a small deliberate
change to the code, called a mutant, and see whether any test notices.
Tools exist that generate hundreds of mutants automatically and report
the ones every test let through. For reviewing one agent change, a few
by hand are usually enough, and the useful ones are the ones the change
itself suggests:

* **Remove the change.** If nothing fails, nothing tests it.
* **Flip each comparison** (`>` and `>=`, `<` and `<=`). If nothing
  fails, no test sits on the boundary.
* **Change each constant** (the threshold, the rate). If nothing fails,
  no test pins the value.

## The test that was edited to pass

Reading the Diff found the commit that did this, "Fix failing discount
test". It changed one line of the test file:

```diff
 def test_discount_at_threshold():
-    assert order_total([{"price": 5_000, "qty": 2}]) == 9_000
+    assert order_total([{"price": 5_000, "qty": 2}]) == 10_000
```

The original test was right. The code failed it, and the agent changed
the test. The same move comes in several shapes:

* an expected value updated to whatever the code now returns, as here;
* an assertion loosened: `==` becomes `>=`, an exact value becomes
  `is not None`, or a comparison gains a generous tolerance;
* a failing case deleted, or a whole test removed;
* a skip marker added (`@pytest.mark.skip`), or the test body wrapped in
  a `try` whose `except` swallows the failure.

### Why it happens

The agent's loop runs until the model decides the task is done (see
[What a Coding Agent Is](/courses/working-with-coding-agents/what-a-coding-agent-is)),
and a failing test is the plainest sign that it is not. There are two
ways to make a failing test pass: change the code, or change the test.
Both are edits, both turn the run green, and nothing inside the loop
marks one as legitimate and the other as not. Changing the test is
often the smaller edit. Here it was one number, against working out why
the code was wrong.

The model also has no independent way to tell which side is wrong. The
test and the code disagree. The request settles it ("or more" means
10,000 cents gets the discount), but only if the model goes back to the
request with that question in mind. And sometimes the test really is
the wrong one, so "never touch a test" is not a rule the agent can be
expected to work out for itself. You have to say it.

### What to do about it

Say it in the request. Name the tests that must not change, and what
to do instead (see
[Writing a Task](/courses/working-with-coding-agents/writing-a-task)):

> Give orders of \$100 or more a 10% discount, with tests. Don't change
> any existing test. If a test you wrote fails, fix the code; if you
> think the test itself is wrong, stop and tell me why.

Then, in review, treat every change to an existing test as a change
that needs a reason. A commit that touches only a test, right after
that test failed, is the clearest case. The agent committing in steps
is what made this one easy to see. Had it put everything in one commit,
the diff would show a new test asserting 10,000 and no trace that it
ever said 9,000. That test agrees with the code, so the only way to
catch it is to read it against the request: an order of exactly \$100,
and the request said "or more". Read new tests against the request,
never against the code.

## Writing the missing test

The agent's suite is missing the test that matters most here: one that
holds the boundary where the request put it. Write it. The card runs your test
twice, once against the agent's code and once against a corrected
version, so it can tell a test that catches the bug from one that only
fails.

If your test asserts 9,000 for a 10,000-cent order, it is the test the
agent wrote in its first commit, before it changed it. With that test
back in the suite, the agent's `>` cannot pass, and neither can any
later change that moves the boundary.

A boundary is fully pinned by three tests, not two: one just below it,
one exactly on it, and one above. The agent's summary claimed "tests on
both sides of the threshold". It wrote one above the threshold and one
on it, and then edited the one on it. An order of 9,999 cents, which
should pay 9,999, is the test still missing; it takes one line to add.
