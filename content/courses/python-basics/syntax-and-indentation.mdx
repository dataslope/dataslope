On the last page we met the Zen of Python, "Readability counts." This page
is where that aphorism becomes a law of the language. Python uses **indentation
itself** to delimit blocks of code, which means whitespace is not cosmetic in
Python; it is syntax.

<Figure
  slug="python-basics-syntax-cutout"
  alt="Nested indented blocks stepping inward like an architectural floor plan, with guide lines marking each indentation level"
/>

Here we cover what counts as a block, what Python's official style guide,
PEP 8, has to say, and how to keep your editor honest. (The deeper story, why
Guido van Rossum made this divisive choice, and the legendary tabs-versus-spaces
war it touched off, waits for you in *The Story of Python* near the end of the
course.)

## Why Python chose significant whitespace

Most languages in the 1980s and 1990s used braces (`{ ... }`) or
keywords (`begin ... end`) to mark blocks. Python took a different
path: Guido van Rossum observed that **programmers already indent code
to show structure to humans**, so why not make the compiler trust that
indentation? The result is that:

1. **Badly indented code will not run.** A misaligned line is a syntax
   error, not a silent bug.
2. **Every Python codebase looks consistent.** There is no "my braces
   on the same line" vs "my braces on the next line" religious war.
3. **Beginner-friendly.** New programmers do not have to learn a
   special punctuation syntax; they just indent naturally.

This design choice is polarizing. Some find it liberating; others miss
the explicit delimiters of C-like languages. Either way, it is
non-negotiable in Python.

## Blocks are indentation

In C, JavaScript, or Java, code inside a function or `if` is wrapped
in `{ ... }`. In Python it is wrapped in **a deeper indentation level**:

<CodeBlock
  adapter="python"
  files={[
    {
      filename: "main.py",
      starterCode: `def shout(message):
    if message:
        return message.upper() + "!"
    return ""

print(shout("hello"))
print(shout(""))
`,
    },
  ]}
/>

The colon (`:`) at the end of `def`, `if`, `for`, `while`, `try`,
`class`, and so on signals "the next indented block belongs to me".

<Figure
  slug="python-syntax-and-indentation-blocks-indentation-inline-cutout"
  alt="A stack of shelves where the depth of a shelf alone says what belongs on it, with no brackets anywhere in sight"
  caption="The indentation is the block, so a stray space is a syntax error rather than a style choice."
/>

<Callout type="info">
Think of the colon as Python's way of saying "here comes a block". It
replaces the opening brace `{` in C-like languages. The dedent
(returning to the previous indentation level) implicitly closes the
block.
</Callout>

## What happens when indentation is wrong

If indentation is missing where Python expects it, you get an
`IndentationError`. If it is inconsistent, you get a `TabError` or a
silently broken program (in older Python 2 codebases).

  slug="python-syntax-and-indentation-semicolons-please-do-not-inline-cutout"
  alt="Two statements crammed onto a single rail beside the same two given a rail each, the second pair easy to reach"
  caption="One statement per line is what keeps the indentation readable in the first place."
/>

<CodeBlock
  adapter="python"
  files={[
    {
      filename: "main.py",
      starterCode: `# Try un-indenting the 'return' line (remove the leading spaces)
# then run again to see the IndentationError.
def square(x):
    return x * x

print(square(5))
`,
    },
  ]}
/>

<Callout type="warn" title="Mixing tabs and spaces">
Python 3 will raise a **TabError** if a single block mixes tabs and
spaces. Python 2 allowed it and silently treated a tab as "however many
spaces it takes to reach the next multiple of 8", which caused famously
confusing bugs. Configure your editor to insert spaces when you press
the Tab key, and you will never see this error.
</Callout>

## The four-space rule (PEP 8)

[PEP 8](https://peps.python.org/pep-0008/), Python's official style
guide, says:

- Use **four spaces** per indentation level.
- Do **not** mix tabs and spaces inside the same block. Python 3
  raises a `TabError` if you try.
- Limit lines to **79 characters** (or 99 in modern codebases that
  follow `black`'s default of 88).
- Two blank lines between top-level functions and classes; one blank
  line between methods inside a class.
- One statement per line. `if x: do(); other()` is legal but frowned
  upon.

<Figure
  slug="python-syntax-and-indentation-four-space-rule-pep-inline-cutout"
  alt="A column of lines all starting at the same ruled margin, with a single line beginning a hair short of it and flagged"
  caption="Four spaces everywhere: the rule matters less than never mixing two conventions in one file."
/>

Tools that enforce this for you:

- [`black`](https://black.readthedocs.io/) reformats your code in one
  consistent style with almost no configuration. It is the most popular
  Python formatter.
- [`ruff`](https://docs.astral.sh/ruff/) is a very fast linter that
  rolls up most of the older tools (`flake8`, `isort`, `pyupgrade`).
- Most editors (VS Code, PyCharm, Vim, Emacs) can run these on save.

### The one-line answer to tabs vs spaces

You may have heard that tabs versus spaces is a holy war among programmers.
For Python the practical answer is short: **use four spaces, and let your editor
insert them when you press Tab.** PEP 8 is explicit about it,

> Spaces are the preferred indentation method. Tabs should be used solely to
> remain consistent with code that is already indented with tabs.

So write new code with four spaces; if you join a project that already uses
tabs, match it. Either way, configure your editor to insert one or the other
automatically and you will never produce the mixed indentation that triggers a
`TabError`. The longer, surprisingly heated history of *why* this argument
exists at all is one of the deep-dives in *The Story of Python* later on, it is
genuinely entertaining, but it should never slow down your actual work.

## Continuation lines

Python statements normally end at the end of a line. There are two
ways to span multiple lines:

1. **Implicit continuation** inside `()`, `[]`, or `{}`. This is the
   preferred style.
2. **Explicit continuation** with a backslash `\` at end of line.

<Figure
  slug="python-syntax-and-indentation-continuation-lines-inline-cutout"
  alt="A long line folded neatly inside a pair of brackets, beside the same line held together by one fragile trailing hook"
  caption="Wrap a long line in brackets rather than a trailing backslash, which breaks on a stray space."
/>

<CodeBlock
  adapter="python"
  files={[
    {
      filename: "main.py",
      starterCode: `# Preferred: implicit continuation inside parentheses.
total = (
    1 + 2 + 3
    + 4 + 5 + 6
)

print("Total:", total)
`,
    },
  ]}
/>

<CodeBlock
  adapter="python"
  files={[
    {
      filename: "main.py",
      starterCode: `# Works but ugly: explicit backslash continuation.
total2 = 1 + 2 + 3 \\
    + 4 + 5 + 6

print("Total2:", total2)
`,
    },
  ]}
/>

PEP 8 recommends avoiding backslash continuation where possible. Modern
code wraps long lines in parentheses even when they are not strictly
needed (e.g. for a long `if` condition).

## Semicolons (please do not)

Python technically allows `;` to separate statements on one line. The
community consensus is **do not use it**. PEP 8 says "avoid it" in
polite language; the real sentiment is "never do this".

<CodeBlock
  adapter="python"
  files={[
    {
      filename: "main.py",
      starterCode: `# Legal Python, but PEP 8 says no.
a = 1
b = 2
print(a + b)
`,
    },
  ]}
/>

The only exception is in one-liners passed to `python -c`:

```bash
python -c "import sys; print(sys.version)"
```

Even there, most people avoid `;` and use newlines instead.

## Real-world comparison: Python vs other languages

Here is how other popular languages handle indentation:

| Language | Block delimiter | Indentation | Community standard |
| --- | --- | --- | --- |
| Python | Indentation | Required | 4 spaces (PEP 8) |
| JavaScript | `{ ... }` | Optional | 2 spaces (Prettier default) |
| Java | `{ ... }` | Optional | 4 spaces |
| C / C++ | `{ ... }` | Optional | Varies (Google: 2, Linux kernel: tabs) |
| Go | `{ ... }` | Optional | Tabs (`gofmt` enforces this) |
| Ruby | `do ... end` or `{ ... }` | Optional | 2 spaces |
| Rust | `{ ... }` | Optional | 4 spaces (`rustfmt` default) |
| Haskell | Indentation or `{ ; }` | Optional but idiomatic | 2 spaces |

Python is unique in making indentation **mandatory**. Haskell has
optional significant whitespace, but most Haskellers use braces to
avoid the complexity. Python goes all-in.
