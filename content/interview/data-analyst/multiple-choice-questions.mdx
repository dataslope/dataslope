## SQL fundamentals

<MultipleChoice
  markdown={`A query uses \`WHERE\`, \`GROUP BY\`, \`HAVING\`, \`SELECT\`, and \`ORDER BY\`. Which clause is evaluated **last**?

- \`SELECT\`
  > \`SELECT\` is evaluated after \`HAVING\` but before the result set is sorted, which is why a column alias defined in \`SELECT\` is usable in \`ORDER BY\` but not in \`WHERE\`.
- [o] \`ORDER BY\`
  > Sorting happens once the rows to return are known: \`FROM\` → \`WHERE\` → \`GROUP BY\` → \`HAVING\` → \`SELECT\` → \`ORDER BY\` → \`LIMIT\`.
- \`HAVING\`
  > \`HAVING\` filters groups immediately after \`GROUP BY\`, well before the rows are sorted.
- \`WHERE\`
  > \`WHERE\` is one of the earliest steps: it filters individual rows before any grouping happens.`}
/>

<MultipleChoice
  markdown={`A \`users\` table has 10 rows, and 3 of them have a \`NULL\` \`email\`. What does \`SELECT COUNT(email) FROM users\` return?

- \`10\`
  > That is what \`COUNT(*)\` returns. \`COUNT(col)\` is the one that skips \`NULL\`s.
- [o] \`7\`
  > \`COUNT(col)\` counts only rows where the column is not \`NULL\`, so the 3 \`NULL\` emails are excluded.
- \`3\`
  > \`COUNT(email)\` counts the populated values, not the missing ones. Counting the missing ones needs something like \`COUNT(*) - COUNT(email)\`.
- \`NULL\`
  > Aggregates do not propagate \`NULL\` the way scalar expressions do; \`COUNT\` always returns a number, and returns \`0\` on an empty input.`}
/>

<MultipleChoice
  markdown={`How many rows does \`SELECT * FROM orders WHERE status = NULL\` return, on a table where many rows genuinely have a \`NULL\` \`status\`?

- Every row whose \`status\` is \`NULL\`.
  > \`= NULL\` never matches, even against a \`NULL\` value. The predicate for that is \`status IS NULL\`.
- [o] Zero rows.
  > Comparing anything to \`NULL\` with \`=\` yields \`NULL\` rather than true, and \`WHERE\` keeps only rows where the predicate is true, so nothing survives.
- Every row in the table.
  > A predicate evaluating to \`NULL\` is not treated as true, so no rows are kept rather than all of them.
- The query raises a syntax error.
  > It is valid SQL and runs without complaint, which is exactly what makes the bug easy to miss.`}
/>

<MultipleChoice
  markdown={`Which query returns the customers who have **never** placed an order?

- \`SELECT c.* FROM customers c INNER JOIN orders o ON o.customer_id = c.id WHERE o.id IS NULL\`
  > An \`INNER JOIN\` has already discarded the unmatched customers, so the \`IS NULL\` filter can never be satisfied and the result is empty.
- [o] \`SELECT c.* FROM customers c LEFT JOIN orders o ON o.customer_id = c.id WHERE o.customer_id IS NULL\`
  > The \`LEFT JOIN\` keeps every customer and fills the order columns with \`NULL\` when there is no match, so the \`IS NULL\` filter isolates exactly the non-buyers. \`NOT EXISTS\` expresses the same anti-join.
- \`SELECT c.* FROM customers c LEFT JOIN orders o ON o.customer_id = c.id WHERE o.amount = 0\`
  > This finds customers whose orders have a zero amount, which is a different population from customers with no orders at all.
- \`SELECT c.* FROM customers c WHERE c.id NOT IN (SELECT customer_id FROM orders)\`
  > The idea is right, but if \`orders.customer_id\` contains even one \`NULL\`, \`NOT IN\` returns no rows at all. \`NOT EXISTS\` or the \`LEFT JOIN\` pattern is the safe form.`}
/>

<MultipleChoice
  markdown={`Which set operator keeps duplicate rows across the two result sets?

- \`UNION\`
  > \`UNION\` deduplicates, which costs a sort or hash pass over the combined result.
- [o] \`UNION ALL\`
  > \`UNION ALL\` concatenates both inputs untouched, which also makes it the faster of the two because it skips deduplication.
- \`INTERSECT\`
  > \`INTERSECT\` returns the distinct rows present in both inputs, so duplicates are collapsed.
- \`EXCEPT\`
  > \`EXCEPT\` returns the distinct rows of the first input that are absent from the second.`}
/>

<MultipleChoice
  markdown={`\`SELECT region, category, SUM(amount) FROM orders GROUP BY region\` fails on most engines. Why?

- \`SUM\` cannot be combined with \`GROUP BY\`.
  > Aggregating per group is precisely what \`GROUP BY\` exists for.
- [o] \`category\` is neither in the \`GROUP BY\` nor wrapped in an aggregate.
  > Each output row represents one region, which may span many categories, so the engine has no single \`category\` value to show. Group by it as well, or aggregate it (\`MIN(category)\`, \`STRING_AGG(...)\`).
- \`GROUP BY\` requires at least two columns.
  > Grouping by a single column is perfectly valid.
- \`amount\` must be listed in the \`GROUP BY\` too.
  > \`amount\` is inside an aggregate, which is exactly how a measure should be handled.`}
/>

<MultipleChoice
  markdown={`\`orders\` has one row per order with an \`amount\`. \`order_items\` has several rows per order. You join them and \`SUM(o.amount)\`. What happens to the total?

- It stays correct, because the join only adds columns.
  > A one-to-many join adds *rows*: the left row is repeated once per match, and each repeat contributes its \`amount\` again.
- [o] It is inflated, because each order's \`amount\` is repeated once per item.
  > This is join fan-out. Aggregate the many-side back to the order grain first, in a CTE or subquery, and only then join. (\`SUM(DISTINCT o.amount)\` looks like a shortcut and is not one: it also collapses two genuinely different orders that happen to share an amount.)
- It is understated, because unmatched orders are dropped.
  > An \`INNER JOIN\` does drop orders with no items, but the dominant and more dangerous effect here is duplication of the matched ones.
- It returns \`NULL\`.
  > \`SUM\` skips \`NULL\`s and returns a number whenever at least one non-\`NULL\` value exists.`}
/>

<MultipleChoice
  markdown={`A report uses \`FROM customers c LEFT JOIN orders o ON o.customer_id = c.id WHERE o.status = 'shipped'\`, and customers with no orders vanish. What happened?

- The \`LEFT JOIN\` was silently rewritten as a \`RIGHT JOIN\`.
  > Engines do not swap join direction; the filter is what changed the result.
- [o] The \`WHERE\` filter on the right table discards the \`NULL\`-padded rows, turning the \`LEFT JOIN\` into an inner join.
  > Non-buyers arrive with \`o.status\` as \`NULL\`, and \`NULL = 'shipped'\` is not true. Move the condition into the \`ON\` clause to keep them.
- \`LEFT JOIN\` cannot be used with a \`WHERE\` clause.
  > The combination is legal and common; the subtlety is only *which* table the filtered column belongs to.
- The join key has duplicates.
  > Duplicate keys would multiply rows, not remove the unmatched ones.`}
/>

<MultipleChoice
  markdown={`What does \`COALESCE(discount, promo_rate, 0)\` return?

- The sum of the three arguments.
  > Adding the arguments is what \`+\` does; \`COALESCE\` selects rather than combines.
- [o] The first argument that is not \`NULL\`, reading left to right, or \`0\` if both columns are \`NULL\`.
  > \`COALESCE\` walks its arguments in order and returns the first non-\`NULL\` one, which is the standard way to supply a fallback.
- \`NULL\` whenever any argument is \`NULL\`.
  > That is the behavior of ordinary arithmetic on \`NULL\`, and the reason \`COALESCE\` exists.
- The last argument, always.
  > The last argument acts as the default and is only reached when everything before it is \`NULL\`.`}
/>

<MultipleChoice
  markdown={`A \`ratings\` column has 100 rows, 20 of them \`NULL\`. How does \`AVG(rating)\` treat the missing values?

- It treats them as \`0\`, so the average is dragged down.
  > Substituting \`0\` requires an explicit \`AVG(COALESCE(rating, 0))\`, which is a different question about the data.
- [o] It ignores them, averaging the 80 non-\`NULL\` values.
  > SQL aggregates skip \`NULL\`s entirely, so both the numerator and the denominator use only the 80 populated ratings.
- It returns \`NULL\` because some inputs are \`NULL\`.
  > An aggregate returns \`NULL\` only when *every* input is \`NULL\`.
- It divides the sum of 80 values by 100 rows.
  > The denominator is the count of non-\`NULL\` values, not the row count. Dividing by 100 requires \`SUM(rating) / COUNT(*)\`.`}
/>

<MultipleChoice
  markdown={`What does \`SELECT COUNT(DISTINCT customer_id) FROM orders\` count?

- Every row in \`orders\`.
  > That is \`COUNT(*)\`, which counts orders rather than customers.
- [o] The number of different non-\`NULL\` customer ids that appear.
  > \`DISTINCT\` collapses repeats, and \`COUNT\` still ignores \`NULL\`, so a customer with 40 orders contributes exactly 1.
- The number of orders that have a non-\`NULL\` customer id.
  > That is \`COUNT(customer_id)\` without \`DISTINCT\`.
- The number of customers in the \`customers\` table.
  > It can only see ids that actually appear in \`orders\`, so customers who never ordered are invisible to it.`}

<MultipleChoice
  markdown={`Which expression counts only the orders from the North region, in a query that is already grouped by month?

- \`COUNT(region = 'North')\`
  > \`COUNT\` counts every non-\`NULL\` argument, and a boolean is non-\`NULL\` whether it is true or false, so this counts every row.
- [o] \`SUM(CASE WHEN region = 'North' THEN 1 ELSE 0 END)\`
  > Conditional aggregation: the \`CASE\` contributes 1 for matching rows and 0 otherwise. \`COUNT(CASE WHEN region = 'North' THEN 1 END)\` works too, because the implicit \`ELSE NULL\` is skipped.
- \`WHERE region = 'North'\`
  > A \`WHERE\` clause would restrict the *whole* query, so the other regions would disappear from every month.
- \`HAVING region = 'North'\`
  > \`HAVING\` filters entire groups after aggregation, which again drops the other regions rather than counting alongside them.`}
/>

<MultipleChoice
  markdown={`What does \`LIMIT 10\` return without an \`ORDER BY\`?

- The 10 rows that were inserted first.
  > Insertion order is not preserved or promised by the relational model.
- [o] An arbitrary 10 rows, which may differ between runs of the same query.
  > Without \`ORDER BY\` there is no defined order, so the engine is free to return whichever 10 rows are cheapest. "Top 10" always needs an explicit sort.
- The 10 rows with the smallest primary key.
  > Primary-key order is a plausible physical outcome on some engines, never a guarantee.
- An error, because \`LIMIT\` requires \`ORDER BY\`.
  > The combination is legal, which is exactly why the bug ships.`}

<MultipleChoice
  markdown={`\`WHERE created_at >= '2026-01-01' AND created_at <= '2026-01-31'\` on a timestamp column. What does it miss?

- Nothing; the range covers all of January.
  > It covers the days but not the hours inside the last one.
- [o] Everything after midnight on 31 January, because the bare date is read as \`2026-01-31 00:00:00\`.
  > A whole final day is silently dropped. The safe pattern is a half-open range: \`>= '2026-01-01' AND < '2026-02-01'\`.
- Rows from 1 January, because the lower bound is exclusive.
  > \`>=\` includes the boundary, so the first day is fine.
- Rows where \`created_at\` is \`NULL\`, which should have been included.
  > \`NULL\` timestamps are excluded, but that is standard comparison behavior rather than the date-range bug.`}
/>

<MultipleChoice
  markdown={`Which is the correct way to express "customers whose name is missing"?

- \`WHERE name = ''\`
  > An empty string is a known value that happens to be empty, which is a different state from unknown.
- [o] \`WHERE name IS NULL\`
  > \`IS NULL\` is the only predicate that tests for the unknown marker. If the source can produce both, \`name IS NULL OR name = ''\` covers them.
- \`WHERE name = NULL\`
  > This evaluates to \`NULL\` for every row and therefore matches nothing.
- \`WHERE NOT name\`
  > Applying \`NOT\` to a text column is a type error on most engines.`}

<MultipleChoice
  markdown={`What is a CTE, and what does it buy you over a nested subquery?

- It materializes a permanent table you can query later.
  > A CTE lives only for the duration of the statement; a permanent table needs \`CREATE TABLE\`.
- [o] A named, inline result set defined with \`WITH\`, which reads top-to-bottom and can be referenced more than once in the same query.
  > The gain is readability and reuse. Whether it is materialized or inlined is an optimizer decision that varies by engine.
- It always runs faster than the equivalent subquery.
  > Most engines treat the two the same, and a materialized CTE can occasionally be slower.
- It lets you skip the \`GROUP BY\` clause.
  > Grouping is unaffected by how the query is structured.`}
/>

<MultipleChoice
  markdown={`\`SELECT AVG(rating) FROM reviews\` returns \`4\` when you expected \`4.33\`. What is the likely cause?

- \`AVG\` rounds to the nearest whole number by design.
  > \`AVG\` returns the true mean; the rounding comes from the type it was given.
- [o] \`rating\` is an integer column, so the division is integer division on some engines.
  > Cast first: \`AVG(rating * 1.0)\` or \`AVG(CAST(rating AS DECIMAL))\`. The same trap turns a conversion rate into \`0\`.
- The column contains \`NULL\`s, which \`AVG\` counts as zero.
  > \`AVG\` skips \`NULL\`s entirely rather than treating them as zero.
- \`AVG\` requires an \`ORDER BY\` to be accurate.
  > Ordering has no bearing on an average.`}

## Advanced SQL

<MultipleChoice
  markdown={`Sales are \`90, 85, 85, 80\` ordered descending. Which ranking function leaves a **gap** after the tie?

- \`ROW_NUMBER()\`
  > \`ROW_NUMBER\` assigns \`1, 2, 3, 4\` with no gaps and no shared values, breaking the tie arbitrarily.
- [o] \`RANK()\`
  > \`RANK\` gives \`1, 2, 2, 4\`: tied rows share a rank and the next rank skips ahead by the number of tied rows.
- \`DENSE_RANK()\`
  > \`DENSE_RANK\` gives \`1, 2, 2, 3\`, sharing the rank but continuing without a gap.
- \`NTILE(4)\`
  > \`NTILE\` distributes rows into a fixed number of buckets rather than ranking them.`}
/>

<MultipleChoice
  markdown={`What is the default window frame when \`OVER\` includes an \`ORDER BY\` but no explicit frame clause?

- \`ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW\`
  > Close, but the default is \`RANGE\`, not \`ROWS\`, and the difference shows up whenever the ordering column has ties.
- [o] \`RANGE BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW\`
  > With \`RANGE\`, "current row" means every peer sharing the same \`ORDER BY\` value, so tied rows all see the same running total.
- The whole partition, unbounded in both directions.
  > That is the default only when \`OVER\` has *no* \`ORDER BY\` at all, which is why \`SUM(x) OVER (PARTITION BY r)\` gives a grand total per partition.
- One row before and one row after the current row.
  > A three-row sliding frame has to be requested explicitly with \`ROWS BETWEEN 1 PRECEDING AND 1 FOLLOWING\`.`}
/>

<MultipleChoice
  markdown={`In \`LAG(revenue, 1) OVER (PARTITION BY region ORDER BY day)\`, what does the **first** row of each region return?

- The last row's value, wrapping around the partition.
  > Window functions do not wrap; there is simply no preceding row.
- [o] \`NULL\`, because there is no previous row in that partition.
  > Supply a third argument to substitute a default, e.g. \`LAG(revenue, 1, 0)\`.
- \`0\`.
  > \`0\` appears only if it is passed explicitly as the default argument.
- The first row's own value.
  > \`LAG(x, 0)\` would return the current row's value; an offset of \`1\` looks strictly backwards.`}
/>

<MultipleChoice
  markdown={`You want to label each customer by spending quartile. Which window function fits?

- \`RANK()\`
  > \`RANK\` produces a position per customer, not a bucket label, and its range grows with the row count.
- [o] \`NTILE(4)\`
  > \`NTILE(n)\` splits the ordered partition into \`n\` buckets of near-equal size and returns the bucket number, which is exactly a quartile label at \`n = 4\`.
- \`PERCENT_RANK()\`
  > \`PERCENT_RANK\` returns a continuous value between 0 and 1, which then still needs bucketing.
- \`ROW_NUMBER()\`
  > \`ROW_NUMBER\` numbers rows sequentially; turning that into quartiles means dividing by the partition count by hand.`}
/>

<MultipleChoice
  markdown={`\`LAST_VALUE(price) OVER (PARTITION BY sku ORDER BY day)\` keeps returning the current row's price instead of the final one. What fixes it?

- Swap \`ORDER BY day\` for \`ORDER BY day DESC\`.
  > Reversing the order makes it return the *earliest* price instead, trading one wrong answer for another.
- [o] Add \`ROWS BETWEEN UNBOUNDED PRECEDING AND UNBOUNDED FOLLOWING\`.
  > The default frame ends at the current row, so "last value so far" is the current row. Widening the frame to the whole partition makes \`LAST_VALUE\` mean what it looks like it means.
- Replace it with \`MAX(price)\`.
  > \`MAX\` returns the largest price, which coincides with the last one only by accident.
- Remove the \`PARTITION BY\`.
  > Dropping the partition changes the grouping and leaves the frame problem untouched.`}
/>

<MultipleChoice
  markdown={`Which clause lets you filter directly on a window function's result, without wrapping the query in a subquery?

- \`HAVING\`
  > \`HAVING\` filters \`GROUP BY\` aggregates, and it runs before window functions are computed.
- [o] \`QUALIFY\`
  > \`QUALIFY\` runs after window functions, so \`QUALIFY ROW_NUMBER() OVER (...) = 1\` works directly. It is available in DuckDB, Snowflake, BigQuery, and Teradata, though not in Postgres or MySQL.
- \`WHERE\`
  > \`WHERE\` is evaluated before window functions exist, which is why referencing one there raises an error.
- \`FILTER\`
  > The \`FILTER (WHERE ...)\` modifier restricts which rows feed an aggregate; it does not filter the output rows.`}
/>

<MultipleChoice
  markdown={`Which frame computes a **7-day moving average** over one row per day?

- \`ROWS BETWEEN 7 PRECEDING AND CURRENT ROW\`
  > That spans 8 rows: the 7 preceding ones plus the current one.
- [o] \`ROWS BETWEEN 6 PRECEDING AND CURRENT ROW\`
  > Six preceding rows plus the current row is a 7-row window, which is a 7-day average when the data has exactly one row per day.
- \`ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW\`
  > An unbounded start gives a cumulative average over all history rather than a fixed 7-day window.
- \`ROWS BETWEEN 3 PRECEDING AND 3 FOLLOWING\`
  > This is a 7-row *centered* window, which peeks at future days. It smooths well for a retrospective chart but is not the trailing average usually meant.`}
/>

<MultipleChoice
  markdown={`What are the two required parts of a recursive CTE?

- A \`GROUP BY\` and a \`HAVING\` clause.
  > Grouping is unrelated to recursion; a recursive CTE is defined by its self-reference.
- [o] An anchor member that seeds the result, and a recursive member that references the CTE, combined with \`UNION ALL\`.
  > The anchor runs once, then the recursive member re-runs against the previous iteration's rows until it returns none. A termination condition is what keeps it finite.
- A window function and a frame clause.
  > Window functions walk one result set; they cannot feed their own output back in.
- Two separate CTEs joined together.
  > Joining two ordinary CTEs traverses exactly one level, which is what recursion exists to avoid hard-coding.`}
/>

<MultipleChoice
  markdown={`What does \`SUM(amount) OVER (PARTITION BY region)\` return, with no \`ORDER BY\` inside the \`OVER\`?

- A running total that resets at each region.
  > A running total requires an \`ORDER BY\`, which is what narrows the default frame to "up to the current row".
- [o] The region's grand total, repeated on every row of that region.
  > With no \`ORDER BY\` the frame is the entire partition, which makes this the standard way to put a group total beside each row without a join.
- The overall total across all regions.
  > \`PARTITION BY\` restricts each row's window to its own region.
- One row per region, like \`GROUP BY\`.
  > A window function preserves the input rows; it never collapses them.`}

<MultipleChoice
  markdown={`Which pattern returns the top 3 products **per category**?

- \`ORDER BY category, sales DESC LIMIT 3\`
  > \`LIMIT\` applies to the whole result, so this returns 3 rows in total rather than 3 per category.
- [o] \`ROW_NUMBER() OVER (PARTITION BY category ORDER BY sales DESC)\` in a subquery, filtered to \`<= 3\` outside it.
  > Numbering restarts inside each category, and the filter has to sit outside the window's own \`SELECT\` (or in \`QUALIFY\`, where it exists).
- \`GROUP BY category HAVING COUNT(*) <= 3\`
  > This filters categories by how many products they have, and returns no product rows at all.

<MultipleChoice
  markdown={`What is the difference between \`ROWS\` and \`RANGE\` in a window frame?

- \`ROWS\` works only on integers; \`RANGE\` works on any type.
  > Both accept the same ordering types; the difference is in what a frame boundary means.
- [o] \`ROWS\` counts physical rows; \`RANGE\` includes every row whose \`ORDER BY\` value ties with the boundary.
  > On a column with duplicates the two give different answers, which is why an explicit \`ROWS\` frame is the safer default for a running total.
- \`RANGE\` is always faster because it scans fewer rows.
  > \`RANGE\` often costs more, since it has to identify the full set of peers.
- They are synonyms kept for backwards compatibility.
  > They are distinct semantics, and mixing them up is a classic source of off-by-a-few totals.`}
/>

<MultipleChoice
  markdown={`How do you compute each row's percentage of its group total in one pass?

- Group the table, then join the totals back on the key.
  > The result is right, but it is the multi-step version of what one window function does inline.
- [o] \`amount * 100.0 / SUM(amount) OVER (PARTITION BY region)\`
  > The window supplies the denominator per region without collapsing the rows. The \`100.0\` also avoids integer division.
- \`amount * 100.0 / SUM(amount)\`
  > A bare \`SUM\` is an aggregate, so this needs a \`GROUP BY\` and would not leave the individual rows in place.
- \`PERCENT_RANK() OVER (PARTITION BY region ORDER BY amount)\`
  > \`PERCENT_RANK\` reports relative position in the ordering, not share of the total.`}
/>

<MultipleChoice
  markdown={`\`day_over_day = revenue - LAG(revenue) OVER (ORDER BY day)\` returns \`NULL\` for scattered rows in the middle of the series. Why?

- \`LAG\` cannot be used in an arithmetic expression.
  > It returns an ordinary value and composes freely.
- [o] Those days have a \`NULL\` \`revenue\`, and any arithmetic involving \`NULL\` yields \`NULL\`.

- The \`ORDER BY\` inside \`OVER\` is being ignored.

<MultipleChoice

<MultipleChoice
  markdown={`You need each row to carry its group's mean alongside the original values, with the DataFrame shape unchanged. Which groupby method fits?

- \`agg\`
  > \`agg\` collapses each group to one row, so it would have to be merged back on the key afterwards.
- [o] \`transform\`

<MultipleChoice

  > A flat overall retention number can hide steadily worsening new-user retention, masked by a growing share of long-tenured users.
- Which individual users are most valuable.
  > That is user-level scoring, not cohorting.
- Whether the metric is statistically significant.
  > Significance needs a comparison and a test; cohorting is descriptive.`}
/>

<MultipleChoice
  markdown={`A test needs 20,000 users per arm but traffic only allows 6,000. What is the honest response?

- Run it anyway and read the direction of the result.
  > An underpowered test mostly returns noise, and any "significant" result it does produce is inflated in magnitude.
- [o] Say up front that the test can only detect a much larger effect, then either run longer, pick a more sensitive metric, or accept that a small effect will be undetectable.
  > Stating the detectable effect before launch is what stops an inconclusive result from being read as "no effect".
- Lower the significance threshold to 0.10 to compensate.
  > Loosening the threshold buys power by accepting more false positives; it does not add information.
- Split the traffic 90/10 to concentrate the sample.
  > An unbalanced split lowers power for a fixed total, though it is useful when exposure risk matters more than power.`}
/>

## Data visualization

<MultipleChoice
  markdown={`What distinguishes a histogram from a bar chart?

- A histogram is drawn horizontally; a bar chart is drawn vertically.
  > Orientation is a styling choice available to both.
- [o] A histogram bins one continuous variable to show its distribution, so its bars are adjacent; a bar chart compares discrete categories, so its bars are separated.
  > The gap between bars is a real signal: it says the x-axis is categorical, and that reordering the bars loses no information.
- A histogram can only display counts, while a bar chart can display any measure.
  > A histogram can show density or relative frequency as well as raw counts.
- They are the same chart under two names.
  > They answer different questions: "how is this variable distributed?" versus "how do these categories compare?"`}
/>

<MultipleChoice
  markdown={`You are plotting daily revenue over 24 consecutive months. Which encoding reads best?

- A pie chart, one slice per month.
  > A pie chart destroys the time ordering and asks the reader to compare 24 angles.
- [o] A line chart, with time on the x-axis.
  > A connected line encodes ordering and rate of change, which is what a time series is read for.
- A scatter plot with no connecting line.
  > Points alone are readable but leave the reader to reconstruct the sequence that the line makes obvious.
- A stacked area chart of each month's share.
  > Stacked areas answer a composition question; here there is only one series to show.`}
/>

<MultipleChoice
  markdown={`When is a pie chart a defensible choice?

- Whenever the values are percentages.
  > Percentages alone do not make a pie readable; the number of slices and the size differences do.
- [o] For a part-to-whole breakdown with only a few slices whose sizes differ clearly.
  > Angles are hard to compare precisely, so a pie survives two or three obviously different parts and fails once slices are numerous or similar.
- For comparing the same category across several time periods.
  > Change over time belongs on a line or a grouped bar chart.
- For showing the distribution of a continuous variable.
  > Distributions call for a histogram, a box plot, or a density plot.`}
/>

<MultipleChoice
  markdown={`What is the main risk of a dual-axis chart plotting revenue and support tickets together?

- Dual axes cannot be rendered by most BI tools.
  > Nearly every tool supports them; the problem is interpretive rather than technical.
- [o] The two axis ranges are chosen independently, so the apparent relationship between the series can be manufactured by rescaling.
  > Two lines can be made to cross, converge, or diverge purely by moving an axis. Small multiples or an indexed view make the comparison honest.
- The chart can only show two series.
  > Series count is a readability limit, not the specific hazard of dual axes.
- Dual axes always require a logarithmic scale.
  > Log scaling is an independent choice that applies to single-axis charts too.`}
/>

<MultipleChoice
  markdown={`What does maximizing the data-ink ratio mean in practice?

- Using the brightest colors available so the data stands out.
  > Saturated color everywhere adds ink without adding information, and it makes real highlights harder to see.
- [o] Removing decoration that carries no information, such as heavy gridlines, 3-D effects, and background fills, so the remaining ink encodes data.
  > Tufte's principle: every mark should earn its place. Careful subtraction usually makes a chart more legible, not less.
- Printing at the highest resolution the display allows.
  > Resolution is a rendering concern, unrelated to how much of the ink is data.
- Packing as many series onto one chart as will fit.
  > Crowding raises ink and lowers legibility, which is the opposite of the intent.`}
/>

<MultipleChoice
  markdown={`What is the practical difference between a dashboard and a report?

- A dashboard is interactive; a report is always static.
  > Interactivity is common in dashboards but is not what separates them; plenty of reports are interactive.
- [o] A dashboard monitors a small set of metrics continuously and prompts a question; a report answers one specific question at a point in time, with narrative and caveats.
  > This is why a dashboard is refreshed and a report is dated: one is for noticing that something changed, the other for explaining why.
- A dashboard is built by engineers; a report is written by analysts.
  > Both are ordinary analyst deliverables.
- A report can contain charts, while a dashboard shows only numbers.
  > Both use whatever visual encoding the question needs.`}
/>

<MultipleChoice
  markdown={`You are shading a map by average order value per region. Which palette fits?

- A categorical palette with one distinct hue per region.
  > Distinct hues imply unordered categories and hide the fact that the values run low to high.
- [o] A sequential palette running light to dark in a single hue.
  > A sequential ramp encodes magnitude with lightness, which is the ordering the reader needs to see.
- A diverging palette centered on zero.
  > A diverging palette is right when a meaningful midpoint exists, such as change versus last year; a plain average has no natural center.
- A rainbow palette across the full spectrum.
  > Rainbow ramps are not perceptually uniform: they create false boundaries where the hue shifts quickly and hide real differences where it does not.`}
/>

<MultipleChoice
  markdown={`You need to show the distribution of order values for four regions side by side. Which chart fits best?

- Four pie charts, one per region.
  > A pie shows composition, not the spread of a continuous variable.
- [o] A box plot (or violin) per region on a shared axis.
  > Median, spread, and outliers are all visible for each region at once, on a common scale.
- A stacked bar chart of total revenue per region.
  > A stacked bar answers a totals question and says nothing about how the values are spread.
- A single scatter plot of order value against region.
  > A strip plot is defensible, but with many orders it becomes an unreadable vertical smear.`}
/>

<MultipleChoice
  markdown={`When are small multiples the better choice over one chart with many overlaid lines?

- Never; a single chart is always more compact.
  > Compactness stops helping once the lines are indistinguishable.
- [o] When several series overlap enough that individual lines cannot be traced, and the reader mainly needs each series' shape.
  > A grid of small panels on a shared scale trades precise cross-series comparison for readability. Overlay stays better when the comparison *is* the point and there are only a few series.
- Whenever the data is time-based.
  > Two or three time series overlay perfectly well.
- Only when the series have different units.
  > Different units are a reason to avoid a shared axis, but small multiples help with same-unit clutter too.`}
/>

<MultipleChoice
  markdown={`What is the main problem with sorting a bar chart of categories alphabetically?

- Alphabetical order is harder for readers to scan.
  > Alphabetical helps for lookup; the problem is what it costs elsewhere.
- [o] It scatters the ranking, so the reader has to compare bar lengths manually instead of reading the order off the chart.
  > Sorting by value makes the largest and smallest obvious instantly. Keep a fixed order only when the categories have an inherent one, or when several charts must stay comparable.
- Bar charts cannot be sorted.
  > Sorting is a standard operation in every charting library.
- It requires a categorical color palette.
  > Color is an independent choice; most bar charts need only one.`}
/>

<MultipleChoice
  markdown={`Which is the strongest argument for direct-labelling lines instead of using a legend?

- Legends are not supported on mobile.
  > Legends render fine; they just cost more effort to use.
- [o] It removes the back-and-forth of matching a color swatch to a line, putting the name where the reader's eye already is.
  > It also survives readers who cannot distinguish the palette's colors, which a color-only legend does not.
- Direct labels let you fit more series on one chart.
  > More series makes labelling harder, not easier — labels start colliding.
- Legends are only for bar charts.
  > Legends are used across every chart type.`}
/>

<MultipleChoice
  markdown={`A stakeholder asks for "everything we know" on one dashboard. What is the better response?

- Build it as asked; more information is strictly better.
  > Past a point, more panels lower the chance any single one gets read.
- [o] Ask what decisions the dashboard should support, then build for those and link the rest as detail.
  > A dashboard's job is to make a small number of things impossible to miss. "Everything" guarantees nothing stands out.
- Refuse, since dashboards should never exceed five charts.
  > A fixed cap is arbitrary; the right number follows from the decisions being supported.
- Build two dashboards, one for each audience, without asking.
  > Splitting before understanding the need risks maintaining two unused dashboards.`}
/>

## Excel & spreadsheets

<MultipleChoice
  markdown={`What does \`XLOOKUP\` improve over both \`VLOOKUP\` and \`INDEX\`/\`MATCH\`?

- It is the only one of the three that can search a sorted range.
  > All three support sorted-range lookups; \`VLOOKUP\` has done so since the beginning.
- [o] It takes the lookup and return ranges directly, searches in either direction, defaults to an exact match, and has a built-in "if not found" argument.
  > It removes the column-offset counting that makes \`VLOOKUP\` fragile, and the two-function pairing that makes \`INDEX\`/\`MATCH\` verbose.
- It recalculates faster on very large workbooks.
  > Performance is broadly comparable; the gain is in correctness and readability.
- It can return several columns at once, which the others cannot.
  > \`XLOOKUP\` can spill a multi-column result, but \`INDEX\` can return a multi-cell range too. The defining improvements are the interface ones.`}
/>

<MultipleChoice
  markdown={`Which argument order is correct?

- \`SUMIFS(criteria_range, criteria, sum_range)\`
  > That is \`SUMIF\`'s order, and reusing it in \`SUMIFS\` is the classic mistake.
- [o] \`SUMIFS(sum_range, criteria_range1, criteria1, ...)\`
  > \`SUMIFS\` puts the range being summed **first**, then repeating criteria pairs, precisely because the number of pairs varies.
- \`SUMIFS(criteria1, criteria_range1, sum_range)\`
  > The criterion never comes before the range it applies to.
- The order is interchangeable as long as the ranges are the same size.
  > Spreadsheet functions match arguments by position, so the order is what gives each range its meaning.`}
/>

<MultipleChoice
  markdown={`A model wraps every lookup in \`IFERROR(..., 0)\`. What is the risk?

- \`IFERROR\` slows recalculation noticeably.
  > Any cost is negligible next to the correctness problem.
- [o] It hides genuine problems: a broken reference, a typo in a key, or a missing row all silently become \`0\`.
  > Totals stay plausible while quietly under-counting. Prefer \`IFNA\`, which catches only "not found", and leave real errors visible.
- \`IFERROR\` cannot be nested inside other functions.
  > It nests freely; that is part of how it spreads through a workbook.
- It converts numbers to text.
  > The fallback value keeps whatever type it was given.`}
/>

<MultipleChoice
  markdown={`A formula in \`C2\` contains \`B$2\`. It is copied down to \`C3\` and right to \`D2\`. What does the reference become in each copy?

- \`B$3\` in \`C3\`, and \`B$2\` in \`D2\`.
  > The dollar sign is on the row, so it is the *row* that is pinned; the column is free to move.
- [o] \`B$2\` in \`C3\`, and \`C$2\` in \`D2\`.
  > \`$\` locks whatever immediately follows it. In \`B$2\` the row is locked and the column is relative, so copying down changes nothing and copying right advances the column.
- \`B$2\` in both copies.
  > That would be \`$B$2\`, with both parts locked.
- \`B3\` in \`C3\`, and \`C2\` in \`D2\`.
  > That is the behavior of the fully relative \`B2\`, with no lock at all.`}
/>

<MultipleChoice
  markdown={`\`VLOOKUP\` is called without its fourth argument. What happens?

- It performs an exact match, which is the default.
  > The default is the other way around, which is why the omission is dangerous.
- [o] It defaults to approximate match, which requires the lookup column to be sorted ascending and otherwise returns a wrong value silently.
  > Always pass \`FALSE\` (or \`0\`) for exact matching. An approximate match on unsorted data returns a neighbouring row's value instead of an error.
- It raises \`#N/A\` because the argument is required.
  > The argument is optional, so nothing signals that it was left out.
- It returns the first row of the range.
  > It returns whichever row the approximate search lands on, which varies with the data.`}
/>

<MultipleChoice
  markdown={`A date cell shows \`45,000\` after the format is cleared. Why?

- The date was corrupted by an import.
  > The underlying value is intact; only its display changed.
- [o] Spreadsheets store dates as serial numbers counting days from a fixed epoch, and the visible date is a display format over that number.
  > Because dates are numbers, arithmetic works directly: subtracting two dates gives a day count, and adding \`7\` moves forward a week.
- The cell holds text that happens to look numeric.
  > Text would stay left-aligned as typed rather than becoming a number.
- Dates are stored as seconds, so the value is a timestamp.
  > The unit is days; the fractional part carries the time of day.`}
/>

<MultipleChoice
  markdown={`Lookups against a pasted list keep returning \`#N/A\` even though the keys look identical on screen. What should you check first?

- Whether the workbook needs a full recalculation.
  > Recalculation would resolve stale results, not values that look right and still fail to match.
- [o] Trailing or leading whitespace and non-breaking spaces in the keys, which \`TRIM\` and \`CLEAN\` remove.
  > \`"ACME "\` and \`"ACME"\` are different strings, and the difference is invisible. A mismatched type, text \`"1001"\` versus the number \`1001\`, causes the same symptom.
- Whether the lookup range is sorted.
  > Sorting matters only for approximate match, and it would return a wrong value rather than \`#N/A\`.
- Whether the two lists have the same number of rows.
  > Row counts do not have to match for a lookup to find its key.`}
/>

<MultipleChoice
  markdown={`What does a pivot table's "Values" area do with a text field dropped into it?

- It concatenates the text values.
  > Spreadsheets offer no concatenating aggregation in a pivot's Values area.
- [o] It falls back to \`Count\`, because the other aggregations need numbers.
  > This is why a pivot that should show revenue sometimes shows a row count instead: the underlying column is text, usually because of a stray currency symbol or a thousands separator.
- It raises an error.
  > It silently picks \`Count\`, which is what makes the mistake easy to ship.
- It shows the first value found.
  > No aggregation returns a single arbitrary value in that area.`}
/>

<MultipleChoice
  markdown={`Your pivot table shows a total of 40,000 but the source now holds 60,000 rows. What is the most likely cause?

- Pivot tables cap out at 40,000 rows.
  > No such limit exists at that size.
- [o] The pivot's source range is a fixed range that never grew with the data, so it needs refreshing over a table or a dynamic range.
  > Basing the pivot on a named table means new rows are picked up on refresh instead of silently excluded.
- The extra rows contain errors and were skipped.
  > Error values would show up as their own category rather than vanish.
- The pivot is filtered to the current month.
  > A filter is possible, but a stale source range is by far the more common cause of a round shortfall.`}
/>

<MultipleChoice
  markdown={`What does \`COUNTA\` count that \`COUNT\` does not?

- Nothing; they are aliases.
  > They differ precisely in which cell contents qualify.
- [o] Any non-empty cell, including text and error values, whereas \`COUNT\` counts numbers only.
  > \`COUNTBLANK\` is the complement. A gap between the two is a fast way to spot numbers stored as text.
- Only cells containing formulas.
  > Neither function distinguishes a formula from a typed value; only the result matters.
- Cells with conditional formatting applied.
  > Formatting is invisible to both.`}
/>

<MultipleChoice
  markdown={`Which is the strongest sign that an analysis should move from a spreadsheet into SQL?

- The file has more than ten sheets.
  > Sheet count alone says little about whether the work belongs in a database.
- [o] The same manual refresh steps are repeated on a schedule against data that already lives in a database.
  > Repeated manual steps against a queryable source is the case where a spreadsheet costs the most: every refresh is a chance to make a new mistake, and none of it is reviewable.
- Someone asked for a chart the spreadsheet cannot draw.
  > A charting gap is usually solved by a BI tool rather than by moving the data.
- The workbook contains \`VLOOKUP\` formulas.
  > Lookups are ordinary spreadsheet work and fine at small scale.`}
/>

<MultipleChoice
  markdown={`A shared workbook's numbers differ depending on who opens it. What should you suspect first?

- Different Excel versions round differently.
  > Arithmetic is consistent across supported versions.
- [o] Volatile or environment-dependent functions such as \`TODAY\`, \`NOW\`, \`RAND\`, or a locale-sensitive date parse.
  > These recalculate per session and per locale, so "as of today" logic quietly shifts under each reader. Pinning the reporting date in a cell makes the workbook reproducible.
- The file is corrupt.
  > Corruption usually fails loudly rather than yielding two plausible sets of numbers.
- Someone left a filter applied.
  > A filter changes what is *displayed*, but formula results stay the same for everyone.`}
/>

<MultipleChoice
  markdown={`What is the practical difference between a spreadsheet's \`SUMPRODUCT\` and a plain \`SUM\`?

- \`SUMPRODUCT\` is faster on large ranges.
  > It usually costs more, since it evaluates arrays element by element.
- [o] \`SUMPRODUCT\` multiplies corresponding elements of several ranges before summing, which also makes it a way to sum under multiple conditions.
  > \`SUMPRODUCT((region="North")*(qty>10)*amount)\` predates \`SUMIFS\` and still handles conditions \`SUMIFS\` cannot express.
- \`SUMPRODUCT\` ignores text values while \`SUM\` errors on them.
  > \`SUM\` skips text in a range too.
- They differ only in argument order.
  > They compute different things: one sums, the other sums products.`}
/>
