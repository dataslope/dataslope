Analytics Engineer interviews assume working knowledge of **dbt**. These
concept checks cover the pieces that come up most.

## Materializations

<MultipleChoice
  markdown={`A dbt model is queried constantly by dashboards and is expensive to compute, but its source data only updates nightly. Which materialization is the best default?

- \`view\`
  > A view re-runs the model's SQL on every query — fine for cheap models, but it pushes the expensive computation onto every dashboard load.
- [o] \`table\`
  > Materializing as a table computes it once per \`dbt run\` (nightly here) and serves fast reads all day — the right trade-off for an expensive, frequently-read, slowly-changing model.
- \`ephemeral\`
  > Ephemeral models are inlined as CTEs into downstream models and aren't queryable on their own, so dashboards can't read them.
- It doesn't matter; they perform identically.
  > Materializations have very different read/compute trade-offs — choosing well is a core AE skill.`}
/>

## ref() and source()

<MultipleChoice
  markdown={`Why reference an upstream model with \`{{ ref('stg_orders') }}\` instead of hardcoding the schema-qualified table name?

- It runs the query faster.
  > \`ref\` doesn't change runtime performance; it changes how dbt builds and wires the project.
- [o] dbt builds the dependency graph (DAG) from \`ref\`/\`source\`, so it knows build order and can manage environments — hardcoded names break that.
  > \`ref\` is how dbt learns "this model depends on that one," enabling correct run ordering, lineage, and dev/prod schema swapping.
- It lets you skip writing tests.
  > Testing is orthogonal to \`ref\`; you still declare tests separately.
- It converts the model to a view automatically.
  > \`ref\` has nothing to do with materialization choice.`}
/>

## Tests

<MultipleChoice
  markdown={`In dbt, what does a built-in \`unique\` + \`not_null\` test on a model's \`id\` column give you?

- It deduplicates the column automatically during the run.
  > dbt tests **assert** conditions; they don't modify data. A failing test surfaces the problem for you to fix upstream.
- [o] A check that fails the run/flags an issue if \`id\` has duplicates or nulls — guarding the model's grain and key integrity.
  > These schema tests validate assumptions (here, that \`id\` is a valid primary key) and fail loudly when the data violates them.
- A guarantee the source system can never produce bad data.
  > Tests catch bad data after the fact; they can't constrain the source.
- A performance index on \`id\`.
  > Tests aren't indexes; they don't change physical storage or query plans.`}
/>
