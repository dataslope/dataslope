## Advanced SQL

<MultipleChoice
  markdown={`How does a window function differ from a \`GROUP BY\` aggregate?

- It can only be used on numeric columns.
  > Ranking and offset functions work on any orderable type.
- [o] It computes per row without collapsing the rows.
  > \`GROUP BY\` collapses each group to one row; a window leaves every input row in place. That is why a window can put a group total beside each detail row without a self-join.
- It always runs faster.
  > Windows often cost more, since they sort or hash-partition the input.
- It removes any need for a \`WHERE\` clause in the query.
  > Row filtering is unrelated and still happens before windows are computed.`}
/>

<MultipleChoice
  markdown={`What are the three parts of an \`OVER\` clause?

- \`SELECT\`, \`FROM\`, and \`WHERE\`.
  > Those are query clauses, not components of a window specification.
- [o] \`PARTITION BY\`, \`ORDER BY\`, and the frame clause.
  > They set which rows share a window, their order inside it, and which of them the function sees. All three are optional. Omitting them all gives one window over the entire result set.
- \`PARTITION BY\`, \`GROUP BY\`, and \`HAVING\`.
  > \`GROUP BY\` and \`HAVING\` belong to aggregation, and cannot appear inside \`OVER\`.
- The function name, the column it reads, and the output alias.
  > Those sit outside the \`OVER\` clause.`}
/>

<MultipleChoice
  markdown={`Values ordered descending are \`100, 90, 90, 80\`. What do \`ROW_NUMBER\`, \`RANK\`, and \`DENSE_RANK\` return for the \`80\`?

- \`4\`, \`4\`, and \`4\`, all three agreeing.
  > Only \`ROW_NUMBER\` and \`RANK\` agree here; \`DENSE_RANK\` does not skip.
- [o] \`4\`, \`4\`, \`3\`.
  > \`ROW_NUMBER\` numbers rows \`1,2,3,4\`; \`RANK\` gives \`1,2,2,4\`, skipping past the tie; \`DENSE_RANK\` gives \`1,2,2,3\`.
- \`3\`, \`3\`, \`3\`.
  > Four rows means the last \`ROW_NUMBER\` is 4, whatever the ties do.
- \`4\`, \`3\`, \`3\`.
  > \`RANK\` leaves a gap after a tie, so it reaches 4 rather than 3.`}
/>

<MultipleChoice
  markdown={`Which pattern deduplicates to the latest record per key, keeping the whole row?

- \`SELECT DISTINCT key, MAX(updated_at) ... GROUP BY key\`, taking the newest timestamp.
  > This returns the key and timestamp but loses the rest of the winning row's columns.
- [o] \`ROW_NUMBER() OVER (PARTITION BY key ORDER BY updated_at DESC)\` filtered to \`= 1\`.
  > The full row survives. \`RANK\` would return several rows per key whenever timestamps tie, which is why \`ROW_NUMBER\` is the safe choice.
- \`SELECT DISTINCT *\`
  > \`DISTINCT *\` removes only rows that are identical in every column, which is a different problem.
- \`GROUP BY key ORDER BY updated_at DESC LIMIT 1\`
  > \`LIMIT\` applies to the whole result, leaving one row overall.`}
/>

<MultipleChoice
  markdown={`What does \`QUALIFY\` do?

- It qualifies a column reference with its table alias.
  > Qualification in that sense is just dotted naming, not a clause.
- [o] It filters on the result of a window function.
  > That happens after \`SELECT\` has computed them. \`WHERE\` runs before windows exist and \`HAVING\` filters group aggregates, so \`QUALIFY\` fills the gap. DuckDB, Snowflake, BigQuery, and Teradata support it; Postgres and MySQL do not.
- It enforces a column's data type.
  > Type enforcement is done by the schema or a cast.
- It is a synonym for \`HAVING\`.
  > \`HAVING\` cannot reference a window function.`}
/>

<MultipleChoice
  markdown={`Which of these is the strongest reason to prefer a CTE over a nested subquery?

- CTEs always execute faster.
  > Most engines optimize both similarly, and a materialized CTE can be slower.
- [o] It is named, reads top-to-bottom, and can be reused.
  > Referencing it more than once in the same statement is the part a subquery cannot match. Readability is the real argument, and it matters when the model is going to be reviewed and maintained.
- CTEs can reference tables that plain subqueries cannot.
  > Both see the same objects.
- Only CTEs can be used with window functions.
  > Window functions work in either.`}
/>

<MultipleChoice
  markdown={`What does a recursive CTE need in order to terminate?

- A \`LIMIT\` clause.
  > \`LIMIT\` caps output but does not stop the recursion from running.
- [o] A recursive member whose filter eventually returns no rows.
  > The anchor seeds the result and the recursive member runs against the previous iteration until it yields nothing. A hierarchy with a cycle will loop forever without a visited-path guard or a depth cap.
- A \`GROUP BY\` on the recursive member.
  > Grouping is unrelated to termination.
- An explicit \`MAXRECURSION\` hint, available on every engine.
  > Some engines offer such a setting, but the general answer is a filter that runs dry.`}
/>

<MultipleChoice
  markdown={`\`SUM(revenue) OVER (PARTITION BY region ORDER BY day)\` gives a climbing number, but you wanted the region total on every row. What is the fix?

- Add \`ROWS BETWEEN 1 PRECEDING AND 1 FOLLOWING\` to the frame.
  > A three-row window is narrower still, not wider.
- [o] Drop the \`ORDER BY\`, or widen the frame explicitly.
  > \`ROWS BETWEEN UNBOUNDED PRECEDING AND UNBOUNDED FOLLOWING\` covers the whole partition. Adding \`ORDER BY\` sets the default frame to "start of partition through current row", which is the definition of a running total.
- Replace \`SUM\` with \`TOTAL\`.
  > No such standard function exists.
- Move the expression into a \`HAVING\` clause.
  > \`HAVING\` cannot contain a window function, and it would filter rather than compute.`}
/>

<MultipleChoice
  markdown={`On a column with duplicate \`ORDER BY\` values, how do \`ROWS\` and \`RANGE\` frames differ?

- They give identical results in every case.
  > They coincide only when the ordering column has no ties.
- [o] \`ROWS\` counts rows; \`RANGE\` includes every tied peer.
  > So tied rows get different running totals under \`ROWS\` and share one under \`RANGE\`. \`RANGE\` is the default when an \`ORDER BY\` is present, which is why an unexplained plateau in a running total usually traces back to ties.
- \`RANGE\` cannot be used with \`SUM\`.
  > \`RANGE\` works with any window aggregate.
- \`ROWS\` requires an integer column to order the rows by.
  > \`ROWS\` counts positions and is indifferent to the column's type.`}
/>

<MultipleChoice
  markdown={`What is the cleanest way to compute month-over-month change in one query?

- Join the table to itself on \`month = month - 1\`.
  > It works, but it is more code, and month arithmetic across a year boundary is easy to get wrong.
- [o] \`revenue - LAG(revenue) OVER (ORDER BY month)\`
  > \`LAG\` reaches back one row in the ordering with no join at all. Add \`PARTITION BY\` to compute it per segment.
- \`revenue - MIN(revenue) OVER ()\`
  > This compares each month to the smallest month rather than the previous one.
- \`revenue / COUNT(*) OVER ()\`
  > This is an average per row, not a period-over-period change.`}
/>

<MultipleChoice
  markdown={`An incremental model filters with \`WHERE updated_at > (SELECT MAX(updated_at) FROM this_model)\`. What can it silently miss?

- Rows whose \`updated_at\` timestamp sits in the future.
  > Future timestamps would be picked up, not missed.
- [o] Late-arriving rows that predate the high-water mark.
  > The last run set that mark from \`updated_at\`. A lookback window (\`> max - interval '3 days'\`) plus a \`unique_key\` merge is the standard mitigation, alongside a periodic full refresh.
- Rows that were deleted at source.
  > Hard deletes are missed too, but they escape any append-style filter; the high-water mark is specifically about late arrivals.
- Nothing; the pattern is exact.
  > It is exact only if source rows always arrive in \`updated_at\` order, which they rarely do.`}
/>

<MultipleChoice
  markdown={`What is a date spine, and why generate one?

- A clustered index on a date column.
  > That is a physical storage choice, not a modelling one.
- [o] A complete, gapless list of dates to join facts against.
  > Days with no activity then appear as zero rather than vanishing. Without one, a chart of daily orders skips quiet days and a running average silently shifts.
- A dimension table that stores only the current date.
  > A single-row table cannot fill gaps.
- A partition key derived from a date.
  > Partitioning organizes storage; it does not create missing rows.`}
/>

<MultipleChoice
  markdown={`Which DuckDB expression produces one row per day for January 2026?

- \`SELECT DATE '2026-01-01' + 31\`
  > This computes a single date, not a series.
- [o] \`SELECT unnest(generate_series(DATE '2026-01-01', DATE '2026-01-31', INTERVAL 1 DAY))\`
  > \`generate_series\` returns the list and \`unnest\` expands it into rows. Postgres offers \`generate_series\` returning rows directly; BigQuery uses \`GENERATE_DATE_ARRAY\`.
- \`SELECT * FROM dates WHERE month = 1\`, against an existing dates table.
  > This assumes a dates table already exists, which is the thing being built.
- \`SELECT RANGE(31)\`
  > \`range\` yields integers, which still need converting into dates.`}
/>

<MultipleChoice
  markdown={`How do you pivot rows into columns in portable SQL?

- With the \`PIVOT\` keyword, which is part of standard SQL.
  > \`PIVOT\` exists in DuckDB, Snowflake, and SQL Server, but it is not portable.
- [o] Conditional aggregation, one \`SUM(CASE WHEN ...)\` per column.
  > Verbose, and it runs everywhere. Verbose but it runs everywhere, and it makes the grain of each output column explicit.
- With \`GROUP BY\` alone.
  > Grouping collapses rows; it cannot create new columns.
- With \`UNPIVOT\`.
  > \`UNPIVOT\` goes the other way, turning columns into rows.`}
/>

<MultipleChoice
  markdown={`How do you avoid a divide-by-zero in a ratio metric?

- Filter out rows where the denominator is zero.
  > This removes real rows from the result, which changes the answer rather than protecting it.
- [o] \`NULLIF(denominator, 0)\` in the divisor.
  > The zero becomes \`NULL\`, so the whole ratio is \`NULL\`. A \`NULL\` ratio is honest: the rate is undefined when nothing happened. Wrap in \`COALESCE\` only when zero is genuinely the right display value.
- \`CASE WHEN denominator = 0 THEN 0 ELSE n / d END\`
  > This runs, but reporting a rate of 0% when there were no trials states something the data does not support.
- Cast both sides to float.
  > Floating-point division by zero yields infinity or an error depending on the engine; the zero is still there.`}
/>

<MultipleChoice
  markdown={`Why compute a conversion rate as \`SUM(conversions) / SUM(sessions)\` rather than \`AVG(per_row_rate)\`?

- The two are algebraically identical.
  > They agree only when every row has the same denominator.
- [o] Averaging per-row rates weights every row equally.
  > A row with 2 sessions counts the same as one with 2,000, which is Simpson's paradox waiting to happen. Summing the components first produces the correctly weighted rate. This is also why ratio metrics cannot be pre-aggregated safely.
- \`AVG\` cannot be applied to a computed column at all.
  > It can; the problem is what the result means.
- \`SUM\` is faster than \`AVG\`.
  > Any speed difference is irrelevant next to the correctness one.`}
/>

<MultipleChoice
  markdown={`Why is \`COUNT(DISTINCT user_id)\` awkward in a pre-aggregated model?

- It is not supported by most warehouses.
  > Every major warehouse supports it.
- [o] Distinct counts are not additive across periods.
  > Daily distinct users cannot be summed into a monthly figure. A user active on ten days would be counted ten times. The options are recomputing from detail, or an approximate sketch such as HyperLogLog that *can* be merged.
- It always returns an approximate answer rather than exact.
  > It is exact unless an approximate function is chosen explicitly.
- It requires an index on the column.
  > Columnar warehouses do not use indexes for this at all.`}
/>

## Data warehousing

<MultipleChoice
  markdown={`What most distinguishes a modern cloud warehouse from a traditional one?

- It uses plain SQL rather than a proprietary query language.
  > Traditional warehouses were SQL systems too.
- [o] Storage and compute scale independently of each other.
  > Compute can be resized or paused without touching the data. It is what makes elastic, pay-per-query pricing possible, and why cost control becomes a modelling concern.
- It stores data as rows rather than columns.
  > Cloud warehouses are columnar; that is the direction of travel, not away from it.
- It removes the need for data modelling.
  > Cheap compute forgives some sloppiness; it does not make grain or conformance go away.`}
/>

<MultipleChoice
  markdown={`Why does \`SELECT *\` cost more in a columnar warehouse than in a row store?

- Columnar engines cannot handle \`*\` in a query whatsoever.
  > It is valid; it is just expensive.
- [o] \`*\` forfeits the ability to read only the named columns.
  > Every column is read, including the large rarely-used ones. On a 200-column table, selecting four columns can scan a small fraction of the bytes. \`*\` also defeats projection pushdown into the file format.
- \`*\` disables the result cache.
  > Caching keys on the query text; the column list is not what invalidates it.
- \`*\` forces a full sort of the table.
  > No sort is implied by the column list.`}
/>

<MultipleChoice
  markdown={`What makes partition pruning save money?

- It compresses each of the partitions more aggressively.
  > Compression is independent of pruning.
- [o] Whole partitions are skipped without ever being read.
  > A filter on the partition key is what enables it, and billed bytes drop. The saving only materializes if queries actually filter on that key, which is why the partition column should be the one people filter by, usually a date.
- It rewrites the query to use fewer joins.
  > Pruning affects what is scanned, not the join plan.
- It caches each partition in memory.
  > Caching is a separate mechanism.`}
/>

<MultipleChoice
  markdown={`How does clustering differ from partitioning?

- They are two names for the same mechanism.
  > They operate at different granularities and are often used together.
- [o] One skips whole units, the other skips blocks inside them.
  > Partitioning splits the table into physical units; clustering sorts or co-locates rows within them. Partition on a low-cardinality column such as date; cluster on the high-cardinality columns queries filter on next.
- Clustering applies only to streaming tables.
  > It applies to ordinary tables.
- Partitioning is automatic, while clustering has to be manual.
  > Both are configured deliberately, though some engines offer automatic clustering maintenance.`}
/>

<MultipleChoice
  markdown={`A dashboard query is slow and the model is rebuilt hourly from a large source. Which materialization fits?

- A view, on the grounds that it is always fresh.
  > A view re-runs the whole computation on every dashboard load, which is the slowness being described.
- [o] A table, rebuilt on the model's own schedule.
  > Readers then hit precomputed results. Freshness is bounded by the schedule, which the hourly rebuild already accepts.
- An ephemeral model.
  > Ephemeral models are inlined into their consumers as CTEs and materialize nothing, so the work still happens per query.
- A snapshot.
  > Snapshots capture history for slowly changing dimensions; they are not a performance mechanism.`}
/>

<MultipleChoice
  markdown={`When is incremental preferable to a full rebuild?

- Whenever the model grows past a million rows or thereabouts.
  > Row count alone is a poor trigger; a million-row rebuild can be trivially cheap.
- [o] When a full rebuild costs more than the added complexity.
  > The source has to be large and the new rows identifiable. Incremental buys runtime and cost at the price of an extra failure mode: silently missing late or restated rows.
- Whenever the model is used by a dashboard.
  > Who consumes the model does not determine how it is built.
- Always, since it is strictly cheaper.
  > It is cheaper per run and more expensive in correctness risk and maintenance.`}
/>

<MultipleChoice
  markdown={`What makes a rebuild idempotent?

- It runs in under a minute.
  > Speed and idempotency are unrelated.
- [o] Running it twice gives the same result as running it once.
  > It is what makes retries and backfills safe. Insert-only logic without a key breaks it; \`MERGE\` on a unique key or delete-then-insert per partition preserves it.
- It writes out to a brand new table on every run.
  > New output each run is the opposite: it leaves the consumer to work out which one is current.
- It never fails.
  > Idempotency is about what happens when you *do* re-run after a failure.`}
/>

<MultipleChoice
  markdown={`How does \`MERGE\` support idempotent upserts?

- It appends rows and deduplicates them later.
  > Deferred deduplication leaves a window in which the table is wrong.
- [o] It matches on a key, updating on a match and inserting otherwise.
  > Re-running the same batch therefore converges to the same state. The key has to be genuinely unique in the source, or a single incoming row can match several targets and the behavior becomes engine-specific.
- It locks the whole table for the duration of the load.
  > Locking is an implementation detail, not the source of idempotency.
- It only works on partitioned tables.
  > Partitioning is not required.`}
/>

<MultipleChoice
  markdown={`Why do teams still schedule periodic full refreshes of incremental models?

- To defragment the underlying storage.
  > Compaction is a real concern but a separate one.
- [o] To repair drift the incremental filter never revisited.
  > Late-arriving rows, restated source records, and logic changes all cause it. A weekly or monthly full refresh bounds how long an error can survive undetected.
- Because incremental models expire after some fixed period.
  > Nothing expires on its own.
- To refresh the documentation.
  > Docs are generated separately from model runs.`}
/>

<MultipleChoice
  markdown={`What is the core difference between OLTP and OLAP workloads?

- OLTP uses SQL, while OLAP uses a visual query builder.
  > Both are SQL systems.
- [o] Many small row operations against wide aggregate scans.
  > OLTP reads and writes individual rows; OLAP scans many rows over few columns. It is why one is row-oriented and normalized, and the other columnar and denormalized.
- OLAP systems cannot handle writes.
  > They handle bulk loads and, increasingly, updates.
- OLTP systems cannot run joins.
  > Joins are central to normalized OLTP schemas.`}
/>

<MultipleChoice
  markdown={`Which lever most reliably reduces warehouse spend?

- Switching to a smaller compute size for every workload.
  > Undersizing can make a query run so much longer that total cost rises.
- [o] Reducing the number of bytes each query scans.
  > Partition and cluster on filtered columns, select fewer columns, and materialize repeated heavy transformations once. Most warehouses bill on scanned data or on compute-seconds, and both track the volume read.
- Adding more indexes.
  > Columnar warehouses generally do not offer secondary indexes at all.
- Running everything in one large virtual warehouse.
  > Consolidation can help with idle time but also creates contention; it is not the primary lever.`}
/>

<MultipleChoice
  markdown={`What does a result cache do?

- It stores the whole physical table in memory permanently.
  > That is a different mechanism, closer to caching or persistence of data.
- [o] It returns a stored result for an identical earlier query.
  > Nothing is recomputed, as long as the underlying data has not changed. It is why re-running a dashboard query is instant and free, and why a small change in query text can suddenly cost money again.
- It caches the query plan but re-executes the scan.
  > Plan caching exists separately and does not avoid the scan.
- It applies only to views.
  > It applies to query results regardless of what they read.`}
/>

<MultipleChoice
  markdown={`In Redshift, what do distribution and sort keys control?

- Which users can read which columns.
  > Access control is unrelated.
- [o] One decides the node, the other the order within a slice.
  > Together they govern shuffle and scan cost. A distribution key matching the join key keeps joins local; a sort key matching the filter column enables zone-map skipping.
- The compression codec that gets applied to every column.
  > Encoding is configured separately per column.
- The order in which columns are returned.
  > Output column order comes from the \`SELECT\` list.`}
/>

<MultipleChoice
  markdown={`When can partitioning make things worse?

- When the table is queried frequently.
  > Frequent querying is an argument for partitioning, not against it.
- [o] When the key has very high cardinality.
  > Many tiny partitions result, and their per-file overhead outweighs the pruning benefit. Partitioning by user id or timestamp-to-the-second is the classic version of this. Date, or date plus one coarse dimension, is usually the sweet spot.
- When the table has more than 100 columns.
  > Column count is unrelated to partition strategy.
- When the data is compressed.
  > Compression and partitioning compose fine.`}
/>

<MultipleChoice
  markdown={`Why is a wide, denormalized table often preferred in a warehouse when the same shape would be wrong in an OLTP database?

- Warehouses cannot perform joins.
  > They can, and do, constantly.
- [o] Unused columns cost nothing, and joins are avoided entirely.
  > Columnar storage is what makes the first true; the second removes a class of fan-out mistakes. The trade is storage and update complexity, which matters far less in an append-mostly analytical store than in a transactional one.
- Denormalized tables are always smaller.
  > They are usually larger; compression narrows the gap but does not close it.
- Normalization is a rule that applies only to relational databases.
  > Warehouses are relational; the calculus is what differs.`}
/>

<MultipleChoice
  markdown={`What is the "small files problem"?

- Files under 1 KB are rejected by object storage.
  > No such limit exists.
- [o] Per-file open and metadata overhead dwarfs the read.
  > Thousands of tiny files are what cause it. Compaction into files of roughly 128 MB to 1 GB is the usual remedy; streaming writes and over-partitioning are the usual causes.
- Small files compress better and waste CPU on decompression.
  > Small files compress *worse*, since each has less context.
- It only affects streaming systems.
  > Over-partitioned batch outputs hit it just as hard.`}
/>

<MultipleChoice
  markdown={`What is a lakehouse, relative to a lake and a warehouse?

- A warehouse that has been moved into object storage, with no other change.
  > Storage location alone is not the distinction.
- [o] Open table formats layered over object storage.
  > Delta, Iceberg, and Hudi add ACID transactions, schema enforcement, and time travel to lake-scale files. Delta Lake, Iceberg, and Hudi are the common implementations, and they are what let one copy of the data serve both SQL and non-SQL engines.
- A data lake with a BI tool connected to it.
  > A BI connection does not add transactions or schema guarantees.
- A warehouse that only stores unstructured data.
  > The point is structured, queryable tables on lake storage.`}
/>

## dbt

<MultipleChoice
  markdown={`What does dbt actually do when you run a model?

- It moves data between systems.
  > Extraction and loading are someone else's job; dbt is the T in ELT.
- [o] It compiles SQL and runs it inside your warehouse.
  > The result is a \`CREATE TABLE AS\` or \`CREATE VIEW AS\`. The data never leaves the warehouse, which is why dbt has no processing engine of its own.
- It executes the transformation on dbt's own compute.
  > dbt Cloud runs the orchestration, never the query.
- It generates Python and runs it.
  > Python models exist on some adapters, but SQL compilation is the core.`}
/>

<MultipleChoice
  markdown={`What does \`ref()\` buy over hard-coding a schema and table name?

- Nothing; it is a style preference.
  > It is what makes the whole project work as a graph.
- [o] It resolves per environment and registers a dependency.
  > That edge is how dbt builds the DAG and orders runs. Hard-coded names build in the wrong order and silently point at production from a dev run.
- It caches the referenced table.
  > No caching is involved.
- It enforces the schema of whichever model is referenced.
  > That is what contracts and tests do.`}
/>

<MultipleChoice
  markdown={`What is the difference between \`ref()\` and \`source()\`?

- \`source()\` is for other dbt projects.
  > Cross-project references use a different mechanism.
- [o] One points at a dbt model, the other at a raw table.
  > \`source()\` covers tables loaded by something else, declared in YAML. Declaring sources is also what enables freshness checks and lineage back to the loader.
- \`source()\` is simply the deprecated spelling of \`ref()\`.
  > Both are current and mean different things.
- \`ref()\` works only in incremental models.
  > It works in every model.`}
/>

<MultipleChoice
  markdown={`What is an ephemeral model?

- A model that gets dropped again after each run.
  > Nothing is created to drop.
- [o] A model never built in the warehouse at all.
  > Its SQL is inlined as a CTE into every model that \`ref\`s it. Useful for small, reused logic. It stops being useful once several models inline the same heavy computation, since the work is then repeated.
- A model materialized in memory.
  > There is no in-memory materialization; the warehouse does all execution.
- A model with a short retention policy.
  > Retention is not a dbt materialization.`}
/>

<MultipleChoice
  markdown={`What does \`dbt build\` do that \`dbt run\` does not?

- Nothing; they are aliases.
  > They differ in scope.
- [o] It interleaves models, tests, seeds, and snapshots.
  > Running in DAG order means a model's tests run before its downstream models are built. That is the important part: a failing test stops the bad data from propagating, where \`run\` then \`test\` would have already built everything downstream.
- It rebuilds every model in the project from scratch.
  > Full rebuilds come from \`--full-refresh\`.
- It compiles without executing.
  > That is \`dbt compile\`.`}
/>

<MultipleChoice
  markdown={`What are dbt's four built-in generic tests?

- \`primary_key\`, \`foreign_key\`, \`check\`, \`index\`.
  > These are database constraints, not dbt's generic tests.
- [o] \`unique\`, \`not_null\`, \`accepted_values\`, and \`relationships\`.
  > \`relationships\` is the referential-integrity one, asserting every value exists in a referenced column.
- \`unique\`, \`not_null\`, \`range\`, \`freshness\`.
  > Freshness is a separate source-level command, and there is no built-in \`range\`.
- \`equal_rowcount\`, \`unique\`, \`not_null\`, \`expression_is_true\`.
  > The first and last come from \`dbt_utils\`, not core.`}
/>

<MultipleChoice
  markdown={`A generic test compiles to a query. What does dbt do with the result?

- It compares the output to a stored fixture.
  > That is closer to how dbt *unit* tests work.
- [o] It passes when the query returns zero rows.
  > Every returned row is a failing record. It is why writing a custom test means writing a query that selects the violations.
- It checks that the query returns at least one row.
  > That would invert every test.
- It compares row counts before and after the run.
  > No such comparison is made.`}

<MultipleChoice

## Dimensional modeling

<MultipleChoice
  markdown={`What distinguishes a fact table from a dimension table?

- Fact tables hold text and dimensions hold numbers.
  > It is nearly the reverse: measures are numeric, descriptive attributes are usually text.
- [o] One records events, the other describes them.
  > A fact table holds measurable events at a defined grain; a dimension holds the attributes you filter and group by. Facts are long and narrow and grow with activity; dimensions are wide and comparatively short.
- Facts are indexed and dimensions are not.
  > Indexing is a physical choice unrelated to the classification.
- Dimensions are always smaller than facts.
  > Usually true, but a customer dimension in a large business can be enormous. Size is not the definition.`}
/>

<MultipleChoice
  markdown={`Why pin down the grain before anything else?

- Because the grain determines the table name.
  > Naming follows the grain but is not why it matters.
- [o] Every later decision follows from what one row represents.
  > Which dimensions apply, which measures are additive, and whether a join fans out all depend on it. "One row per order line per day" is a testable statement; a table without an agreed grain quietly accumulates double counting.
- Because the warehouse needs it in order to allocate storage.
  > Storage is allocated regardless.
- Because tests cannot run without it.
  > Tests run either way; they are just far less meaningful.`}
/>

<MultipleChoice
  markdown={`Why prefer a surrogate key over the source system's natural key?

- Surrogate keys are shorter to type.
  > Brevity is not the argument.
- [o] It insulates the warehouse from source key changes.
  > It is also what makes SCD Type 2 possible, since one natural key then needs several rows. A natural key cannot identify "the version of this customer that was current last March".
- Natural keys cannot be indexed.
  > They index perfectly well.
- Surrogate keys enforce referential integrity automatically.
  > Integrity still has to be tested or constrained.`}
/>

<MultipleChoice
  markdown={`What belongs in the staging layer?

- [o] One model per source table, doing light cleaning only.

- Joined and aggregated tables ready for BI.
  > That is the mart layer.
- Raw data exactly as loaded, untouched.
  > Untouched raw data is the source; staging is the first transformation.`}

<MultipleChoice
  markdown={`What are the three types of fact table?

- [o] Transaction, periodic snapshot, and accumulating snapshot.

<MultipleChoice
  markdown={`An account balance is recorded daily. Which type of measure is it?

- [o] Semi-additive, so it sums across accounts but not time.

<MultipleChoice
  markdown={`What does SCD Type 1 do, and what is the cost?

  > That is Type 2.
- [o] It overwrites the attribute in place, losing the history.
  > One row per entity is simple, but past reporting silently changes. Fine for correcting a typo in a name; wrong for a customer's region, where historical reporting would silently shift.

  > That is Type 3, which keeps only one prior value.

<MultipleChoice
  markdown={`How is SCD Type 2 implemented?

- [o] A new row per version, keyed by a new surrogate key.

<MultipleChoice

<MultipleChoice

- [o] Percentages are non-additive across rows.

## Metrics & the semantic layer

<MultipleChoice
  markdown={`What is a semantic layer for?

- [o] Defining metrics once, centrally, for every tool.
  > Dimensions and entities too, so every tool computes the same number the same way. It moves metric logic out of a dozen dashboards and into version-controlled definitions.

<MultipleChoice
  markdown={`What is metric drift?

  > A trending metric is often exactly what you want to see.
- [o] One named metric defined differently in different places.

  > Schema change is caught by contracts and tests.
- A metric that becomes slow to compute.

<MultipleChoice
  markdown={`What is the difference between a measure and a metric?

- [o] One is a raw column, the other a defined calculation.

  > Either can be materialized.
- A metric is always a ratio.

<MultipleChoice
  markdown={`What is a fan-out (fan trap), and why is it dangerous?

- [o] A one-to-many join duplicates the one-side rows.

- A dashboard fanning one query out to many warehouses.
  > Query routing is unrelated.
- A dimension with too many members.

/>

<MultipleChoice
  markdown={`How does a chasm trap differ from a fan trap?

- They are the same thing under two names.
  > They arise from different join shapes.
- [o] A chasm trap crosses two unrelated one-to-many branches.
  > The cross product it produces is worse than a fan trap's single inflation. Splitting into separate queries per branch, or aggregating each branch before joining, avoids it.
- A chasm trap only occurs in NoSQL databases.
  > It is a relational join problem.
- A chasm trap under-counts rather than over-counting.
  > It over-counts, and typically by more.`}
/>

<MultipleChoice
  markdown={`Why can't a distinct count be pre-aggregated?

## Testing & data quality

<MultipleChoice
  markdown={`A \`unique\` test on \`order_id\` fails. What does that actually tell you?

- The column contains some \`NULL\` values.
  > That is what \`not_null\` catches; \`unique\` ignores \`NULL\`s on most adapters.
- [o] The model's stated grain is wrong.
  > A join fanned out, the source has genuine duplicates, or an incremental run appended rows it should have merged. A failing uniqueness test is nearly always a grain problem, which is why it is the highest-signal test in the suite.
- The column needs an index.
  > Warehouses generally have no such index, and it would not change the data.
- The test is misconfigured.
  > Possible, but the first assumption should be that the data is telling the truth.`}
/>

<MultipleChoice
  markdown={`When should a test be set to \`severity: warn\` rather than \`error\`?

- [o] When it is worth surfacing but should not block the build.

  > Severity is available on any test and the choice is about consequence, not location.`}

<MultipleChoice
  markdown={`How do you test uniqueness of a compound key?

- [o] Test a concatenated surrogate key, or use \`dbt_utils\`.

  > \`relationships\` checks referential integrity, not uniqueness.

<MultipleChoice
  markdown={`What does \`store_failures\` give you?

<MultipleChoice
  markdown={`Where should the bulk of tests live, staging or marts?

- Entirely in marts, since that is what people read.
  > Testing only at the end tells you something broke, not where.
- [o] Both, but with quite different intent.
  > Staging tests assert source assumptions such as key uniqueness and non-null; mart tests assert business rules such as reconciliation. A staging failure localizes the problem immediately; a mart failure catches logic errors introduced downstream.
- Entirely in staging, so problems are caught early.
  > Early testing cannot catch a bug introduced by a mart's own join.
- In a separate test-only project.
  > Separating tests from the models they describe makes them rot.`}
/>

<MultipleChoice
  markdown={`How do dbt unit tests differ from data tests?

- They run faster on the same data.
  > They run on different data entirely.
- [o] It runs the logic against fixed fixtures, not today's data.
  > An expected output is asserted, so it validates the transformation itself. It is the right tool for tricky logic (a window function, a date-boundary rule), where you want the edge case pinned regardless of what the warehouse currently holds.
- Unit tests only apply to macros.
  > They apply to models.
- Unit tests remove the need for data tests entirely.
  > They are complementary: one checks the logic, the other checks reality.`}
/>

<MultipleChoice
  markdown={`How should the response differ between a test failing in CI and the same test failing in production?

- Identically; a failure is a failure.
  > The blast radius and the available actions differ.
- [o] One blocks a merge; the other means bad data is already out.
  > In CI it is fixed before shipping. In production it needs triage, communication to consumers, and only then a fix. The production case has a stakeholder dimension the CI case does not.
- CI failures should be ignored if the branch is urgent.
  > Urgency is precisely when the gate is most valuable.
- Production failures should always trigger an immediate rollback.
  > Sometimes correct, but only after understanding what broke.`}
/>

<MultipleChoice
  markdown={`What causes alert fatigue in a test suite, and what fixes it?

- Too few tests, fixed by adding more.
  > Adding tests indiscriminately is how fatigue starts.
- [o] Tests firing on known, tolerated conditions cause it.
  > People learn to ignore the channel. Tighten thresholds, route by severity, and delete tests nobody acts on. A test whose failure produces no action is not a test, it is noise.
- Slow tests, which is fixed by running them less often.
  > Running less often delays detection without improving signal.
- Tests written by too many authors.
  > Authorship is not the problem; actionability is.`}
/>

<MultipleChoice
  markdown={`How does data observability differ from testing?

- Observability is testing with better dashboards.
  > It is a different detection model, not a presentation of the same one.
- [o] One checks what you specified, the other what you did not.
  > Testing asserts conditions you thought of; observability monitors volume, freshness, schema, and distribution for anomalies you did not anticipate. They cover different gaps: one catches known failure modes precisely, the other catches unknown ones approximately.
- Observability replaces the need for tests.
  > Anomaly detection is far noisier than an explicit assertion and cannot express business rules.
- Testing is for sources and observability is for marts.
  > Both apply throughout.`}
/>

<MultipleChoice
  markdown={`How do you test that a metric is correct, not merely non-null?

- Add a \`not_null\` and a \`unique\` test to the metric column.
  > These catch structural problems and say nothing about the value.
- [o] Reconcile it against an independent calculation.
  > The source system's own total, a published figure, or a differently-derived model, asserting the difference is within tolerance. It is the only class of test that catches logic that is confidently, consistently wrong.
- Check that it is greater than zero.
  > A sign check catches gross failures and little else.
- Compare it to yesterday's value and alert on any change.
  > Metrics are supposed to change; this fires constantly.`}
/>

<MultipleChoice
  markdown={`Why prefer fixing data upstream over patching it in a downstream model?

- Downstream fixes are harder to write.
  > They are usually easier, which is the temptation.
- [o] A patch fixes one consumer and leaves the rest broken.
  > It also quietly becomes permanent. Patching downstream is sometimes the right emergency action; it should come with a ticket for the real fix.
- Upstream systems are always owned by that same team.
  > They frequently are not, which is what makes the upstream fix slower.
- Warehouses cannot express the fix downstream.
  > They usually can, which is exactly the problem.`}
/>

<MultipleChoice
  markdown={`What extra tests do \`dbt_utils\` and \`dbt_expectations\` add?

- Nothing beyond the four built-in tests, repackaged.
  > Both add substantial new assertions.
- [o] Row-count, expression, and distributional assertions.
  > \`equal_rowcount\`, \`expression_is_true\`, \`unique_combination_of_columns\`, plus value ranges and column-type expectations. \`dbt_expectations\` in particular ports the Great Expectations vocabulary into dbt's test framework.
- Only performance benchmarks.
  > Neither package benchmarks queries.
- Tests that run outside the warehouse.
  > All dbt tests compile to SQL and run in the warehouse.`}
/>

<MultipleChoice
  markdown={`What is the difference between a source test and a model test?

- Source tests run first and model tests run last, but they assert the same things.
  > They assert different classes of thing.
- [o] One covers data you do not control, the other your own.
  > A source test failing points at the loader or the upstream system; a model test points at your transformation. The distinction matters for who gets paged.
- Source tests cannot be generic tests.
  > The same generic tests apply to both.
- Model tests cannot be configured with severity.
  > Severity applies to both.`}
/>

<MultipleChoice
  markdown={`An \`accepted_values\` test starts failing after a source added a new status code. What is the right first move?

- Delete the test, since the value set is evidently not fixed.
  > Deleting it removes the only mechanism that noticed the change.
- [o] Confirm it is legitimate, then update logic and test together.
  > Work out what downstream logic assumes about statuses first. The test did its job: it surfaced a source change before a \`CASE\` statement silently bucketed the new status as "other".
- Add the value to the test and move on.
  > Half the fix. The downstream \`CASE\` expressions that never heard of the new status are the actual risk.
- Set the test to \`warn\` permanently.
  > This converts a caught problem into a standing notification nobody reads.`}
/>

<MultipleChoice
  markdown={`Freshness on a source is configured with \`warn_after: 12 hours\` and \`error_after: 24 hours\`. What does that express?

- The model will be rebuilt every 12 hours.
  > Freshness checks state; it does not schedule builds.
- [o] Flag at 12 hours old, and fail the pipeline at 24.
  > Building on data that stale is worse than stopping. Setting the thresholds from what consumers actually need is what keeps the warning meaningful.
- Rows older than 24 hours will be deleted.
  > Nothing is deleted.
- Tests will be skipped for 12 hours following a load.
  > No skipping is implied.`}
/>
