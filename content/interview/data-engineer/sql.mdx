## Q&A

### What's the difference between RANK, DENSE_RANK, and ROW_NUMBER?

All number rows within a partition; they differ on **ties**:

- **`ROW_NUMBER`** — always distinct (1, 2, 3, 4), ties broken arbitrarily.
- **`RANK`** — ties share a rank, then it **skips** (1, 2, 2, 4).
- **`DENSE_RANK`** — ties share a rank, **no skip** (1, 2, 2, 3).

```sql
SELECT name, score,
  ROW_NUMBER() OVER (ORDER BY score DESC) AS rn,
  RANK()       OVER (ORDER BY score DESC) AS rnk,
  DENSE_RANK() OVER (ORDER BY score DESC) AS dr
FROM players;
```

### How do you keep only the latest row per key (deduplication)?

Number rows within each key by recency, then keep number 1:

```sql
SELECT *
FROM events
QUALIFY ROW_NUMBER() OVER (
  PARTITION BY user_id ORDER BY event_time DESC
) = 1;
```

Use `ROW_NUMBER` (not `RANK`) so exact-tie timestamps still collapse to
one row. Without `QUALIFY` (e.g. Postgres), wrap it in a subquery and
filter `WHERE rn = 1`.

### What's the difference between a CTE and a subquery? When is a CTE worth it?

Both produce an intermediate result. A **CTE** (`WITH … AS`) is named and
can be referenced multiple times and read top-to-bottom, which makes
multi-step transformations far more readable. A correlated **subquery**
runs per outer row and can be a performance trap. CTEs shine for staging
steps and recursive queries.

### A query is slow. What do you check first?

Read the **query plan** (`EXPLAIN`). Look for full scans where an index
should help, the join order/strategy, and the row estimates (bad
estimates → bad plans, often from stale statistics). Common wins: filter
early, avoid `SELECT *`, ensure join/filter columns are indexed,
pre-aggregate before joining, and partition/prune large tables.

### What's the difference between UNION and UNION ALL?

`UNION` concatenates two result sets **and removes duplicates** (an
expensive sort/hash); `UNION ALL` keeps everything, including duplicates.
Prefer `UNION ALL` unless you specifically need dedup — it skips the
distinct step.

## Concept checks

<MultipleChoice
  markdown={`Two orders in the same region are tied on \`amount\`. You need both to get the **same** rank, and the next distinct amount to skip a number (1, 2, 2, 4). Which function do you want?

- \`ROW_NUMBER()\`
  > \`ROW_NUMBER()\` assigns a distinct number to every row even on ties (1, 2, 3, 4), breaking ties arbitrarily — it never repeats a value.
- [o] \`RANK()\`
  > \`RANK()\` gives tied rows the same rank and then skips, producing 1, 2, 2, 4 — exactly the pattern described.
- \`DENSE_RANK()\`
  > \`DENSE_RANK()\` also ties rows together but does *not* skip — it yields 1, 2, 2, 3.
- \`NTILE(4)\`
  > \`NTILE\` buckets rows into a fixed number of groups; it isn't a tie-aware ranking.`}

<MultipleChoice
  markdown={`Why \`ROW_NUMBER()\` rather than \`RANK()\` for "keep one row per user"?

- They're interchangeable for deduplication.
  > They differ on ties: two rows with the *same* \`event_time\` would both get rank 1 under \`RANK\`, so you'd keep both.
- [o] \`ROW_NUMBER()\` guarantees a single row per partition even on ties, so filtering to \`= 1\` keeps exactly one.
  > It assigns distinct numbers within each partition no matter what — exactly what "one row per user" needs.
- \`RANK()\` can't be used in a window at all.
  > \`RANK()\` is a valid window function; it's just the wrong tie behavior for dedup.
- \`ROW_NUMBER()\` sorts the whole table, which is required.
  > Ordering happens within each partition for ranking, not as a global sort requirement.`}
/>
