## SQL

<MultipleChoice
  markdown={`What is the logical order in which SQL clauses are evaluated?

- Exactly the order they are written.
  > \`SELECT\` is written first and evaluated near the end, which is why its aliases are unavailable in \`WHERE\`.
- [o] \`FROM\` → \`WHERE\` → \`GROUP BY\` → \`HAVING\` → \`SELECT\` → \`ORDER BY\` → \`LIMIT\`.
  > This single fact explains most beginner errors: aliases usable in \`ORDER BY\` but not \`WHERE\`, and aggregates belonging in \`HAVING\`.
- \`SELECT\` → \`FROM\` → \`WHERE\` → \`GROUP BY\`.
  > Rows must be sourced and filtered before anything can be projected.
- It varies from one engine to the next and cannot be relied on.
  > The logical order is standardized; only the physical plan varies.`}
/>

<MultipleChoice
  markdown={`Which pattern keeps only the latest row per key, preserving all columns?

- \`GROUP BY key\` with \`MAX(updated_at)\`.
  > This returns the key and timestamp but discards the winning row's other columns.
- [o] \`ROW_NUMBER() OVER (PARTITION BY key ORDER BY updated_at DESC)\` filtered to \`= 1\`.
  > \`RANK\` would return several rows per key on a timestamp tie, which is why \`ROW_NUMBER\` is the safe default here.
- \`SELECT DISTINCT ON (key) *\`, which every engine will support.
  > \`DISTINCT ON\` solves it neatly, but it is a Postgres and DuckDB extension.
- \`SELECT DISTINCT *\`.
  > This removes only fully identical rows.`}
/>

<MultipleChoice
  markdown={`A query on a partitioned table is slow and scans everything. What is the most likely cause?

- The table has been split into far too many very small partitions.
  > Over-partitioning hurts, but it would not eliminate pruning entirely.
- [o] The filter is not on the partition column, or wraps it.
  > A function applied to the column stops the engine pruning. \`WHERE DATE(event_ts) = '2026-01-01'\` defeats pruning on \`event_ts\`; a bare range predicate preserves it.
- The table is not indexed.
  > Columnar engines generally have no secondary indexes; pruning takes their place.
- Statistics are out of date.
  > Stale statistics skew join order, but pruning is driven by the predicate.`}
/>

<MultipleChoice
  markdown={`What does a correlated subquery do, and why can it be slow?

- It runs a single time and then caches the result for reuse.
  > An uncorrelated subquery can be; a correlated one cannot.
- [o] It references the outer query, so it re-evaluates per row.
  > Conceptually, at least. Modern planners often rewrite it into a join. When the rewrite does not happen, an \`EXISTS\` or an explicit join is the usual remedy.
- It joins a table to itself.
  > That is a self join.
- It always returns exactly one row.
  > A scalar subquery must, but correlated subqueries appear in \`EXISTS\` and \`IN\` too.`}
/>

<MultipleChoice
  markdown={`What is the gaps-and-islands problem?

- Finding \`NULL\` values in a column.
  > Missing values are a different question.
- [o] Identifying runs of consecutive values and the breaks in them.
  > Consecutive login days, uninterrupted status periods, and sessionization are all cases of it. The standard trick is a difference between a row number and the value itself, which stays constant within a run and becomes a group key.
- Detecting duplicate rows.
  > Duplicates are found with a count per key.
- Filling in whichever partitions are missing from a table.
  > A date spine handles that.`}
/>

<MultipleChoice
  markdown={`Which frame computes a 7-day moving average on daily data?

- \`ROWS BETWEEN 7 PRECEDING AND CURRENT ROW\`
  > That spans 8 rows.
- [o] \`ROWS BETWEEN 6 PRECEDING AND CURRENT ROW\`
  > Six prior rows plus the current one is seven days, provided the series has no missing days, which is why a date spine often comes first.
- \`RANGE BETWEEN 7 PRECEDING AND CURRENT ROW\`
  > \`RANGE\` with an interval works on some engines and behaves differently around gaps and ties.
- \`ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW\`
  > That is a cumulative average over all history.`}
/>

<MultipleChoice
  markdown={`How do you find duplicate rows on a key?

- \`SELECT DISTINCT key FROM t\`
  > This lists the keys and hides which ones repeat.
- [o] \`SELECT key FROM t GROUP BY key HAVING COUNT(*) > 1\`
  > Grouping and filtering on the count is the direct expression. \`COUNT(*) OVER (PARTITION BY key)\` gives the same answer while keeping the offending rows visible.
- \`SELECT key FROM t WHERE COUNT(*) > 1\`
  > An aggregate cannot appear in \`WHERE\`.
- \`SELECT key, ROW_NUMBER() OVER () FROM t\`, numbering rows.
  > An unpartitioned row number just numbers every row.`}
/>

<MultipleChoice
  markdown={`What is a covering index, and what does it avoid?

- An index on every column of the table.
  > That would duplicate the table.
- [o] An index holding every column the query needs.
  > The query is then served from the index without reading the table rows. The saving is the random I/O of the table lookups, which on a wide table dominates.
- An index that covers \`NULL\` values.
  > \`NULL\` handling is orthogonal.
- An index maintained by the query planner automatically.
  > Indexes are created explicitly.`}
/>

<MultipleChoice
  markdown={`How do you join two very large tables efficiently in a distributed engine?

- Broadcast one side of the join out to every node in the cluster.
  > Broadcast works only when one side is small enough to fit in each worker's memory.
- [o] Co-partition both sides so matching rows share a node.
  > Otherwise accept a shuffle sort-merge join, and make sure the key is not skewed. Pre-bucketing on the join key is what turns a repeated expensive shuffle into a one-time cost.
- Add an index on the join key.
  > Most distributed engines do not use secondary indexes for this.
- Convert the join to a subquery.
  > Syntax does not change the physical strategy.`}
/>

<MultipleChoice
  markdown={`What does \`NTILE(10)\` do?

- Returns the value sitting at the 10th percentile of the column.
  > That would be a percentile function.
- [o] Splits the ordered partition into 10 equal-sized buckets.
  > It returns each row's bucket number. With a row count that does not divide evenly, earlier buckets get the extra rows.
- Returns every 10th row.
  > Sampling by position is a different operation.
- Rounds values to the nearest tenth.
  > No arithmetic is applied to the values.`}
/>

<MultipleChoice
  markdown={`\`UNION\` versus \`UNION ALL\`: which should be the default in a pipeline, and why?

- \`UNION\`, because duplicates are always a bug.
  > Deduplicating by default hides real duplicates that should have been investigated.
- [o] \`UNION ALL\`, because it skips the deduplication pass.
  > Reach for \`UNION\` only when you specifically need distinct rows. Silent deduplication also masks a fan-out upstream, which you would rather see fail a uniqueness test.
- They perform identically, so the choice does not matter.
  > \`UNION\` costs a sort or hash over the whole result.
- \`UNION\`, because \`UNION ALL\` is non-standard.
  > Both are standard SQL.`}
/>

<MultipleChoice
  markdown={`What does partition pruning depend on?

- The table being clustered.
  > Clustering is a separate, complementary mechanism.
- [o] A filter on the partition column the engine can read early.
  > It is why the partition column should be the one people actually filter on, almost always a date.
- The partition count happening to be an exact power of two.
  > No such requirement.
- Statistics being refreshed.
  > Pruning uses partition metadata, not table statistics.`}
/>

<MultipleChoice
  markdown={`What is a materialized view, and what is its cost?

- A view that gets recomputed from scratch on every single query.
  > That is an ordinary view.
- [o] A stored, precomputed result that repeated queries reuse.
  > The cost is storage, and staleness until it is refreshed. Some engines refresh incrementally on write; others need a scheduled full refresh, which is a pipeline concern.
- A view restricted to certain columns.
  > Column restriction is just a projection.
- A temporary table scoped to a session.
  > Temp tables vanish with the session.`}
/>

<MultipleChoice
  markdown={`Which returns rows present in the left table but absent from the right?

- \`INNER JOIN\` with \`IS NULL\`.
  > An inner join has already dropped the unmatched rows.
- [o] \`LEFT JOIN ... WHERE right.key IS NULL\`, or equivalently \`NOT EXISTS\`.
  > \`NOT IN\` expresses the same intent but returns nothing at all if the subquery yields a single \`NULL\`.
- A \`FULL OUTER JOIN\` with no filtering applied afterwards.
  > That returns everything from both sides.
- \`CROSS JOIN\` with a filter.
  > A cross join multiplies rows before anything is filtered.`}
/>

<MultipleChoice
  markdown={`When is a \`CROSS JOIN\` the right tool?

- Never; it is always a mistake.
  > It is the correct tool in several modelling situations.
- [o] When you deliberately need every combination of two sets.
  > A date spine crossed with every store produces a dense grid before joining sparse facts. The accidental version, from a missing join condition, is what gives it its reputation.
- When the join key is missing entirely from one of the tables.
  > A missing key is a modelling problem to fix, not to cross-join around.
- When joining more than three tables.
  > Table count is irrelevant.`}
/>

## Data modeling

<MultipleChoice
  markdown={`What does the grain of a fact table define?

- How many partitions it needs.
  > Partitioning follows from query patterns and size.
- [o] Exactly what a single row represents.
  > It determines which dimensions apply and whether a measure can be summed. "One row per order line per day" is testable with a uniqueness assertion; a table with no agreed grain accumulates double counting.
- The physical sort order of the stored table.
  > That is clustering.
- The level of access control applied.
  > Security is unrelated.`}
/>

<MultipleChoice
  markdown={`What is the difference between a star and a snowflake schema?

- A star has more tables.
  > A snowflake has more, since its dimensions are split.
- [o] A snowflake normalizes its dimensions; a star does not.
  > The star trades redundancy for fewer joins and simpler queries. The star trades some redundancy for fewer joins and simpler queries, which is usually the right trade in a warehouse.
- A snowflake schema can support more fact tables than a star.
  > Both support any number.
- A star cannot express hierarchies.
  > Hierarchies live inside the flat dimension as columns.`}
/>

<MultipleChoice
  markdown={`Which SCD type preserves full history with validity ranges?

- Type 0, which refuses the change.
  > Type 0 retains the original value outright.
- [o] Type 2.
  > A new row per version with effective dates and a current flag, joined from facts on the surrogate key that was current at the time.
- Type 1.
  > Type 1 overwrites and keeps no history.
- Type 3.
  > Type 3 keeps only one prior value in an extra column.`}
/>

<MultipleChoice
  markdown={`What are SCD Types 4 and 6?

- Two names for the same technique.
  > They are distinct.
- [o] One splits out history; the other blends Types 1, 2, and 3.
  > Type 4 puts fast-changing attributes in a separate history table; Type 6 lets a row carry both current and historical values. Type 6 is sometimes written as "1 + 2 + 3", which is where the number comes from.
- Type 4 deletes old rows; Type 6 archives them.
  > Neither discards history.
- Type 4 applies to fact tables and Type 6 to dimension tables.
  > Both are dimension techniques.`}
/>

<MultipleChoice
  markdown={`What is 3NF, in one sentence?

- Every table has a primary key.
  > That is closer to 1NF's spirit and a general requirement.
- [o] Every non-key attribute depends on the key and only the key.
  > The whole key, and nothing but it, so no transitive dependencies remain. It is what prevents the same fact being stored in two places and drifting apart under update.
- Every column holds an atomic value.
  > That is 1NF.
- No table is allowed to hold more than a single foreign key.
  > Foreign key count is unconstrained.`}
/>

<MultipleChoice
  markdown={`What is a data vault, and when would you choose it over a star schema?

- A backup format for warehouse tables.
  > It is a modelling methodology, not a backup.
- [o] Hubs, links, and satellites, chosen for auditability.
  > Business keys, relationships, and attributes with history. It suits absorbing many changing sources when that matters more than query ergonomics. It is insert-only and highly normalized, so a dimensional presentation layer is usually built on top for consumers.
- A star schema with all history removed.
  > It retains more history, not less.
- A NoSQL alternative to dimensional modelling entirely.
  > It is implemented in relational warehouses.`}
/>

<MultipleChoice
  markdown={`What does "grain mismatch" mean?

- Two tables using different date formats.
  > Formatting is a parsing issue.
- [o] Combining tables whose rows represent different things.
  > Order headers against order lines, say, so measures duplicate or fail to align. The fix is to aggregate one side to the other's grain before joining, rather than joining and hoping.
- A partition key that was chosen with the wrong cardinality.
  > That is a partitioning problem.
- A dimension with missing members.
  > That is a referential integrity problem.`}
/>

<MultipleChoice
  markdown={`Why use a date dimension rather than date functions?

- Date functions are simply unsupported in most cloud warehouses.
  > They are universally supported.
- [o] It puts fiscal calendars and holidays in one governed place.
  > Week-start conventions and business-day flags too, and a join then does work that would otherwise be repeated in every query. It is also what makes "compare to the same week last year" a join rather than a bespoke expression.
- It makes queries run faster in all cases.
  > Any speed benefit is secondary and situational.
- It is required for partitioning.
  > Partitioning uses a column, not a dimension.`}
/>

<MultipleChoice
  markdown={`What is a surrogate key sequence's advantage over a UUID?

- UUIDs cannot be primary keys.
  > They can.
- [o] Sequential integers are compact and keep storage ordered.
  > They compress and sort well, where random UUIDs scatter writes and are four times wider. UUIDs win when keys must be generated independently across systems without coordination, which is a real trade rather than a wrong answer.
- Sequences guarantee uniqueness across entirely separate systems.
  > That is precisely what UUIDs offer and sequences do not.
- UUIDs cannot be indexed.
  > They index fine; they just index worse.`}
/>

<MultipleChoice
  markdown={`How do you model a many-to-many between facts and a dimension?

- Duplicate the fact row per dimension member.
  > Duplication breaks the grain and inflates every measure.
- [o] Introduce a bridge table holding the pairs.
  > An allocation weight lets measures be apportioned instead of double counted. Without the weight, "revenue by product category" for a multi-category order counts the revenue once per category.
- Store the dimension keys as a comma-separated list.
  > This is unjoinable and unqueryable without parsing.
- Create a separate fact table per dimension member.
  > Unmaintainable, and it fragments the measure.`}
/>

<MultipleChoice
  markdown={`What is a periodic snapshot fact table for?

- Recording every individual transaction.
  > That is a transaction fact.
- [o] Capturing state at regular intervals rather than events.
  > Daily balances and month-end inventory are the classic cases, and they answer questions about levels. Its measures are typically semi-additive: summable across accounts, not across days.
- Storing a backup of a fact table.
  > It is a modelling pattern, not a backup.
- Tracking each milestone of a single long-running process.
  > That is an accumulating snapshot.`}
/>

<MultipleChoice
  markdown={`A dimension attribute changes and history does not matter. Which type applies, and what is the risk?

- Type 2, with the risk of table growth.
  > Type 2 is what you use when history *does* matter.
- [o] Type 1, overwriting the attribute in place.
  > The risk is that "history does not matter" is often wrong, and prior reports silently change when re-run. Once the old value is gone it cannot be recovered, which is why Type 2 is often the safer default for anything used in reporting.
- Type 0, with the risk of stale data.
  > Type 0 rejects the change entirely.
- Type 3, with the risk of losing the current value.
  > Type 3 retains both current and one prior value.`}
/>

<MultipleChoice
  markdown={`What is a mini-dimension, and what problem does it solve?

- A dimension with fewer than 100 rows.
  > Size alone does not define it.
- [o] Fast-changing attributes split into their own small table.
  > It stops Type 2 versioning from exploding the main dimension's row count. Demographic bands on a customer dimension are the classic case.
- A dimension used by only one fact table.
  > That is simply a non-conformed dimension.
- A denormalized copy of a dimension, built purely for BI tools.
  > That is a mart-level convenience table.`}
/>

<MultipleChoice
  markdown={`What is the difference between a bus matrix and a data mart?

- They are the same artifact seen at two different scales.
  > One is a plan, the other a built thing.
- [o] One is a planning grid, the other a built subject area.
  > The bus matrix maps business processes against conformed dimensions; the mart is the thing you query. The matrix is what keeps independently-built marts conformable rather than accidentally incompatible.
- A bus matrix is a physical table.
  > It is documentation.
- A data mart contains only aggregates.
  > Marts usually contain detail as well.`}
/>

<MultipleChoice
  markdown={`How do you handle a fact row whose dimension member has not arrived yet?

- Reject the fact and alert.
  > Alerting is reasonable; rejecting loses the event.
- [o] Assign it a reserved "unknown" dimension key, then repair it once the real member lands.
  > Every dimension carrying an explicit unknown row is what stops an inner join from silently deleting facts.
- Insert a dimension row carrying the key and \`NULL\` for the attributes.
  > This creates a placeholder indistinguishable from a real member, which then collides when the genuine row arrives.
- Use an outer join everywhere instead.
  > Outer joins mask the problem and leave \`NULL\`s scattered through downstream logic.`}
/>

## Warehousing & storage

<MultipleChoice
  markdown={`Why is columnar storage faster for analytical queries?

- Columns compress into a single file per table.
  > File layout is not the mechanism.
- [o] Fewer columns are read, and each compresses far better.
  > Values within a column share a type, so encoding is much more effective. Less I/O on both counts. It is also why \`SELECT *\` is disproportionately expensive in a columnar store.
- Columnar formats keep the entire table resident in memory.
  > Memory residency is unrelated to layout.
- Rows are stored sorted by primary key.
  > Sorting is a separate choice.`}
/>

<MultipleChoice
  markdown={`What makes a good partition key?

- The column with the most distinct values.
  > High cardinality produces many tiny partitions and the small files problem.
- [o] A low-cardinality column that queries reliably filter on.
  > Most often a date, producing partitions of a workable size. The two tests are "do queries filter on it" and "are the resulting partitions neither tiny nor enormous".
- The primary key.
  > A unique key is the worst possible partition key.
- Whichever column happens to be listed first in the schema.
  > Column order carries no meaning here.`}
/>

<MultipleChoice
  markdown={`How do Parquet, ORC, and Avro differ?

- They are three broadly interchangeable columnar file formats.
  > Avro is not columnar.
- [o] Two are columnar; Avro is row-based with schema evolution.
  > Parquet and ORC suit analytical scans, Avro suits streaming and record-at-a-time writes. Kafka pipelines commonly land Avro and convert to Parquet for the analytical layer.
- Avro compresses better than both.
  > Columnar formats compress better on analytical data.
- ORC is a compressed form of Parquet.
  > They are independent formats.`}
/>

<MultipleChoice
  markdown={`Why does compression work better in a columnar format?

- Columnar files are smaller before compression.
  > Uncompressed size is comparable.
- [o] A column's values share a type and often a narrow range.
  > Run-length, dictionary, and delta encodings all apply, where a mixed-type row would defeat them. A low-cardinality string column can compress by an order of magnitude through dictionary encoding alone.
- Compression algorithms only ever work well on numeric data.
  > They work on any bytes; homogeneity is what raises the ratio.
- Columnar files skip compressing the headers.
  > Header size is negligible.`}
/>

<MultipleChoice
  markdown={`What is the small files problem, and what causes it?

- Files smaller than the block size get rejected outright.
  > They are accepted, just inefficient.
- [o] Per-file overhead comes to dwarf the actual read.
  > Streaming micro-batches and over-partitioning are the usual causes. Compaction into roughly 128 MB to 1 GB files is the standard remedy.
- Small files cannot be compressed.
  > They compress, just less effectively.
- It only affects HDFS.
  > Object stores suffer from it too, through request overhead and listing cost.`}
/>

<MultipleChoice
  markdown={`Why did ELT largely replace ETL?

- Transformation logic became simpler.
  > It generally became more complex.
- [o] Cheap elastic compute made transform-in-place practical.
  > Load the raw data first, and the transformations become versioned SQL rather than a separate processing tier. Keeping the raw data also means a logic change can be re-applied without re-extracting from the source.
- Sources stopped supporting extraction.
  > Extraction is unchanged.
- ETL simply cannot cope with any semi-structured data at all.
  > It can; the shift was economic and operational.`}
/>

<MultipleChoice
  markdown={`What most drives cost in a cloud data warehouse?

- The sheer number of tables the warehouse holds.
  > Table count is close to free.
- [o] Bytes scanned, or compute-seconds consumed.
  > Both track how much data the queries actually read. It is why partitioning, clustering, narrow column selection, and materializing repeated heavy work are the levers that matter.
- The number of users.
  > Seat licensing exists but is rarely the dominant line.
- Storage volume.
  > Storage is usually the cheapest component by a wide margin.`}
/>

<MultipleChoice
  markdown={`What is a lakehouse?

- A warehouse with a separate data lake bolted onto it.
  > Coexistence is not the architecture.
- [o] Open table formats layered over object storage.
  > Delta, Iceberg, and Hudi add ACID transactions, schema enforcement, and time travel to lake-scale files. One copy of the data then serves SQL engines and Spark or Python alike, which is the point.
- A data lake queried through a BI tool.
  > A connector adds no transactional guarantees.
- A warehouse that stores only Parquet.
  > File format alone is not the distinction.`}
/>

<MultipleChoice
  markdown={`How does schema evolution differ between Avro and Parquet?

- Neither supports it.
  > Both do, differently.
- [o] Avro resolves a writer schema against a reader schema.
  > That handles added, removed, and renamed fields. Parquet supports evolution too, but is more constrained around type changes and ordering. It is why Avro is favoured at the ingestion boundary where sources change unpredictably.
- Parquet requires rewriting all historical files on any change.
  > Adding a column does not require a rewrite.
- Avro requires the schema to be embedded in every record.
  > The schema is per file, or held in a registry.`}
/>

<MultipleChoice
  markdown={`What is predicate and projection pushdown?

- Two names for partition pruning.
  > Pruning is a related but coarser mechanism.
- [o] Pushing the filter and column list into the file scan.
  > The reader then skips row groups and columns instead of returning everything for the engine to discard. Parquet's per-row-group min/max statistics are what make predicate pushdown effective.
- Moving the computation from the client over to the server.
  > That is a different architectural idea.
- Rewriting joins as subqueries.
  > Unrelated to scan behavior.`}
/>

<MultipleChoice
  markdown={`What is the difference between OLTP and OLAP storage layout?

- OLTP is columnar and OLAP is row-based.
  > This has them the wrong way round.
- [o] One stores rows together, the other stores columns together.
  > OLTP reads or writes a whole record in one place; OLAP scans few columns over many rows. It follows directly from the workload: point reads and writes versus wide aggregate scans.
- Both are columnar; only the indexes differ.
  > Transactional systems are overwhelmingly row-oriented.
- The layout is identical, and only the underlying hardware differs.
  > Layout is the defining difference.`}
/>

<MultipleChoice
  markdown={`What does clustering (or sorting) within a partition buy you?

- It reduces the number of partitions.
  > Partition count is unchanged.
- [o] Similar values sit together, so whole blocks can be skipped.
  > Per-block min/max statistics are what let the engine rule a block out. It is the finer-grained companion to partition pruning, and it is where high-cardinality filter columns belong.
- It compresses the partition further.
  > Compression often does improve, but skipping is the mechanism that matters.
- It enforces uniqueness of the keys inside each partition.
  > No constraint is implied.`}
/>

<MultipleChoice
  markdown={`A pipeline writes 5,000 files of 2 MB each per hour. What should you change?

- Nothing at all, since more files parallelize better.
  > Past the parallelism you can actually use, files cost more than they return.
- [o] Compact them into far fewer, much larger files.
  > Roughly 128 MB to 1 GB, either at write time or in a periodic compaction job. Per-file open, metadata, and object-store request overhead is what dominates otherwise.
- Switch from Parquet to CSV.
  > That loses columnar reads and compression, making things worse.
- Add more partitions.
  > More partitions produces more, smaller files.`}
/>

<MultipleChoice
  markdown={`Why does \`SELECT *\` cost disproportionately more in a columnar warehouse?

- It disables the query cache.
  > Caching keys on the query text; the column list is not the issue.
- [o] \`*\` gives up reading only the columns you actually name.
  > Every column is read, including the large rarely-used ones. On a wide table it can be the difference between scanning gigabytes and scanning terabytes.
- It forces a full sort.
  > No sort is implied.
- It quietly stops the engine from pruning any partitions.
  > Pruning depends on the \`WHERE\` clause, not the projection.`}
/>

<MultipleChoice
  markdown={`What does time travel in a lakehouse table format give you?

- Automatic backups to cold storage.
  > Backup is a separate mechanism.
- [o] Querying the table as of an earlier version or timestamp.
  > Reproducing a report and recovering from a bad write both become straightforward. Retention of old snapshots costs storage, so a vacuum or expiry policy is part of operating it.
- Noticeably faster queries across the historical partitions.
  > No speed benefit is implied.
- Scheduled rollback of failed pipelines.
  > It enables rollback; it does not schedule it.`}
/>

## Pipelines & orchestration

<MultipleChoice
  markdown={`What makes a pipeline idempotent, and why does it matter most?

- It runs in under an hour.
  > Duration is unrelated.
- [o] Re-running the same window produces the same result.
  > It is what makes retries, backfills, and recovery from partial failure safe. The usual implementations are delete-then-insert per partition, or a merge on a unique key. Blind appends break it.
- It never writes to the same target table more than once.
  > Rewriting the same partition is exactly how idempotency is achieved.
- It has no external dependencies.
  > Dependencies are orthogonal.`}
/>

<MultipleChoice
  markdown={`What does an orchestrator give you over cron?

- Lower latency between tasks.
  > Latency is comparable.
- [o] Dependency-aware scheduling, retries, and observability.
  > Backfills too, and a place for failure to be visible rather than silent. Cron runs a command at a time and knows nothing about whether the thing it depends on succeeded.
- Guaranteed exactly-once execution.
  > Neither provides that; the task must be idempotent.
- The ability to run several separate tasks all in parallel.
  > Cron can start parallel jobs; it just cannot coordinate them.`}
/>

<MultipleChoice
  markdown={`Which is a common DAG anti-pattern?

- Splitting work into many small tasks.
  > Granularity aids retries and observability.

<MultipleChoice

<MultipleChoice

<MultipleChoice

<MultipleChoice

<MultipleChoice

<MultipleChoice

<MultipleChoice
  markdown={`What is the difference between event time and processing time?

- [o] When it happened, against when you got round to it.

- Processing time is only relevant in batch systems.

<MultipleChoice
  markdown={`What does a watermark represent?

- [o] An assertion that no older events are still expected.
  > It is what allows a window to be closed and emitted. It is a heuristic trade: a later watermark waits for more stragglers at the cost of latency.
- The point at which a consumer last committed.
  > That is an offset.
- The threshold at which backpressure begins.
  > Backpressure is unrelated.`}

<MultipleChoice
  markdown={`What are the main window types in stream processing?

- [o] Tumbling, hopping or sliding, and session windows.

<MultipleChoice
  markdown={`How should late-arriving data be handled once its window has closed?

<MultipleChoice

- [o] Retaining the most recent value per key indefinitely.

<MultipleChoice

- [o] The signal that a consumer cannot keep up.

<MultipleChoice

- [o] An idempotent producer plus transactions across the cycle.

<MultipleChoice

- [o] Both sides arrive over time, so the join needs buffered state.

<MultipleChoice
  markdown={`How do you make a Kafka consumer idempotent?

<MultipleChoice

- [o] It caps parallelism and fixes the unit of ordering.

- [o] When the value of the result decays within minutes.

  > Catch the specific exception, and keep enough context to diagnose them. Counting the failures as a metric is what turns a slow degradation into something visible.
- Use a bare \`except:\` and continue.
  > A bare except also swallows \`KeyboardInterrupt\` and genuine bugs.
- Validate with a regular expression first, then parse without error handling.
  > Validation reduces failures but cannot guarantee none.`}
/>

<MultipleChoice
  markdown={`When should you reach for pandas rather than plain Python?

- Whenever the data has more than 100 rows.
  > Plain Python is fine well past that.
- [o] When the work is columnar and fits comfortably in memory.
  > Group-and-aggregate, joins, and time-series resampling all vectorize well. Streaming row-at-a-time work with constant memory is where generators still win.
- Whenever reading a CSV.
  > \`csv\` from the standard library is often the better tool for a streaming read.
- When you need to guarantee type safety.
  > pandas dtypes are flexible rather than a guarantee.`}

<MultipleChoice
  markdown={`What is the most common performance pitfall in Python data code?

- Using too many functions.
  > Function call overhead is rarely the bottleneck.
- [o] Doing per-row work in the interpreter needlessly.
  > \`iterrows\`, \`apply(axis=1)\`, and appending to a DataFrame in a loop are the usual culprits, and the last is quadratic. Appending to a DataFrame in a loop is quadratic, since each append copies the whole frame.
- Reading files instead of databases.
  > Source choice is a design decision, not a pitfall.
- Using generators instead of lists.
  > Generators are usually the improvement.`}

<MultipleChoice
  markdown={`How do you split an iterable into fixed-size batches without materializing it?

- \`[items[i:i+n] for i in range(0, len(items), n)]\`
  > Slicing requires a sequence with a known length, so it will not work on a generator.
- [o] Take \`n\` items at a time with \`itertools.islice\`.
  > Or use \`itertools.batched\` on Python 3.12 and later. Both keep memory bounded to one batch, which is the whole point when the source is a stream.
- Convert to a list first, then slice.
  > That materializes everything.
- Use \`zip(*[iter(items)] * n)\`.
  > A well-known trick, but it silently drops the final partial batch.`}
