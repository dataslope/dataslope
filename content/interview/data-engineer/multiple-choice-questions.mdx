## SQL

<MultipleChoice
  markdown={`What is the logical order in which SQL clauses are evaluated?

- Exactly the order they are written.
  > \`SELECT\` is written first and evaluated near the end, which is why its aliases are unavailable in \`WHERE\`.
- [o] \`FROM\` → \`WHERE\` → \`GROUP BY\` → \`HAVING\` → \`SELECT\` → \`ORDER BY\` → \`LIMIT\`.
  > This single fact explains most beginner errors: aliases usable in \`ORDER BY\` but not \`WHERE\`, and aggregates belonging in \`HAVING\`.
- \`SELECT\` → \`FROM\` → \`WHERE\` → \`GROUP BY\`.
  > Rows must be sourced and filtered before anything can be projected.
- It varies by engine and cannot be relied on.
  > The logical order is standardized; only the physical plan varies.`}
/>

<MultipleChoice
  markdown={`Which pattern keeps only the latest row per key, preserving all columns?

- \`GROUP BY key\` with \`MAX(updated_at)\`.
  > This returns the key and timestamp but discards the winning row's other columns.
- [o] \`ROW_NUMBER() OVER (PARTITION BY key ORDER BY updated_at DESC)\` filtered to \`= 1\`.
  > \`RANK\` would return several rows per key on a timestamp tie, which is why \`ROW_NUMBER\` is the safe default here.
- \`SELECT DISTINCT ON (key) *\` on every engine.
  > \`DISTINCT ON\` solves it neatly, but it is a Postgres and DuckDB extension.
- \`SELECT DISTINCT *\`.
  > This removes only fully identical rows.`}
/>

<MultipleChoice
  markdown={`A query on a partitioned table is slow and scans everything. What is the most likely cause?

- The table has too many partitions.
  > Over-partitioning hurts, but it would not eliminate pruning entirely.
- [o] The filter is not on the partition column, or wraps it in a function so the engine cannot prune.
  > \`WHERE DATE(event_ts) = '2026-01-01'\` defeats pruning on \`event_ts\`; a bare range predicate preserves it.
- The table is not indexed.
  > Columnar engines generally have no secondary indexes; pruning takes their place.
- Statistics are out of date.
  > Stale statistics skew join order, but pruning is driven by the predicate.`}
/>

<MultipleChoice
  markdown={`What does a correlated subquery do, and why can it be slow?

- It runs once and caches the result.
  > An uncorrelated subquery can be; a correlated one cannot.
- [o] It references a column from the outer query, so conceptually it re-evaluates per outer row — though modern planners often rewrite it into a join.
  > When the rewrite does not happen, an \`EXISTS\` or an explicit join is the usual remedy.
- It joins a table to itself.
  > That is a self join.
- It always returns exactly one row.
  > A scalar subquery must, but correlated subqueries appear in \`EXISTS\` and \`IN\` too.`}
/>

<MultipleChoice
  markdown={`What is the gaps-and-islands problem?

- Finding \`NULL\` values in a column.
  > Missing values are a different question.
- [o] Identifying runs of consecutive values (islands) and the breaks between them (gaps) — consecutive login days, uninterrupted status periods, sessionization.
  > The standard trick is a difference between a row number and the value itself, which stays constant within a run and becomes a group key.
- Detecting duplicate rows.
  > Duplicates are found with a count per key.
- Filling missing partitions in a table.
  > A date spine handles that.`}
/>

<MultipleChoice
  markdown={`Which frame computes a 7-day moving average on daily data?

- \`ROWS BETWEEN 7 PRECEDING AND CURRENT ROW\`
  > That spans 8 rows.
- [o] \`ROWS BETWEEN 6 PRECEDING AND CURRENT ROW\`
  > Six prior rows plus the current one is seven days — provided the series has no missing days, which is why a date spine often comes first.
- \`RANGE BETWEEN 7 PRECEDING AND CURRENT ROW\`
  > \`RANGE\` with an interval works on some engines and behaves differently around gaps and ties.
- \`ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW\`
  > That is a cumulative average over all history.`}
/>

<MultipleChoice
  markdown={`How do you find duplicate rows on a key?

- \`SELECT DISTINCT key FROM t\`
  > This lists the keys and hides which ones repeat.
- [o] \`SELECT key FROM t GROUP BY key HAVING COUNT(*) > 1\`
  > Grouping and filtering on the count is the direct expression. \`COUNT(*) OVER (PARTITION BY key)\` gives the same answer while keeping the offending rows visible.
- \`SELECT key FROM t WHERE COUNT(*) > 1\`
  > An aggregate cannot appear in \`WHERE\`.
- \`SELECT key, ROW_NUMBER() OVER () FROM t\`
  > An unpartitioned row number just numbers every row.`}
/>

<MultipleChoice
  markdown={`What is a covering index, and what does it avoid?

- An index on every column of the table.
  > That would duplicate the table.
- [o] An index containing all columns a query needs, so the query is served from the index without reading the table rows.
  > The saving is the random I/O of the table lookups, which on a wide table dominates.
- An index that covers \`NULL\` values.
  > \`NULL\` handling is orthogonal.
- An index maintained by the query planner automatically.
  > Indexes are created explicitly.`}
/>

<MultipleChoice
  markdown={`How do you join two very large tables efficiently in a distributed engine?

- Broadcast one side to every node.
  > Broadcast works only when one side is small enough to fit in each worker's memory.
- [o] Co-partition both sides on the join key so matching rows land on the same node, or accept a shuffle sort-merge join and make sure the key is not skewed.
  > Pre-bucketing on the join key is what turns a repeated expensive shuffle into a one-time cost.
- Add an index on the join key.
  > Most distributed engines do not use secondary indexes for this.
- Convert the join to a subquery.
  > Syntax does not change the physical strategy.`}
/>

<MultipleChoice
  markdown={`What does \`NTILE(10)\` do?

- Returns the 10th percentile of the column.
  > That would be a percentile function.
- [o] Splits the ordered partition into 10 buckets of as-equal-as-possible size and returns each row's bucket number.
  > With a row count that does not divide evenly, earlier buckets get the extra rows.
- Returns every 10th row.
  > Sampling by position is a different operation.
- Rounds values to the nearest tenth.
  > No arithmetic is applied to the values.`}
/>

<MultipleChoice
  markdown={`\`UNION\` versus \`UNION ALL\` — which should be the default in a pipeline, and why?

- \`UNION\`, because duplicates are always a bug.
  > Deduplicating by default hides real duplicates that should have been investigated.
- [o] \`UNION ALL\`, because it does no deduplication pass and is therefore cheaper; reach for \`UNION\` only when you specifically need distinct rows.
  > Silent deduplication also masks a fan-out upstream, which you would rather see fail a uniqueness test.
- They perform identically, so it does not matter.
  > \`UNION\` costs a sort or hash over the whole result.
- \`UNION\`, because \`UNION ALL\` is non-standard.
  > Both are standard SQL.`}
/>

<MultipleChoice
  markdown={`What does partition pruning depend on?

- The table being clustered.
  > Clustering is a separate, complementary mechanism.
- [o] The query filtering directly on the partition column, in a form the engine can evaluate before reading data.
  > It is why the partition column should be the one people actually filter on — almost always a date.
- The number of partitions being a power of two.
  > No such requirement.
- Statistics being refreshed.
  > Pruning uses partition metadata, not table statistics.`}
/>

<MultipleChoice
  markdown={`What is a materialized view, and what is its cost?

- A view that is recomputed on every query.
  > That is an ordinary view.
- [o] A stored, precomputed result that speeds up repeated queries, at the cost of storage and of being stale until refreshed.
  > Some engines refresh incrementally on write; others need a scheduled full refresh, which is a pipeline concern.
- A view restricted to certain columns.
  > Column restriction is just a projection.
- A temporary table scoped to a session.
  > Temp tables vanish with the session.`}
/>

<MultipleChoice
  markdown={`Which returns rows present in the left table but absent from the right?

- \`INNER JOIN\` with \`IS NULL\`.
  > An inner join has already dropped the unmatched rows.
- [o] \`LEFT JOIN ... WHERE right.key IS NULL\`, or equivalently \`NOT EXISTS\`.
  > \`NOT IN\` expresses the same intent but returns nothing at all if the subquery yields a single \`NULL\`.
- \`FULL OUTER JOIN\` with no filter.
  > That returns everything from both sides.
- \`CROSS JOIN\` with a filter.
  > A cross join multiplies rows before anything is filtered.`}
/>

<MultipleChoice
  markdown={`When is a \`CROSS JOIN\` the right tool?

- Never; it is always a mistake.
  > It is the correct tool in several modelling situations.
- [o] When you deliberately need every combination — a date spine crossed with every store, say, to produce a dense grid before joining sparse facts.
  > The accidental version, from a missing join condition, is what gives it its reputation.
- When the join key is missing from one table.
  > A missing key is a modelling problem to fix, not to cross-join around.
- When joining more than three tables.
  > Table count is irrelevant.`}
/>

## Data modeling

<MultipleChoice
  markdown={`What does the grain of a fact table define?

- How many partitions it needs.
  > Partitioning follows from query patterns and size.
- [o] Exactly what one row represents, which determines which dimensions apply and whether a measure can be summed.
  > "One row per order line per day" is testable with a uniqueness assertion; a table with no agreed grain accumulates double counting.
- The physical sort order of the table.
  > That is clustering.
- The level of access control applied.
  > Security is unrelated.`}
/>

<MultipleChoice
  markdown={`What is the difference between a star and a snowflake schema?

- A star has more tables.
  > A snowflake has more, since its dimensions are split.
- [o] A star keeps dimensions flat and denormalized around the fact; a snowflake normalizes them into sub-dimensions, adding joins.
  > The star trades some redundancy for fewer joins and simpler queries, which is usually the right trade in a warehouse.
- A snowflake supports more fact tables.
  > Both support any number.
- A star cannot express hierarchies.
  > Hierarchies live inside the flat dimension as columns.`}
/>

<MultipleChoice
  markdown={`Which SCD type preserves full history with validity ranges?

- Type 0.
  > Type 0 refuses changes outright, retaining the original value.
- [o] Type 2.
  > A new row per version with effective dates and a current flag, joined from facts on the surrogate key that was current at the time.
- Type 1.
  > Type 1 overwrites and keeps no history.
- Type 3.
  > Type 3 keeps only one prior value in an extra column.`}
/>

<MultipleChoice
  markdown={`What are SCD Types 4 and 6?

- Two names for the same technique.
  > They are distinct.
- [o] Type 4 splits fast-changing attributes into a separate history table; Type 6 combines Types 1, 2, and 3 so a row carries both current and historical values.
  > Type 6 is sometimes written as "1 + 2 + 3", which is where the number comes from.
- Type 4 deletes old rows; Type 6 archives them.
  > Neither discards history.
- Type 4 applies to facts and Type 6 to dimensions.
  > Both are dimension techniques.`}
/>

<MultipleChoice
  markdown={`What is 3NF, in one sentence?

- Every table has a primary key.
  > That is closer to 1NF's spirit and a general requirement.
- [o] Every non-key attribute depends on the key, the whole key, and nothing but the key — so no transitive dependencies remain.
  > It is what prevents the same fact being stored in two places and drifting apart under update.
- Every column holds an atomic value.
  > That is 1NF.
- No table has more than one foreign key.
  > Foreign key count is unconstrained.`}
/>

<MultipleChoice
  markdown={`What is a data vault, and when would you choose it over a star schema?

- A backup format for warehouse tables.
  > It is a modelling methodology, not a backup.
- [o] Hubs (business keys), links (relationships), and satellites (attributes with history), chosen when auditability and absorbing many changing sources matter more than query ergonomics.
  > It is insert-only and highly normalized, so a dimensional presentation layer is usually built on top for consumers.
- A star schema with all history removed.
  > It retains more history, not less.
- A NoSQL alternative to dimensional modelling.
  > It is implemented in relational warehouses.`}
/>

<MultipleChoice
  markdown={`What does "grain mismatch" mean?

- Two tables using different date formats.
  > Formatting is a parsing issue.
- [o] Joining or aggregating tables whose rows represent different things — order headers against order lines, say — so measures duplicate or fail to align.
  > The fix is to aggregate one side to the other's grain before joining, rather than joining and hoping.
- A partition key with the wrong cardinality.
  > That is a partitioning problem.
- A dimension with missing members.
  > That is a referential integrity problem.`}
/>

<MultipleChoice
  markdown={`Why use a date dimension rather than date functions?

- Date functions are not supported in most warehouses.
  > They are universally supported.
- [o] It puts fiscal periods, holidays, week-start conventions, and business-day flags in one governed place, and lets a join do work that would otherwise be repeated logic in every query.
  > It is also what makes "compare to the same week last year" a join rather than a bespoke expression.
- It makes queries run faster in all cases.
  > Any speed benefit is secondary and situational.
- It is required for partitioning.
  > Partitioning uses a column, not a dimension.`}
/>

<MultipleChoice
  markdown={`What is a surrogate key sequence's advantage over a UUID?

- UUIDs cannot be primary keys.
  > They can.
- [o] Sequential integers are compact, compress and sort well, and keep clustered storage from fragmenting; random UUIDs scatter writes and are four times wider.
  > UUIDs win when keys must be generated independently across systems without coordination, which is a real trade rather than a wrong answer.
- Sequences guarantee uniqueness across systems.
  > That is precisely what UUIDs offer and sequences do not.
- UUIDs cannot be indexed.
  > They index fine; they just index worse.`}
/>

<MultipleChoice
  markdown={`How do you model a many-to-many between facts and a dimension?

- Duplicate the fact row per dimension member.
  > Duplication breaks the grain and inflates every measure.
- [o] Introduce a bridge table holding the pairs, ideally with an allocation weight so measures can be apportioned instead of double counted.
  > Without the weight, "revenue by product category" for a multi-category order counts the revenue once per category.
- Store the dimension keys as a comma-separated list.
  > This is unjoinable and unqueryable without parsing.
- Create a separate fact table per dimension member.
  > Unmaintainable, and it fragments the measure.`}
/>

<MultipleChoice
  markdown={`What is a periodic snapshot fact table for?

- Recording every individual transaction.
  > That is a transaction fact.
- [o] Capturing state at regular intervals — daily balances, month-end inventory — so questions about levels rather than events can be answered directly.
  > Its measures are typically semi-additive: summable across accounts, not across days.
- Storing a backup of a fact table.
  > It is a modelling pattern, not a backup.
- Tracking milestones of a long-running process.
  > That is an accumulating snapshot.`}
/>

<MultipleChoice
  markdown={`A dimension attribute changes and history does not matter. Which type applies, and what is the risk?

- Type 2, with the risk of table growth.
  > Type 2 is what you use when history *does* matter.
- [o] Type 1: overwrite in place. The risk is that "history does not matter" is often wrong, and prior reports silently change when re-run.
  > Once the old value is gone it cannot be recovered, which is why Type 2 is often the safer default for anything used in reporting.
- Type 0, with the risk of stale data.
  > Type 0 rejects the change entirely.
- Type 3, with the risk of losing the current value.
  > Type 3 retains both current and one prior value.`}
/>

<MultipleChoice
  markdown={`What is a mini-dimension, and what problem does it solve?

- A dimension with fewer than 100 rows.
  > Size alone does not define it.
- [o] Frequently-changing attributes split out of a large dimension into their own table, so Type 2 versioning does not explode the row count of the main dimension.
  > Demographic bands on a customer dimension are the classic case.
- A dimension used by only one fact table.
  > That is simply a non-conformed dimension.
- A denormalized copy of a dimension for BI.
  > That is a mart-level convenience table.`}
/>

<MultipleChoice
  markdown={`What is the difference between a bus matrix and a data mart?

- They are the same artifact at different scales.
  > One is a plan, the other a built thing.
- [o] A bus matrix is the planning grid of business processes against conformed dimensions; a data mart is a built, queryable subject area.
  > The matrix is what keeps independently-built marts conformable rather than accidentally incompatible.
- A bus matrix is a physical table.
  > It is documentation.
- A data mart contains only aggregates.
  > Marts usually contain detail as well.`}
/>

<MultipleChoice
  markdown={`How do you handle a fact row whose dimension member has not arrived yet?

- Reject the fact and alert.
  > Alerting is reasonable; rejecting loses the event.
- [o] Assign it a reserved "unknown" dimension key, then repair it once the real member lands.
  > Every dimension carrying an explicit unknown row is what stops an inner join from silently deleting facts.
- Insert a dimension row with the key and \`NULL\` attributes.
  > This creates a placeholder indistinguishable from a real member, which then collides when the genuine row arrives.
- Use an outer join everywhere instead.
  > Outer joins mask the problem and leave \`NULL\`s scattered through downstream logic.`}
/>

## Warehousing & storage

<MultipleChoice
  markdown={`Why is columnar storage faster for analytical queries?

- Columns compress into a single file per table.
  > File layout is not the mechanism.
- [o] A query reads only the columns it references, and values within a column are homogeneous so they compress far better — less I/O on both counts.
  > It is also why \`SELECT *\` is disproportionately expensive in a columnar store.
- Columnar formats keep the whole table in memory.
  > Memory residency is unrelated to layout.
- Rows are stored sorted by primary key.
  > Sorting is a separate choice.`}
/>

<MultipleChoice
  markdown={`What makes a good partition key?

- The column with the most distinct values.
  > High cardinality produces many tiny partitions and the small files problem.
- [o] A low-to-moderate cardinality column that queries reliably filter on, most often a date, producing partitions of a workable size.
  > The two tests are "do queries filter on it" and "are the resulting partitions neither tiny nor enormous".
- The primary key.
  > A unique key is the worst possible partition key.
- Whichever column is listed first in the schema.
  > Column order carries no meaning here.`}
/>

<MultipleChoice
  markdown={`How do Parquet, ORC, and Avro differ?

- They are interchangeable columnar formats.
  > Avro is not columnar.
- [o] Parquet and ORC are columnar and suit analytical scans; Avro is row-based with a strong schema-evolution story, which suits streaming and record-at-a-time writes.
  > Kafka pipelines commonly land Avro and convert to Parquet for the analytical layer.
- Avro compresses better than both.
  > Columnar formats compress better on analytical data.
- ORC is a compressed form of Parquet.
  > They are independent formats.`}
/>

<MultipleChoice
  markdown={`Why does compression work better in a columnar format?

- Columnar files are smaller before compression.
  > Uncompressed size is comparable.
- [o] All values in a column share a type and often a narrow range, so run-length, dictionary, and delta encodings apply where a mixed-type row would defeat them.
  > A low-cardinality string column can compress by an order of magnitude through dictionary encoding alone.
- Compression algorithms only work on numeric data.
  > They work on any bytes; homogeneity is what raises the ratio.
- Columnar files skip compressing the headers.
  > Header size is negligible.`}
/>

<MultipleChoice
  markdown={`What is the small files problem, and what causes it?

- Files smaller than the block size are rejected.
  > They are accepted, just inefficient.
- [o] Thousands of tiny files impose per-file open and metadata overhead that dwarfs the read; streaming micro-batches and over-partitioning are the usual causes.
  > Compaction into roughly 128 MB to 1 GB files is the standard remedy.
- Small files cannot be compressed.
  > They compress, just less effectively.
- It only affects HDFS.
  > Object stores suffer from it too, through request overhead and listing cost.`}
/>

<MultipleChoice
  markdown={`Why did ELT largely replace ETL?

- Transformation logic became simpler.
  > It generally became more complex.
- [o] Cheap, elastic warehouse compute made it practical to load raw data first and transform in place, where the transformations are versioned SQL rather than a separate processing tier.
  > Keeping the raw data also means a logic change can be re-applied without re-extracting from the source.
- Sources stopped supporting extraction.
  > Extraction is unchanged.
- ETL cannot handle semi-structured data.
  > It can; the shift was economic and operational.`}
/>

<MultipleChoice
  markdown={`What most drives cost in a cloud data warehouse?

- The number of tables.
  > Table count is close to free.
- [o] Bytes scanned or compute-seconds consumed, both of which track how much data queries read.
  > It is why partitioning, clustering, narrow column selection, and materializing repeated heavy work are the levers that matter.
- The number of users.
  > Seat licensing exists but is rarely the dominant line.
- Storage volume.
  > Storage is usually the cheapest component by a wide margin.`}
/>

<MultipleChoice
  markdown={`What is a lakehouse?

- A warehouse with a data lake attached.
  > Coexistence is not the architecture.
- [o] Open table formats such as Delta, Iceberg, or Hudi layered over object storage, adding ACID transactions, schema enforcement, and time travel to lake-scale files.
  > One copy of the data then serves SQL engines and Spark or Python alike, which is the point.
- A data lake queried through a BI tool.
  > A connector adds no transactional guarantees.
- A warehouse that stores only Parquet.
  > File format alone is not the distinction.`}
/>

<MultipleChoice
  markdown={`How does schema evolution differ between Avro and Parquet?

- Neither supports it.
  > Both do, differently.
- [o] Avro carries a writer schema with the data and resolves it against a reader schema, handling added, removed, and renamed (aliased) fields; Parquet supports evolution too, but is more constrained around type changes and ordering.
  > It is why Avro is favoured at the ingestion boundary where sources change unpredictably.
- Parquet requires rewriting all historical files on any change.
  > Adding a column does not require a rewrite.
- Avro requires the schema to be embedded in every record.
  > The schema is per file, or held in a registry.`}
/>

<MultipleChoice
  markdown={`What is predicate and projection pushdown?

- Two names for partition pruning.
  > Pruning is a related but coarser mechanism.
- [o] Pushing filters and the column list down into the file scan, so the reader skips row groups and columns instead of returning everything for the engine to discard.
  > Parquet's per-row-group min/max statistics are what make predicate pushdown effective.
- Moving computation from the client to the server.
  > That is a different architectural idea.
- Rewriting joins as subqueries.
  > Unrelated to scan behavior.`}
/>

<MultipleChoice
  markdown={`What is the difference between OLTP and OLAP storage layout?

- OLTP is columnar and OLAP is row-based.
  > This has them the wrong way round.
- [o] OLTP stores rows together so a single record is read or written in one place; OLAP stores columns together so a scan over few columns reads far less data.
  > It follows directly from the workload: point reads and writes versus wide aggregate scans.
- Both are columnar; only the indexes differ.
  > Transactional systems are overwhelmingly row-oriented.
- The layout is identical; only the hardware differs.
  > Layout is the defining difference.`}
/>

<MultipleChoice
  markdown={`What does clustering (or sorting) within a partition buy you?

- It reduces the number of partitions.
  > Partition count is unchanged.
- [o] Rows with similar values sit together, so per-block min/max statistics let the engine skip blocks that cannot match the filter.
  > It is the finer-grained companion to partition pruning, and it is where high-cardinality filter columns belong.
- It compresses the partition further.
  > Compression often does improve, but skipping is the mechanism that matters.
- It enforces uniqueness within the partition.
  > No constraint is implied.`}
/>

<MultipleChoice
  markdown={`A pipeline writes 5,000 files of 2 MB each per hour. What should you change?

- Nothing; more files parallelize better.
  > Past the parallelism you can actually use, files cost more than they return.
- [o] Compact them into far fewer, larger files — roughly 128 MB to 1 GB — either at write time or in a periodic compaction job.
  > Per-file open, metadata, and object-store request overhead is what dominates otherwise.
- Switch from Parquet to CSV.
  > That loses columnar reads and compression, making things worse.
- Add more partitions.
  > More partitions produces more, smaller files.`}
/>

<MultipleChoice
  markdown={`Why does \`SELECT *\` cost disproportionately more in a columnar warehouse?

- It disables the query cache.
  > Caching keys on the query text; the column list is not the issue.
- [o] Columnar storage lets a query read only the columns it names, and \`*\` gives that up, reading every column including large rarely-used ones.
  > On a wide table it can be the difference between scanning gigabytes and scanning terabytes.
- It forces a full sort.
  > No sort is implied.
- It prevents partition pruning.
  > Pruning depends on the \`WHERE\` clause, not the projection.`}
/>

<MultipleChoice
  markdown={`What does time travel in a lakehouse table format give you?

- Automatic backups to cold storage.
  > Backup is a separate mechanism.
- [o] The ability to query the table as of an earlier version or timestamp, which makes reproducing a report and recovering from a bad write straightforward.
  > Retention of old snapshots costs storage, so a vacuum or expiry policy is part of operating it.
- Faster queries on historical partitions.
  > No speed benefit is implied.
- Scheduled rollback of failed pipelines.
  > It enables rollback; it does not schedule it.`}
/>

## Pipelines & orchestration

<MultipleChoice
  markdown={`What makes a pipeline idempotent, and why does it matter most?

- It runs in under an hour.
  > Duration is unrelated.
- [o] Re-running it for the same input window produces the same result, which is what makes retries, backfills, and recovery from partial failure safe.
  > The usual implementations are delete-then-insert per partition, or a merge on a unique key. Blind appends break it.
- It never writes to the same table twice.
  > Rewriting the same partition is exactly how idempotency is achieved.
- It has no external dependencies.
  > Dependencies are orthogonal.`}
/>

<MultipleChoice
  markdown={`What does an orchestrator give you over cron?

- Lower latency between tasks.
  > Latency is comparable.
- [o] Dependency-aware scheduling, retries, backfills, observability into each run, and a place for failure to be visible rather than silent.
  > Cron runs a command at a time and knows nothing about whether the thing it depends on succeeded.
- Guaranteed exactly-once execution.
  > Neither provides that; the task must be idempotent.
- The ability to run tasks in parallel.
  > Cron can start parallel jobs; it just cannot coordinate them.`}
/>

<MultipleChoice
  markdown={`Which is a common DAG anti-pattern?

- Splitting work into many small tasks.
  > Granularity aids retries and observability.
- [o] A single monolithic task doing extract, transform, and load together, so a failure at the end re-runs everything and the logs say only "failed".
  > The opposite extreme — thousands of trivial tasks — has its own scheduler overhead, so the balance is per-pipeline.
- Declaring explicit dependencies between tasks.

<MultipleChoice
  markdown={`What is the difference between a transformation and an action in Spark?

<MultipleChoice
  markdown={`Why is a shuffle expensive?

  > Recomputation happens only on failure.
- [o] It redistributes data across the network by key, writing intermediate files and serializing everything, so it is bounded by disk and network rather than CPU.

- It disables parallelism.

<MultipleChoice
  markdown={`What distinguishes a narrow from a wide dependency?

- [o] A narrow dependency means each output partition draws from one input partition, so no shuffle is needed; a wide dependency draws from many and forces one.

<MultipleChoice
  markdown={`What is data skew, and how do you address it?

- [o] A few keys holding a disproportionate share of the rows, so one task runs far longer than the rest; salting the hot key, or broadcasting the small side, spreads the work.
  > The tell is a stage where 199 of 200 tasks finish quickly and one runs for an hour.
- Data that does not fit the schema.
  > That is a validation problem.
- Partitions of unequal file size on disk.
  > Related symptom, but skew is about key distribution.`}

<MultipleChoice
  markdown={`When is a broadcast join the right choice?

- [o] When one side is small enough to fit in each executor's memory, so it can be copied everywhere and the large side never shuffles.

- When the join key is unique.
  > Uniqueness does not determine the strategy.
- When the tables are already sorted.

<MultipleChoice
  markdown={`Why is \`reduceByKey\` preferred over \`groupByKey\`?

- [o] It combines values on the map side before shuffling, so far less data crosses the network; \`groupByKey\` shuffles every value.

<MultipleChoice
  markdown={`How does Spark achieve fault tolerance?

- [o] By recording the lineage of transformations, so a lost partition can be recomputed from its inputs rather than restored from a copy.

<MultipleChoice

- [o] It pulls every row to the driver, which has finite memory, so a large result crashes the driver rather than the executors.

<MultipleChoice
  markdown={`When is caching a DataFrame worth it?

<MultipleChoice

<MultipleChoice

- [o] Spark keeps intermediate results in memory across stages and optimizes a whole DAG at once, where MapReduce writes to disk between every map and reduce.

  markdown={`Why does Spark use lazy evaluation?

## Streaming

<MultipleChoice
  markdown={`What does a Kafka partition guarantee?

- Global ordering across the whole topic.
  > Ordering is per partition only.
- [o] Ordering within that partition, and that one partition is consumed by at most one consumer in a group at a time.
  > It is why messages that must stay ordered relative to each other need a shared partition key.
- Exactly-once delivery.
  > That requires transactions and idempotent producers on top.
- That each message is delivered to every consumer.
  > Within a group, each message goes to one consumer; separate groups each get a copy.`}
/>

<MultipleChoice
  markdown={`What happens when a consumer group has more consumers than partitions?

- Throughput increases proportionally.
  > It cannot; there is nothing more to assign.
- [o] The surplus consumers sit idle, since a partition is assigned to only one consumer in the group.
  > Partition count is therefore the ceiling on a group's parallelism, and it is why it is chosen with headroom.
- Partitions are split automatically.
  > Partition count only changes by explicit reconfiguration.
- Messages are duplicated across consumers.
  > Duplication happens across groups, not within one.`}
/>

<MultipleChoice
  markdown={`What does committing an offset mean?

- Deleting the messages up to that point.
  > Retention governs deletion, independently of any consumer.
- [o] Recording how far this consumer group has progressed, so a restart or a rebalance resumes from there instead of the beginning.
  > Committing before processing risks losing messages; committing after risks reprocessing them, which is why idempotent handling matters.
- Acknowledging receipt to the producer.
  > Producers get acknowledgements from brokers, not consumers.
- Locking the partition.
  > Assignment, not offsets, controls exclusivity.`}
/>

<MultipleChoice
  markdown={`What does at-least-once delivery mean for your consumer?

- Nothing; the broker deduplicates.
  > Kafka does not deduplicate on the consumer's behalf.
- [o] A message can be delivered more than once, so the handler must be idempotent — keyed upserts, or a deduplication store on a message id.
  > Most production systems choose at-least-once plus idempotency over the coordination cost of true exactly-once.
- Messages may be lost but never duplicated.
  > That is at-most-once.
- Each message is processed exactly once.
  > That is a stronger guarantee requiring transactional coordination.`}
/>

<MultipleChoice
  markdown={`What is the difference between event time and processing time?

- Event time is when the record was written to Kafka.
  > That is closer to ingestion time, a third distinct notion.
- [o] Event time is when the thing actually happened; processing time is when your system got round to handling it.
  > Windowing on event time gives results that stay correct across replays and delays; processing time does not.
- They are the same when the pipeline is fast enough.
  > They converge, but never provably coincide.
- Processing time is only relevant in batch systems.
  > It is a streaming concept.`}
/>

<MultipleChoice
  markdown={`What does a watermark represent?

- The maximum size of a window.
  > Window size is configured separately.
- [o] The system's assertion that no events older than this timestamp are still expected, allowing a window to be closed and emitted.
  > It is a heuristic trade: a later watermark waits for more stragglers at the cost of latency.
- The point at which a consumer last committed.
  > That is an offset.
- The threshold at which backpressure begins.
  > Backpressure is unrelated.`}
/>

<MultipleChoice
  markdown={`What are the main window types in stream processing?

- Fixed, floating, and dynamic.
  > Not the standard vocabulary.
- [o] Tumbling (fixed, non-overlapping), hopping or sliding (fixed, overlapping), and session (bounded by a gap of inactivity).
  > Session windows are the natural fit for user activity, since their length is determined by behavior rather than a clock.
- Batch, micro-batch, and continuous.
  > Those describe execution models.
- Time, count, and key.
  > Count-based windows exist, but this is not the standard triad.`}
/>

<MultipleChoice
  markdown={`How should late-arriving data be handled once its window has closed?

- Discard it silently.
  > Silent loss is the outcome you are trying to avoid noticing too late.
- [o] Choose deliberately: allow a grace period and update the emitted result, route it to a side output for separate handling, or drop it with a metric so the volume is visible.
  > The wrong answer is having no policy, which usually means dropping it invisibly.
- Reopen the window indefinitely.
  > Unbounded state grows until the job fails.
- Reprocess the entire stream.
  > A full replay is a recovery mechanism, not routine handling.`}
/>

<MultipleChoice
  markdown={`What is log compaction in Kafka?

- Compressing messages to save disk.
  > That is message compression, configured separately.
- [o] Retaining at least the most recent value per key indefinitely, discarding older values for the same key.
  > It turns a topic into a changelog you can replay to rebuild current state, which is what makes it suit CDC and state stores.
- Deleting messages older than the retention period.
  > That is time-based retention, the other policy.
- Merging small segment files.
  > Segment management is internal housekeeping.`}
/>

<MultipleChoice
  markdown={`What is backpressure, and how do streaming systems handle it?

- A spike in producer throughput.
  > The spike is the cause; backpressure is the response.
- [o] The signal that a consumer cannot keep up, handled by slowing the source, buffering to bounded storage, or shedding load deliberately.
  > A system with no backpressure mechanism instead exhausts memory and fails, which is strictly worse than slowing down.
- Messages being delivered out of order.
  > Ordering is a separate concern.
- The latency added by a watermark.
  > Watermark delay is a deliberate correctness trade.`}
/>

<MultipleChoice
  markdown={`How is exactly-once processing achieved in Kafka?

- By setting \`acks=all\` on the producer.
  > That improves durability, not deduplication.
- [o] With an idempotent producer plus transactions spanning the consume-process-produce cycle, so offsets and output commit atomically.
  > It holds within Kafka. The moment the output goes to an external system, the practical answer is at-least-once plus an idempotent write.
- By committing offsets before processing.
  > That yields at-most-once, losing messages on failure.
- By disabling retries.
  > Disabling retries loses messages rather than deduplicating them.`}
/>

<MultipleChoice
  markdown={`How does a streaming join differ from a batch join?

- It cannot join on more than one key.
  > Key count is unconstrained.
- [o] Both sides arrive over time, so the join needs buffered state bounded by a window, and a match may simply never arrive.
  > Deciding how long to hold state, and what to do with unmatched rows when it expires, is the design work a batch join never requires.
- It produces the same result as a batch join with no extra considerations.
  > State and time make it materially different.
- It requires both streams to be sorted.
  > Ordering is per partition and not a precondition.`}
/>

<MultipleChoice
  markdown={`How do you make a Kafka consumer idempotent?

- Commit offsets more frequently.
  > Frequent commits narrow the duplicate window without closing it.
- [o] Key the work so reprocessing converges — an upsert on a natural key, or a processed-id store checked before acting.
  > Once the handler is idempotent, at-least-once delivery stops being a problem worth engineering around.
- Process messages in a single thread.
  > Concurrency is not the source of duplicates.
- Increase the session timeout.
  > A longer timeout reduces rebalances but does not make reprocessing safe.`}
/>

<MultipleChoice
  markdown={`Why does the number of partitions in a Kafka topic matter?

- It determines how long messages are retained.
  > Retention is configured separately.
- [o] It caps a consumer group's parallelism, and it fixes the unit of ordering — and increasing it later changes key-to-partition mapping, breaking per-key ordering for existing keys.
  > That last point is why partition count is chosen with headroom rather than tuned reactively.
- It controls the replication factor.
  > Replication is an independent setting.
- More partitions always mean higher throughput.
  > Past a point, more partitions add broker overhead and rebalance cost.`}
/>

<MultipleChoice
  markdown={`When should a streaming pipeline be chosen over batch?

- Whenever the data volume is large.
  > Large volumes are often better served by batch.
- [o] When the value of the result decays within minutes — fraud detection, alerting, live personalization — enough to justify the extra operational complexity.
  > Batch is simpler to reason about, cheaper to reprocess, and easier to test; streaming should be a requirement, not a default.
- Whenever the source is a message queue.
  > A queue can perfectly well be drained in batches.
- When the pipeline must be idempotent.
  > Idempotency is required in both.`}
/>

  > Streaming row-at-a-time work with constant memory is where generators still win.
- Whenever reading a CSV.
  > \`csv\` from the standard library is often the better tool for a streaming read.
- When you need to guarantee type safety.
  > pandas dtypes are flexible rather than a guarantee.`}
/>

<MultipleChoice
  markdown={`What is the most common performance pitfall in Python data code?

- Using too many functions.
  > Function call overhead is rarely the bottleneck.
- [o] Doing per-row work in the interpreter — \`iterrows\`, \`apply(axis=1)\`, or appending to a DataFrame in a loop — where a vectorized or bulk operation exists.
  > Appending to a DataFrame in a loop is quadratic, since each append copies the whole frame.
- Reading files instead of databases.
  > Source choice is a design decision, not a pitfall.
- Using generators instead of lists.
  > Generators are usually the improvement.`}

<MultipleChoice
  markdown={`How do you split an iterable into fixed-size batches without materializing it?

- \`[items[i:i+n] for i in range(0, len(items), n)]\`
  > Slicing requires a sequence with a known length, so it will not work on a generator.
- [o] Repeatedly take \`n\` items with \`itertools.islice\` until the iterator is exhausted, or use \`itertools.batched\` on Python 3.12+.
  > Both keep memory bounded to one batch, which is the whole point when the source is a stream.
- Convert to a list first, then slice.
  > That materializes everything.
- Use \`zip(*[iter(items)] * n)\`.
  > A well-known trick, but it silently drops the final partial batch.`}
