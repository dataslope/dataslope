"Here's an events table with duplicates — give me the latest row per
user" is a near-universal data-engineering SQL question. The tool is
`ROW_NUMBER()` in a window, then keep rank 1.

## Challenge: latest event per user

<SqlChallengeCard
  dialect="duckdb"
  title="Most recent event per user"
  instructions={`The table \`events\` has columns \`user_id\`, \`event_time\`, and \`status\`, with several rows per user. Return exactly **one row per user** — the row with the most recent \`event_time\`. Columns: \`user_id\`, \`event_time\`, \`status\`.`}
  initSql={`CREATE TABLE events AS SELECT * FROM (VALUES
  (1, TIMESTAMP '2024-01-01 10:00', 'signup'),
  (1, TIMESTAMP '2024-01-03 09:00', 'active'),
  (2, TIMESTAMP '2024-01-02 12:00', 'signup'),
  (2, TIMESTAMP '2024-01-05 08:00', 'churn'),
  (2, TIMESTAMP '2024-01-04 15:00', 'active'),
  (3, TIMESTAMP '2024-01-01 11:00', 'signup')
) AS t(user_id, event_time, status);`}
  starterCode={`-- Keep only the most recent row per user_id.
SELECT
  user_id,
  event_time,
  status
FROM events
-- use a window function to rank within each user, then keep rank 1;`}
  solutionSql={`SELECT
  user_id,
  event_time,
  status
FROM events
QUALIFY ROW_NUMBER() OVER (
  PARTITION BY user_id
  ORDER BY event_time DESC
) = 1
ORDER BY user_id;`}
  tests={[
    {
      id: "row_count",
      name: "One row per user",
      description: "Three users → three rows",
      expectedRowCount: 3,
    },
    {
      id: "columns",
      name: "Has the required columns",
      description: "user_id, event_time, status",
      expectedColumnsInclude: ["user_id", "event_time", "status"],
    },
  ]}
/>

## Concept check

<MultipleChoice
  markdown={`Why \`ROW_NUMBER()\` here rather than \`RANK()\` or \`DENSE_RANK()\`?

- They're interchangeable for deduplication.
  > They differ on ties: if a user had two rows with the *same* \`event_time\`, \`RANK\`/\`DENSE_RANK\` would give both rank 1 and you'd keep both — defeating "one row per user."
- [o] \`ROW_NUMBER()\` guarantees a single row per partition even on ties, so filtering to \`= 1\` keeps exactly one.
  > It assigns distinct numbers within each partition no matter what, which is what "exactly one row per user" requires.
- \`RANK()\` can't be used in a window at all.
  > \`RANK()\` is a perfectly valid window function; it's just the wrong tie behavior for dedup.
- \`ROW_NUMBER()\` sorts the whole table, which is required.
  > Ordering happens *within* each partition for ranking; it isn't a global sort requirement.`}
/>
