## Data structures & algorithms

<MultipleChoice
  markdown={`What does Big-O notation describe?

- The memory an algorithm uses.
  > It describes whichever resource is being analyzed; time is just the most common.
- The best case running time.
  > Big-O is normally used for the upper bound; best case is usually written with Ω.
- [o] How the cost grows as the input grows.
  > Constants and lower-order terms are ignored. It answers "what happens at 10x the data", which is why an O(n log n) algorithm can lose to an O(n²) one on small inputs and still be the right choice.
- The exact number of operations an algorithm performs.
  > Constants and lower-order terms are deliberately discarded.`}
/>

<MultipleChoice
  markdown={`What is the average and worst-case lookup cost of a hash map?

- [o] O(1) on average, O(n) in the worst case.
  > The worst case is every key hashing to the same bucket. Java's HashMap mitigates this by converting a long collision chain into a balanced tree, giving O(log n) instead.
- O(n) on average.
  > Average O(n) would make hash maps useless.
- O(1) in both cases.
  > Worst case degrades when many keys collide into one bucket.
- O(log n) in both the average and worst cases.
  > That is a balanced tree, not a hash table.`}
/>

<MultipleChoice
  markdown={`When is a linked list genuinely preferable to a dynamic array?

- [o] When you already hold a reference to the node you are splicing.
  > The splice is then O(1) with no shifting. Without that reference you pay O(n) to find the node first, which is why arrays win in practice more often than the textbook suggests.
- When you need to sort the whole collection frequently.
  > Sorting a linked list is generally slower than sorting an array.
- When you need fast lookup by index.
  > Indexing a linked list is O(n); an array is O(1).
- When memory is tight.
  > Each node carries pointer overhead and destroys cache locality.`}
/>

<MultipleChoice
  markdown={`What does "amortized O(1)" mean for appending to a dynamic array?

- It is only O(1) when the capacity has been preallocated.
  > Preallocating removes the resizes entirely; amortization is what makes it O(1) without doing so.
- Every append takes constant time.
  > The append that triggers a resize copies every element.
- The first append is slow and the rest are fast.
  > Resizes recur as the array grows, not just at the start.
- [o] Most appends are O(1) and the occasional resize is O(n).
  > Doubling the capacity spreads that cost so the average over many appends stays constant. Growing by a constant amount instead of doubling would make the amortized cost O(n).`}
/>

<MultipleChoice
  markdown={`What are the time complexities of a binary heap's push and pop-min?

- O(log n) and O(n).
  > Popping sifts down through the height of the tree, which is O(log n).
- O(n log n) for both the push and the pop-min.
  > That is the cost of a full heapsort, not a single operation.
- O(1) and O(1).
  > Maintaining the heap property costs a sift.
- [o] O(log n) for both, with O(1) to peek at the minimum.
  > Building a heap from n items in one pass is O(n), which is better than n separate pushes.`}
/>

<MultipleChoice
  markdown={`Which traversal should you use to find the shortest path in an *unweighted* graph?

- Topological sort.
  > Topological sort orders a DAG; it does not compute distances.
- [o] Breadth-first search.
  > BFS explores by distance, so the first time it reaches a node it has done so via the fewest edges.
- Dijkstra's algorithm only.
  > Dijkstra works but is heavier than needed; with uniform weights it degenerates to BFS.
- Depth-first search.
  > DFS finds *a* path, with no guarantee it is the shortest.`}
/>

<MultipleChoice
  markdown={`How do you detect a cycle in a *directed* graph with DFS?

- Count edges and compare to nodes minus one.
  > That test applies to undirected trees only.
- Run BFS from every node.
  > Reachability alone does not identify a cycle in a directed graph.
- [o] Track the nodes currently on the recursion stack.
  > An edge back to one of those is a back edge, and therefore a cycle. Three colors (unvisited, in-progress, done) is the standard encoding. Kahn's algorithm is the iterative alternative.
- Track whether each node has already been visited before.
  > A revisited node may simply be reachable by two different paths, which is not a cycle.`}
/>

<MultipleChoice
  markdown={`What does Kahn's algorithm produce, and what does its failure tell you?

- A minimum spanning tree; failure means negative weights.
  > That is Kruskal's or Prim's territory.
- A shortest-path tree; failure means the graph is disconnected.
  > Kahn's does not compute distances.
- [o] A topological ordering, or proof of a cycle.
  > If it cannot place every node, the remainder contains one. It repeatedly removes nodes with in-degree zero, so a leftover set with no zero-in-degree node is exactly a cycle.
- A strongly connected component decomposition.
  > That is Tarjan's or Kosaraju's.`}
/>

<MultipleChoice
  markdown={`What is the complexity of Dijkstra's algorithm with a binary heap, and what breaks it?

- O(E log E), and it breaks on dense graphs.
  > Density affects the constant, not correctness.
- O(V + E), and it breaks on weighted graphs.
  > Weights are exactly what it is for; O(V + E) is BFS.
- [o] O((V + E) log V), and it breaks on negative edge weights.
  > Once a node is finalized Dijkstra never revisits it, which a negative edge could invalidate. Bellman-Ford handles negatives at O(VE).
- O(V²), and it breaks on graphs that are not connected.
  > O(V²) is the array implementation; disconnection is handled fine.`}
/>

<MultipleChoice
  markdown={`What are the average and worst-case complexities of search in an unbalanced BST?

- [o] O(log n) average and O(n) in the worst case.
  > Sorted insertion degenerates the tree into a linked list. Self-balancing variants (red-black, AVL) restore the O(log n) guarantee.
- O(log n) in both the average and the worst case.
  > Only a balanced tree guarantees the worst case.
- O(1) and O(log n).
  > Constant-time search would require hashing.
- O(n) and O(n log n).
  > Search never exceeds the tree's height.`}

<MultipleChoice
  markdown={`Which DFS traversal of a BST yields the keys in sorted order?

- Level-order.
  > Level-order is BFS, yielding keys by depth.
- Pre-order.
  > Pre-order visits the node before its left subtree, so it yields the root first.
- Post-order.
  > Post-order visits both subtrees before the node, useful for deletion and expression evaluation.
- [o] In-order.
  > Left, node, right. That is exactly ascending key order for a BST, and the reason in-order traversal is the standard way to validate one.`}

<MultipleChoice
  markdown={`What problem is a trie especially good at?

- [o] Prefix queries, in time proportional to the key length.
  > Autocomplete, longest-common-prefix, and dictionary matching all qualify, and the set size does not matter. The trade is memory: a node per character can dwarf a hash set unless the keys share prefixes heavily.
- Finding the k largest elements.
  > That is a heap's job.
- Range queries over numbers.
  > A balanced BST or a sorted array serves ranges better.
- Detecting duplicate entries using O(1) space.
  > A trie's whole cost is space.`}
/>

<MultipleChoice
  markdown={`\`mid = (lo + hi) / 2\` is a classic binary search bug in fixed-width integer languages. Why?

- It requires the array to be sorted descending.
  > Sort order is a precondition of the algorithm, not of this expression.
- [o] \`lo + hi\` can overflow the integer type.
  > \`lo + (hi - lo) / 2\` cannot, which is the standard fix. It is the bug that sat in the JDK's binary search for nine years. The other classic is a loop condition that never terminates.
- Integer division truncates, skipping elements.
  > Truncation is expected and correct here.
- It selects the wrong midpoint when the array length is even.
  > Either midpoint is fine on an even length.`}
/>

<MultipleChoice
  markdown={`What does the sliding-window technique optimize?

- Balancing a binary tree.
  > Unrelated to tree structure.
- Sorting an array that happens to be nearly sorted.
  > That calls for insertion sort or a heap.
- Searching an unsorted array.
  > A window offers nothing over a linear scan there.
- [o] Problems over contiguous subarrays or substrings.
  > Extending and shrinking a window beats re-examining every subarray, turning O(n²) into O(n). "Longest substring without repeating characters" is the canonical case, usually paired with a hash map of last-seen positions.`}
/>

<MultipleChoice
  markdown={`Quicksort's worst case is O(n²). When does it occur, and what mitigates it?

- When the array is too large for memory; mitigated by merge sort.
  > External sorting is a different problem.
- On reverse-sorted input; nothing can be done.
  > Pivot choice can be fixed.
- On input with many duplicates; mitigated by using a stable sort.
  > Duplicates hurt naive partitioning, but three-way partitioning fixes that specifically.
- [o] When the pivot consistently splits off a single element.
  > Sorted input with a first-element pivot is the classic trigger. A random or median-of-three pivot mitigates it. Introsort goes further, switching to heapsort once recursion gets too deep, which is what most standard libraries ship.`}
/>

<MultipleChoice
  markdown={`What makes a sort "stable", and when does it matter?

- It always runs in the same time regardless of input.
  > That is a consistency property, not stability.
- It uses O(1) extra space.
  > That is being in-place, which is often at odds with stability.
- [o] Equal elements keep their original relative order.
  > It matters when sorting by several keys in sequence. Sort by name, then stably by department, and within each department the names remain sorted. Quicksort is not stable; merge sort and Timsort are.
- It never crashes on malformed input.
  > Stability is about ordering, not robustness.`}
/>

<MultipleChoice
  markdown={`What is the difference between memoization and tabulation?

- [o] One is top-down and cached, the other bottom-up.
  > Memoization caches as the recursion goes; tabulation fills a table iteratively in dependency order. Memoization only computes the subproblems it needs; tabulation avoids recursion depth limits and is easier to space-optimize.
- They produce different answers.
  > Both solve the same recurrence.
- Tabulation applies only to one-dimensional problems.
  > Multi-dimensional tables are routine.
- Memoization is faster in every case.
  > Tabulation usually has lower constant overhead by avoiding recursion.`}
/>

<MultipleChoice
  markdown={`When is a greedy algorithm guaranteed to be optimal?

- Whenever it produces the same answer as brute force on small inputs.
  > Small-input agreement is evidence, not proof.
- [o] With optimal substructure and the greedy-choice property.
  > A locally best choice then belongs to some global optimum. Activity selection and Huffman coding qualify; 0/1 knapsack does not, which is why it needs dynamic programming.
- Whenever the problem involves maximizing a value.
  > Plenty of maximization problems defeat greedy approaches.
- When the input is sorted.
  > Sorting often enables a greedy algorithm but does not justify one.`}
/>

<MultipleChoice
  markdown={`When should you represent a graph as an adjacency matrix rather than an adjacency list?

- Always, on the grounds that a matrix is simpler to work with.
  > Simplicity costs O(V²) memory regardless of edge count.
- When the graph is a tree.
  > A tree is maximally sparse, the worst case for a matrix.
- When edges are weighted.
  > Both representations carry weights fine.
- [o] When the graph is dense, or edge checks must be O(1).
  > A sparse graph with a million nodes would need a terabyte-scale matrix, which is why lists are the default.`}
/>

<MultipleChoice
  markdown={`What does the two-pointer technique typically require of the input?

- That the input contains no duplicate values.
  > Duplicates are usually handled with a small skip step.
- That it fits in memory.
  > True but not the distinguishing requirement.
- [o] Some exploitable order, usually sortedness.
  > Moving a pointer then rules out a whole range of possibilities. "Find two numbers summing to a target in a sorted array" is O(n) with two pointers and O(n log n) if you have to sort first.

<MultipleChoice
  markdown={`Which of these is closest to the actual constraint that makes an API RESTful?

- Restricting yourself to just \`GET\` and \`POST\`.
  > Restricting the verb set works against the uniform interface.
- Returning JSON.

<MultipleChoice
  markdown={`Which URL best follows REST resource naming conventions?

- \`GET /users/delete/42\`
  > \`GET\` must not have side effects, and the action is again in the path.
- \`POST /createNewUser\`
  > The verb belongs in the HTTP method, not the path.
- [o] \`POST /users\`
  > Plural nouns identify collections; the method supplies the action. The created resource then lives at \`/users/{id}\`.
- \`POST /user/new/create\`

<MultipleChoice
  markdown={`Which HTTP methods are idempotent?

- \`POST\` and \`PUT\`.
  > \`POST\` creating a new resource each time is the standard non-idempotent case.
- Only \`GET\`.
  > Several others are too.
- [o] \`GET\`, \`PUT\`, \`DELETE\`, and \`HEAD\`.
  > Repeating any of them leaves the server in the same state. \`DELETE\` is idempotent even though the second call returns 404: the *state* is the same. \`POST\` and \`PATCH\` generally are not.
- All of them, since HTTP is stateless.
  > Statelessness of the protocol says nothing about the effect of a request.`}

<MultipleChoice
  markdown={`A payment client times out and retries. How do you stop a double charge?

- Reject any second request within 30 seconds.
  > A time window blocks legitimate requests and still lets late retries through.
- [o] Require a client-generated idempotency key.
  > Store the first result against it and return that for any repeat. It makes retrying safe without the client having to know whether the first attempt landed.

<MultipleChoice

- [o] One means unauthenticated, the other unauthorized.

<MultipleChoice
  markdown={`Why is offset pagination a poor fit for a large, frequently-changing collection?

- [o] Deep offsets scan and discard everything before them.
  > Rows inserted mid-pagination also shift the window, so items get skipped or repeated. Cursor (keyset) pagination, meaning "everything after this sorted key", avoids both problems.
- Offsets are hard-limited to around 10,000 rows.
  > No such universal limit exists, though some engines impose one.
- It cannot be combined with sorting.
  > It requires sorting to be meaningful at all.
- It requires a stateful server.

<MultipleChoice
  markdown={`Which approach to API versioning is most transparent to the client?

- Breaking changes with a migration guide, no version.
  > This shifts the whole cost onto every consumer at once.
- Deploying each version to a separate domain.
  > Workable but heavy, and it breaks relative links and cookie scoping.
- [o] A version in the URL path, such as \`/v1/users\`.

- Query parameter versioning, such as \`?version=1\`.
  > It works, but it mixes an API-wide concern into per-request parameters and complicates caching.`}

<MultipleChoice

- By observing when requests start failing.
  > Discovering a limit by tripping it is what the headers exist to avoid.
- From a dedicated endpoint, polled once every minute.
  > Polling for quota spends quota.
- From the API documentation only.

## Concurrency

<MultipleChoice
  markdown={`What is the difference between concurrency and parallelism?

- [o] One is about structure, the other about simultaneity.
  > Concurrency lets tasks make progress independently; parallelism executes them at the same instant on multiple cores. Concurrency is about dealing with many things at once; parallelism is about doing many things at once.
- Parallelism is concurrency with locks.
  > Locks are a coordination mechanism, not a definition.
- They are the same thing.
  > A single-core machine can be concurrent without ever being parallel.
- Concurrency requires multiple processes and parallelism multiple threads.
  > Both can be built from either.`}
/>

<MultipleChoice
  markdown={`How do processes and threads differ?

- Threads are faster because they skip the scheduler.
  > Both are scheduled by the OS.
- [o] Threads share memory; processes are isolated.
  > Sharing makes communication cheap and data races possible; isolation forces IPC. Isolation is why a crashing process cannot corrupt its siblings, and why process pools are used to sidestep Python's GIL.
- Processes cannot run in parallel.
  > Processes are the classic route to true parallelism.
- Threads have their own address space.
  > Sharing an address space is what defines them.`}
/>

<MultipleChoice
  markdown={`What is a race condition?

- A thread that runs faster than expected.
  > Speed alone is not a correctness problem.
- Two threads competing over one and the same lock.
  > Lock contention is expected behavior, not a bug.
- A deadlock that resolves itself.
  > A resolved deadlock is a livelock, which is different again.
- [o] Behavior that depends on the interleaving of operations.
  > The result then varies between runs. \`x = x + 1\` is three operations (read, add, write), and two threads can interleave them to lose an update.`}
/>

<MultipleChoice
  markdown={`What are the four conditions that must all hold for a deadlock?

- Shared memory, threads, locks, and recursion.
  > Deadlock needs none of these specifically.
- [o] Mutual exclusion, hold-and-wait, no preemption, and circular wait.
  > Breaking any one prevents deadlock, which is why a global lock ordering, breaking circular wait, is the usual practical fix.
- Starvation, livelock, priority inversion, and lock contention.
  > These are other concurrency pathologies.
- Two threads, two locks, one CPU, and no timeout.
  > These are incidental to one example rather than the general conditions.`}
/>

<MultipleChoice
  markdown={`How does a livelock differ from a deadlock?

- A livelock always resolves eventually.
  > It can persist indefinitely; that is what makes it a bug.
- A livelock involves only one thread.
  > It requires at least two interacting.
- [o] In one the threads are idle, in the other they are busy.
  > Deadlocked threads are blocked; livelocked ones keep changing state in response to each other and still make no progress. Two people stepping aside for each other in a corridor, forever. Randomized backoff is the classic fix.
- A livelock is caused by starvation of the CPU itself.
  > Starvation is a separate condition.`}
/>

<MultipleChoice
  markdown={`What is the difference between a mutex and a semaphore?

- A mutex cannot be released by the thread that acquired it.
  > That is exactly the thread that should release it.
- A mutex is faster.
  > Relative cost depends on the implementation.
- [o] One holder with ownership, against N holders without.
  > A mutex is typically owned by the thread that locked it; a counting semaphore admits up to N and has no ownership. A semaphore initialized to 1 behaves like a lock but without the ownership check, so it can legitimately be released by a different thread.
- A semaphore can only be used across processes.
  > Both come in intra- and inter-process forms.`}
/>

<MultipleChoice
  markdown={`Why does Python's GIL exist, and when does it actually hurt?

- It makes all Python code thread-safe.
  > It guarantees only that a single bytecode instruction is atomic; \`x += 1\` still races.
- [o] It serializes bytecode, hurting CPU-bound threading.
  > Simplifying memory management is the reason it exists; I/O-bound work is largely unaffected because threads release it during I/O. Threads release the GIL during I/O, which is why threading still helps a network-bound workload. CPU-bound work needs \`multiprocessing\` or a native extension that releases it.
- It prevents deadlocks, and it hurts when using locks.
  > It does not prevent deadlocks in user code.
- It only affects Python 2.
  > It is present in CPython 3 as well, though free-threaded builds are now available.`}
/>

<MultipleChoice
  markdown={`What happens when you call a blocking function inside an async coroutine?

- The runtime moves it to a background thread.
  > No automatic offloading happens.
- It raises an exception.
  > It runs perfectly, which is what makes the bug hard to spot.
- [o] It blocks the entire event loop until it returns.
  > Every other coroutine stalls in the meantime. The fix is an async-native library, or \`run_in_executor\` / \`asyncio.to_thread\` to push the blocking call onto a thread pool.
- It runs concurrently anyway, since coroutines are threads.
  > Coroutines are not threads; a single-threaded loop interleaves them cooperatively.`}
/>

<MultipleChoice
  markdown={`Which workload is the best fit for \`multiprocessing\` over threads in Python?

- [o] A numerical transform over a large array in pure Python.
  > CPU-bound work needs separate interpreters to use multiple cores. The cost is process startup and pickling data across the boundary.
- Reading many small files.
  > File I/O releases the GIL, so threads suffice.
- Waiting on a long series of slow database queries.
  > Another I/O-bound case.
- Fetching 500 URLs.
  > Network waiting is I/O-bound; threads or async are lighter.`}
/>

<MultipleChoice
  markdown={`What does a thread pool buy you over creating a thread per task?

- It makes tasks run faster individually.
  > Per-task speed is unchanged, and pooling adds a small queueing overhead.
- [o] It bounds concurrency and amortizes thread creation.
  > A burst of 10,000 tasks does not then spawn 10,000 threads. The bound is the important half: unbounded thread creation exhausts memory and thrashes the scheduler.
- It guarantees the tasks run in submission order.
  > Ordering is not guaranteed unless the pool has a single worker.
- It removes the need for locks.
  > Shared state still needs protection.`}
/>
