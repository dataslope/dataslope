## Data structures & algorithms

<MultipleChoice
  markdown={`What does Big-O notation describe?

- The exact number of operations an algorithm performs.
  > Constants and lower-order terms are deliberately discarded.
- [o] How the cost grows as the input grows, ignoring constants and lower-order terms.
  > It answers "what happens at 10x the data", which is why an O(n log n) algorithm can lose to an O(n²) one on small inputs and still be the right choice.
- The best case running time.
  > Big-O is normally used for the upper bound; best case is usually written with Ω.
- The memory an algorithm uses.
  > It describes whichever resource is being analyzed; time is just the most common.`}
/>

<MultipleChoice
  markdown={`What is the average and worst-case lookup cost of a hash map?

- O(1) in both cases.
  > Worst case degrades when many keys collide into one bucket.
- [o] O(1) on average, O(n) in the worst case when every key hashes to the same bucket.
  > Java's HashMap mitigates this by converting a long collision chain into a balanced tree, giving O(log n) instead.
- O(log n) in both cases.
  > That is a balanced tree, not a hash table.
- O(n) on average.
  > Average O(n) would make hash maps useless.`}
/>

<MultipleChoice
  markdown={`When is a linked list genuinely preferable to a dynamic array?

- When you need fast lookup by index.
  > Indexing a linked list is O(n); an array is O(1).
- [o] When you insert or remove in the middle frequently *and already hold a reference to the node*, since the splice is O(1) with no shifting.
  > Without that reference you pay O(n) to find the node first, which is why arrays win in practice more often than the textbook suggests.
- When memory is tight.
  > Each node carries pointer overhead and destroys cache locality.
- When you need to sort the data often.
  > Sorting a linked list is generally slower than sorting an array.`}
/>

<MultipleChoice
  markdown={`What does "amortized O(1)" mean for appending to a dynamic array?

- Every append takes constant time.
  > The append that triggers a resize copies every element.
- [o] Most appends are O(1); the occasional resize is O(n), but doubling the capacity spreads that cost so the average over many appends stays constant.
  > Growing by a constant amount instead of doubling would make the amortized cost O(n).
- The first append is slow and the rest are fast.
  > Resizes recur as the array grows, not just at the start.
- It is O(1) only if the capacity is preallocated.
  > Preallocating removes the resizes entirely; amortization is what makes it O(1) without doing so.`}
/>

<MultipleChoice
  markdown={`What are the time complexities of a binary heap's push and pop-min?

- O(1) and O(1).
  > Maintaining the heap property costs a sift.
- [o] O(log n) for both, with O(1) to peek at the minimum.
  > Building a heap from n items in one pass is O(n), which is better than n separate pushes.
- O(log n) and O(n).
  > Popping sifts down through the height of the tree, which is O(log n).
- O(n log n) for both.
  > That is the cost of a full heapsort, not a single operation.`}
/>

<MultipleChoice
  markdown={`Which traversal should you use to find the shortest path in an *unweighted* graph?

- Depth-first search.
  > DFS finds *a* path, with no guarantee it is the shortest.
- [o] Breadth-first search.
  > BFS explores by distance, so the first time it reaches a node it has done so via the fewest edges.
- Dijkstra's algorithm only.
  > Dijkstra works but is heavier than needed; with uniform weights it degenerates to BFS.
- Topological sort.
  > Topological sort orders a DAG; it does not compute distances.`}
/>

<MultipleChoice
  markdown={`How do you detect a cycle in a *directed* graph with DFS?

- Track whether each node has been visited before.
  > A revisited node may simply be reachable by two different paths, which is not a cycle.
- [o] Track nodes currently on the recursion stack; an edge back to one of those is a back edge and therefore a cycle.
  > Three colors (unvisited, in-progress, done) is the standard encoding. Kahn's algorithm is the iterative alternative.
- Count edges and compare to nodes minus one.
  > That test applies to undirected trees only.
- Run BFS from every node.
  > Reachability alone does not identify a cycle in a directed graph.`}
/>

<MultipleChoice
  markdown={`What does Kahn's algorithm produce, and what does its failure tell you?

- A shortest-path tree; failure means the graph is disconnected.
  > Kahn's does not compute distances.
- [o] A topological ordering; if it cannot place every node, the remaining nodes contain a cycle.
  > It repeatedly removes nodes with in-degree zero, so a leftover set with no zero-in-degree node is exactly a cycle.
- A minimum spanning tree; failure means negative weights.
  > That is Kruskal's or Prim's territory.
- A strongly connected component decomposition.
  > That is Tarjan's or Kosaraju's.`}
/>

<MultipleChoice
  markdown={`What is the complexity of Dijkstra's algorithm with a binary heap, and what breaks it?

- O(V²), and it breaks on disconnected graphs.
  > O(V²) is the array implementation; disconnection is handled fine.
- [o] O((V + E) log V), and it breaks on negative edge weights.
  > Once a node is finalized Dijkstra never revisits it, which a negative edge could invalidate. Bellman-Ford handles negatives at O(VE).
- O(E log E), and it breaks on dense graphs.
  > Density affects the constant, not correctness.
- O(V + E), and it breaks on weighted graphs.
  > Weights are exactly what it is for; O(V + E) is BFS.`}
/>

<MultipleChoice
  markdown={`What are the average and worst-case complexities of search in an unbalanced BST?

- O(log n) and O(log n).
  > Only a balanced tree guarantees the worst case.
- [o] O(log n) average, O(n) worst case when inserted in sorted order and the tree degenerates into a linked list.
  > Self-balancing variants (red-black, AVL) restore the O(log n) guarantee.
- O(1) and O(log n).
  > Constant-time search would require hashing.
- O(n) and O(n log n).
  > Search never exceeds the tree's height.`}
/>

<MultipleChoice
  markdown={`Which DFS traversal of a BST yields the keys in sorted order?

- Pre-order.
  > Pre-order visits the node before its left subtree, so it yields the root first.
- [o] In-order.
  > Left, node, right. That is exactly ascending key order for a BST, and the reason in-order traversal is the standard way to validate one.
- Post-order.
  > Post-order visits both subtrees before the node, useful for deletion and expression evaluation.
- Level-order.
  > Level-order is BFS, yielding keys by depth.`}
/>

<MultipleChoice
  markdown={`What problem is a trie especially good at?

- Finding the k largest elements.
  > That is a heap's job.
- [o] Prefix queries over a set of strings (autocomplete, longest-common-prefix, dictionary matching) in time proportional to the key length rather than the set size.
  > The trade is memory: a node per character can dwarf a hash set unless the keys share prefixes heavily.
- Range queries over numbers.
  > A balanced BST or a sorted array serves ranges better.
- Detecting duplicates in O(1) space.
  > A trie's whole cost is space.`}
/>

<MultipleChoice
  markdown={`\`mid = (lo + hi) / 2\` is a classic binary search bug in fixed-width integer languages. Why?

- Integer division truncates, skipping elements.
  > Truncation is expected and correct here.
- [o] \`lo + hi\` can overflow the integer type on a large array; \`lo + (hi - lo) / 2\` cannot.
  > It is the bug that sat in the JDK's binary search for nine years. The other classic is a loop condition that never terminates.
- It selects the wrong midpoint when the array length is even.
  > Either midpoint is fine on an even length.
- It requires the array to be sorted descending.
  > Sort order is a precondition of the algorithm, not of this expression.`}
/>

<MultipleChoice
  markdown={`What does the sliding-window technique optimize?

- Sorting a nearly-sorted array.
  > That calls for insertion sort or a heap.
- [o] Problems over contiguous subarrays or substrings, by extending and shrinking a window instead of re-examining every subarray, turning O(n²) into O(n).
  > "Longest substring without repeating characters" is the canonical case, usually paired with a hash map of last-seen positions.
- Searching an unsorted array.
  > A window offers nothing over a linear scan there.
- Balancing a binary tree.
  > Unrelated to tree structure.`}
/>

<MultipleChoice
  markdown={`Quicksort's worst case is O(n²). When does it occur, and what mitigates it?

- On reverse-sorted input; nothing can be done.
  > Pivot choice can be fixed.
- [o] When the pivot consistently splits off one element (sorted input with a first-element pivot is the classic trigger), mitigated by a random or median-of-three pivot.
  > Introsort goes further, switching to heapsort once recursion gets too deep, which is what most standard libraries ship.
- On input with many duplicates; mitigated by using a stable sort.
  > Duplicates hurt naive partitioning, but three-way partitioning fixes that specifically.
- When the array is too large for memory; mitigated by merge sort.
  > External sorting is a different problem.`}
/>

<MultipleChoice
  markdown={`What makes a sort "stable", and when does it matter?

- It never crashes on malformed input.
  > Stability is about ordering, not robustness.
- [o] Equal elements keep their original relative order, which matters when sorting by several keys in sequence.
  > Sort by name, then stably by department, and within each department the names remain sorted. Quicksort is not stable; merge sort and Timsort are.
- It always runs in the same time regardless of input.
  > That is a consistency property, not stability.
- It uses O(1) extra space.
  > That is being in-place, which is often at odds with stability.`}
/>

<MultipleChoice
  markdown={`What is the difference between memoization and tabulation?

- Memoization is faster in every case.
  > Tabulation usually has lower constant overhead by avoiding recursion.
- [o] Memoization is top-down recursion caching results as it goes; tabulation is bottom-up, filling a table iteratively in dependency order.
  > Memoization only computes the subproblems it needs; tabulation avoids recursion depth limits and is easier to space-optimize.
- Tabulation applies only to one-dimensional problems.
  > Multi-dimensional tables are routine.
- They produce different answers.
  > Both solve the same recurrence.`}
/>

<MultipleChoice
  markdown={`When is a greedy algorithm guaranteed to be optimal?

- Whenever the problem involves maximizing a value.
  > Plenty of maximization problems defeat greedy approaches.
- [o] When the problem has optimal substructure *and* the greedy-choice property, so a locally best choice is part of some global optimum.
  > Activity selection and Huffman coding qualify; 0/1 knapsack does not, which is why it needs dynamic programming.
- When the input is sorted.
  > Sorting often enables a greedy algorithm but does not justify one.
- Whenever it produces the same answer as brute force on small inputs.
  > Small-input agreement is evidence, not proof.`}
/>

<MultipleChoice
  markdown={`When should you represent a graph as an adjacency matrix rather than an adjacency list?

- Always; matrices are simpler.
  > Simplicity costs O(V²) memory regardless of edge count.
- [o] When the graph is dense, or when you need O(1) edge-existence checks.
  > A sparse graph with a million nodes would need a terabyte-scale matrix, which is why lists are the default.
- When the graph is a tree.
  > A tree is maximally sparse, the worst case for a matrix.
- When edges are weighted.
  > Both representations carry weights fine.`}
/>

<MultipleChoice
  markdown={`What does the two-pointer technique typically require of the input?

- That it fits in memory.
  > True but not the distinguishing requirement.
- [o] Some exploitable order or structure (usually sortedness), so moving a pointer lets you rule out a whole range of possibilities.
  > "Find two numbers summing to a target in a sorted array" is O(n) with two pointers and O(n log n) if you have to sort first.
- That it contains no duplicates.
  > Duplicates are usually handled with a small skip step.
- That it is a linked list.
  > Arrays are the more common setting, though fast/slow pointers on a linked list are a well-known variant.`}

## API design

<MultipleChoice
  markdown={`Which of these is closest to the actual constraint that makes an API RESTful?

- Returning JSON.
  > Representation format is unconstrained; REST predates JSON's dominance.
- [o] A uniform interface over identified resources, with stateless requests that carry everything needed to be understood on their own.
  > Statelessness is what lets any server instance handle any request, which is why it matters far beyond style.
- Using only \`GET\` and \`POST\`.
  > Restricting the verb set works against the uniform interface.
- Versioning the URL.
  > Versioning is a practical necessity, not part of the architectural style.`}
/>

<MultipleChoice
  markdown={`Which URL best follows REST resource naming conventions?

- \`POST /createNewUser\`
  > The verb belongs in the HTTP method, not the path.
- [o] \`POST /users\`
  > Plural nouns identify collections; the method supplies the action. The created resource then lives at \`/users/{id}\`.
- \`GET /users/delete/42\`
  > \`GET\` must not have side effects, and the action is again in the path.
- \`POST /user/new/create\`
  > Redundant path segments, and a singular collection name.`}
/>

<MultipleChoice
  markdown={`Which HTTP methods are idempotent?

- Only \`GET\`.
  > Several others are too.
- [o] \`GET\`, \`PUT\`, \`DELETE\`, and \`HEAD\`: repeating the request leaves the server in the same state.
  > \`DELETE\` is idempotent even though the second call returns 404: the *state* is the same. \`POST\` and \`PATCH\` generally are not.
- All of them, since HTTP is stateless.
  > Statelessness of the protocol says nothing about the effect of a request.
- \`POST\` and \`PUT\`.
  > \`POST\` creating a new resource each time is the standard non-idempotent case.`}
/>

<MultipleChoice
  markdown={`A payment client times out and retries. How do you stop a double charge?

- Deduplicate by comparing amount and timestamp.
  > Two genuine identical payments seconds apart would be wrongly collapsed.
- [o] Require a client-generated idempotency key, store the first result against it, and return that stored result for any repeat.
  > It makes retrying safe without the client having to know whether the first attempt landed.
- Make the endpoint a \`PUT\`.
  > \`PUT\` is idempotent by convention only if the handler actually implements it that way.
- Reject any second request within 30 seconds.
  > A time window blocks legitimate requests and still lets late retries through.`}
/>

<MultipleChoice
  markdown={`What is the difference between 401 and 403?

- 401 means the resource does not exist; 403 means it does but is private.
  > A hidden resource is usually 404 on purpose.
- [o] 401 means unauthenticated, the request lacks valid credentials; 403 means authenticated but not permitted.
  > "Who are you?" versus "I know who you are and the answer is still no."
- 401 is for expired tokens only.
  > An absent token is 401 too.
- They are interchangeable.
  > Clients react differently: 401 usually triggers a re-auth flow, 403 should not.`}
/>

<MultipleChoice
  markdown={`Which status code fits a request that is syntactically valid but semantically wrong, such as an end date before its start date?

- 500 Internal Server Error.
  > 5xx says the server failed; this is the client's input.
- [o] 400 Bad Request, or 422 Unprocessable Entity where that distinction is used.
  > 422 signals "I parsed it, but it does not make sense", which is more informative for validation failures.
- 404 Not Found.
  > Nothing is missing.
- 204 No Content.
  > 204 reports success with no body.`}
/>

<MultipleChoice
  markdown={`Why is offset pagination a poor fit for a large, frequently-changing collection?

- Offsets are limited to 10,000 rows.
  > No such universal limit exists, though some engines impose one.
- [o] Deep offsets force the database to scan and discard everything before them, and rows inserted mid-pagination shift the window so items are skipped or repeated.
  > Cursor (keyset) pagination, meaning "everything after this sorted key", avoids both problems.
- It cannot be combined with sorting.
  > It requires sorting to be meaningful at all.
- It requires a stateful server.
  > Offsets are stateless; that is their appeal.`}
/>

<MultipleChoice
  markdown={`Which approach to API versioning is most transparent to the client?

- Breaking changes with a migration guide, no version.
  > This shifts the whole cost onto every consumer at once.
- [o] A version in the URL path, such as \`/v1/users\`, which is visible, cacheable, and trivial to route.
  > Header-based versioning is cleaner in theory and harder to debug in practice, since you cannot see the version in a log line or paste it into a browser.
- Query parameter versioning, such as \`?version=1\`.
  > It works, but it mixes an API-wide concern into per-request parameters and complicates caching.
- Deploying each version to a separate domain.
  > Workable but heavy, and it breaks relative links and cookie scoping.`}
/>

<MultipleChoice
  markdown={`How should a client learn its rate limit?

- By observing when requests start failing.
  > Discovering a limit by tripping it is what the headers exist to avoid.
- [o] From response headers giving the limit, remaining quota, and reset time, plus \`Retry-After\` on a 429.
  > Well-behaved clients then back off proactively rather than hammering until they are throttled.
- From the API documentation only.
  > Documentation cannot report the client's *current* remaining quota.
- From a dedicated endpoint polled every minute.
  > Polling for quota spends quota.`}
/>

<MultipleChoice
  markdown={`When does GraphQL fit better than REST?

- Whenever the API is public.
  > Public APIs benefit from REST's cacheability and predictability.
- [o] When varied clients need different subsets of a graph-shaped domain and would otherwise over-fetch or make many round trips.
  > The cost is caching complexity, query-depth abuse, and N+1 resolution that needs batching.
- When the payloads are large.
  > Payload size alone does not favor either.
- When strong typing is required.
  > REST can be strongly typed with OpenAPI.`}
/>

<MultipleChoice
  markdown={`What does gRPC give you that REST-over-JSON does not?

- Human-readable payloads.
  > Protobuf is binary, which is the trade.
- [o] A compact binary format with generated clients from a schema, plus first-class streaming over HTTP/2.
  > It is why gRPC dominates internal service-to-service traffic and is rare on public browser-facing APIs.
- Automatic authentication.
  > Auth is layered on either way.
- Freedom from schema definitions.
  > It requires a \`.proto\` schema; that requirement is the source of its benefits.`}
/>

<MultipleChoice
  markdown={`How should an API report a validation failure across several fields?

- Return the first error and stop.
  > This forces the client through one round trip per mistake.
- [o] Return a structured body listing each field, an error code, and a human-readable message, under a consistent envelope.
  > A machine-readable \`code\` lets clients localize and branch; a message alone forces string matching.
- Return a 200 with an \`error\` field.
  > A success status for a failed request breaks every generic client and proxy.
- Return a plain-text description.
  > Unparseable by clients, and it forces string matching for behavior.`}
/>

<MultipleChoice
  markdown={`What does content negotiation let a client do?

- Choose which fields are returned.
  > Field selection is done with query parameters or GraphQL.
- [o] Ask for a representation in a particular format or language via \`Accept\` and \`Accept-Language\`, with the server responding in \`Content-Type\`.
  > It is also how API versioning by media type works, when that approach is chosen.
- Negotiate a rate limit.
  > Limits are server policy.
- Compress the request body.
  > That is \`Content-Encoding\`, a related but distinct header.`}
/>

<MultipleChoice
  markdown={`When is a stateful session preferable to a stateless JWT?

- When the API serves mobile clients.
  > Client type does not decide this.
- [o] When you need immediate revocation, since a session can be deleted server-side while a signed token stays valid until it expires.
  > The workarounds (very short expiry plus refresh tokens, or a revocation list) reintroduce the server-side state JWTs were meant to avoid.
- When the payload is large.
  > A large payload argues *for* a session, since the token travels on every request, but revocation is the decisive point.
- When you have multiple servers.
  > Multiple servers is the classic argument *for* stateless tokens.`}
/>

<MultipleChoice
  markdown={`Is HATEOAS required for an API to be useful?

- Yes; without it the API is not REST.
  > Strictly, Fielding's model does require it, which is why almost no popular "REST" API is fully RESTful.
- [o] It is a formal REST constraint, but most successful HTTP APIs omit it and are perfectly usable with documentation and stable URLs.
  > Knowing both the definition and the industry reality is the answer an interviewer is looking for.
- No; it was removed from the REST specification.
  > REST is a dissertation, not a spec, and nothing was removed.

## Concurrency

<MultipleChoice
  markdown={`What is the difference between concurrency and parallelism?

- They are the same thing.
  > A single-core machine can be concurrent without ever being parallel.
- [o] Concurrency is structuring work so tasks can make progress independently; parallelism is actually executing them at the same instant on multiple cores.
  > Concurrency is about dealing with many things at once; parallelism is about doing many things at once.
- Concurrency requires multiple processes and parallelism multiple threads.
  > Both can be built from either.
- Parallelism is concurrency with locks.
  > Locks are a coordination mechanism, not a definition.`}
/>

<MultipleChoice
  markdown={`How do processes and threads differ?

- Threads are faster because they skip the scheduler.
  > Both are scheduled by the OS.
- [o] Threads share a memory space within one process, making communication cheap and data races possible; processes are isolated and must communicate through IPC.
  > Isolation is why a crashing process cannot corrupt its siblings, and why process pools are used to sidestep Python's GIL.
- Processes cannot run in parallel.
  > Processes are the classic route to true parallelism.
- Threads have their own address space.
  > Sharing an address space is what defines them.`}
/>

<MultipleChoice
  markdown={`What is a race condition?

- Two threads competing for the same lock.
  > Lock contention is expected behavior, not a bug.
- [o] Behavior that depends on the unpredictable interleaving of operations, so the result varies between runs.
  > \`x = x + 1\` is three operations (read, add, write), and two threads can interleave them to lose an update.
- A thread that runs faster than expected.
  > Speed alone is not a correctness problem.
- A deadlock that resolves itself.
  > A resolved deadlock is a livelock, which is different again.`}
/>

<MultipleChoice
  markdown={`What are the four conditions that must all hold for a deadlock?

- Two threads, two locks, one CPU, and no timeout.
  > These are incidental to one example rather than the general conditions.
- [o] Mutual exclusion, hold-and-wait, no preemption, and circular wait.
  > Breaking any one prevents deadlock, which is why a global lock ordering, breaking circular wait, is the usual practical fix.
- Starvation, livelock, priority inversion, and contention.
  > These are other concurrency pathologies.
- Shared memory, threads, locks, and recursion.
  > Deadlock needs none of these specifically.`}
/>

<MultipleChoice
  markdown={`How does a livelock differ from a deadlock?

- A livelock always resolves eventually.
  > It can persist indefinitely; that is what makes it a bug.
- [o] In a deadlock threads are blocked and idle; in a livelock they keep changing state in response to each other and still make no progress.
  > Two people stepping aside for each other in a corridor, forever. Randomized backoff is the classic fix.
- A livelock involves only one thread.
  > It requires at least two interacting.
- A livelock is caused by CPU starvation.
  > Starvation is a separate condition.`}
/>

<MultipleChoice
  markdown={`What is the difference between a mutex and a semaphore?

- A mutex is faster.
  > Relative cost depends on the implementation.
- [o] A mutex allows exactly one holder and is typically owned by the thread that locked it; a counting semaphore admits up to N holders and has no ownership.
  > A semaphore initialized to 1 behaves like a lock but without the ownership check, so it can legitimately be released by a different thread.
- A semaphore can only be used across processes.
  > Both come in intra- and inter-process forms.
- A mutex cannot be released by the thread that acquired it.
  > That is exactly the thread that should release it.`}
/>

<MultipleChoice
  markdown={`Why does Python's GIL exist, and when does it actually hurt?

- It prevents deadlocks, and it hurts when using locks.
  > It does not prevent deadlocks in user code.
- [o] It simplifies memory management by serializing bytecode execution, and it hurts CPU-bound multithreaded work while leaving I/O-bound work largely unaffected.
  > Threads release the GIL during I/O, which is why threading still helps a network-bound workload. CPU-bound work needs \`multiprocessing\` or a native extension that releases it.
- It makes all Python code thread-safe.
  > It guarantees only that a single bytecode instruction is atomic; \`x += 1\` still races.
- It only affects Python 2.
  > It is present in CPython 3 as well, though free-threaded builds are now available.`}
/>

<MultipleChoice
  markdown={`What happens when you call a blocking function inside an async coroutine?

- The runtime moves it to a background thread.
  > No automatic offloading happens.
- [o] It blocks the entire event loop, so every other coroutine stalls until it returns.
  > The fix is an async-native library, or \`run_in_executor\` / \`asyncio.to_thread\` to push the blocking call onto a thread pool.
- It raises an exception.
  > It runs perfectly, which is what makes the bug hard to spot.
- It runs concurrently anyway, since coroutines are threads.
  > Coroutines are not threads; a single-threaded loop interleaves them cooperatively.`}
/>

<MultipleChoice
  markdown={`Which workload is the best fit for \`multiprocessing\` over threads in Python?

- Fetching 500 URLs.
  > Network waiting is I/O-bound; threads or async are lighter.
- [o] Computing a numerical transform over a large array in pure Python.
  > CPU-bound work needs separate interpreters to use multiple cores. The cost is process startup and pickling data across the boundary.
- Reading many small files.
  > File I/O releases the GIL, so threads suffice.
- Waiting on database queries.
  > Another I/O-bound case.`}
/>

<MultipleChoice
  markdown={`What does a thread pool buy you over creating a thread per task?

- It removes the need for locks.
  > Shared state still needs protection.
- [o] It bounds concurrency and amortizes thread creation, so a burst of 10,000 tasks does not spawn 10,000 threads.
  > The bound is the important half: unbounded thread creation exhausts memory and thrashes the scheduler.
- It guarantees tasks run in submission order.
  > Ordering is not guaranteed unless the pool has a single worker.
- It makes tasks run faster individually.
  > Per-task speed is unchanged, and pooling adds a small queueing overhead.`}
/>

<MultipleChoice
  markdown={`What is an atomic operation?

- Any operation that completes in one CPU cycle.
  > Cycle count is unrelated; many atomics take several.
- [o] One that appears to other threads as either fully done or not started, with no observable intermediate state.
  > Compare-and-swap is the primitive most lock-free structures build on.
- An operation guarded by a lock.
  > Locking is one way to *achieve* atomicity, not what it means.

<MultipleChoice

<MultipleChoice

<MultipleChoice

<MultipleChoice

<MultipleChoice

## Object-oriented design & Python

<MultipleChoice
  markdown={`What does encapsulation actually buy you?

- [o] It confines invariants to one place, so state can only change through methods that keep it valid, and the internals can be rewritten without touching callers.

<MultipleChoice
  markdown={`Why favour composition over inheritance?

- [o] Inheritance binds a subclass to its parent's implementation permanently, while composition lets behavior be swapped and combined at runtime.

<MultipleChoice

<MultipleChoice

- [o] Both high- and low-level modules should depend on abstractions, so the policy does not hard-code which implementation it uses.

<MultipleChoice
  markdown={`When is the Strategy pattern the right tool?

<MultipleChoice

<MultipleChoice

  markdown={`When does introducing a message queue help?

- Whenever two services need to communicate.
  > Synchronous calls are simpler when the caller needs an answer now.
- [o] When work can be done asynchronously, when you need to absorb traffic spikes, or when producers and consumers should scale and fail independently.
  > The cost is eventual consistency, duplicate delivery, and ordering that is only guaranteed within a partition.
- When you need lower latency for the end user.
  > Perceived latency can improve, but the total work takes longer.
- When the database is slow.
  > A queue defers load; it does not make a slow query fast.`}

<MultipleChoice
  markdown={`Which rate-limiting algorithm best allows short bursts while capping the long-run rate?

- Fixed window.
  > A fixed window permits a double burst across the boundary and is otherwise rigid.
- [o] Token bucket.
  > Tokens accumulate up to a cap, so an idle client can burst, then is limited by the refill rate. Leaky bucket smooths output instead of permitting bursts.
- Leaky bucket.
  > It enforces a constant outflow, which deliberately suppresses bursts.
- Concurrency limiting.
  > That caps simultaneous requests, a different quantity from rate.`}

<MultipleChoice
  markdown={`In a URL shortener, why is a hash of the long URL a problematic id scheme on its own?

- Hashes are too long to be useful.
  > They can be truncated, which is where the problem starts.
- [o] Truncating to a short code creates collisions, so you still need a uniqueness check and a resolution strategy on write.
  > A counter encoded in base62, or a pre-generated key pool, avoids collisions by construction.
- Hashing is too slow at scale.
  > Hashing is trivially fast.
- Hashes cannot be stored in a database.
  > They store as ordinary strings.`}
/>

<MultipleChoice
  markdown={`For a news feed, when is fan-out on write the wrong choice?

- When most users have few followers.
  > That is the case it handles best.
- [o] For accounts with millions of followers, where one post triggers millions of writes; the usual answer is a hybrid, pulling celebrity posts at read time.
  > Fan-out on write optimizes reads at the cost of write amplification; the tail of the follower distribution is what breaks it.
- When the feed must be chronological.
  > Ordering works under either strategy.
- When reads outnumber writes.
  > A read-heavy workload is exactly what fan-out on write is for.`}
/>

<MultipleChoice
  markdown={`What does a CDN actually improve?

- Database query time.
  > A CDN never touches the database.
- [o] Latency and origin load for cacheable content, by serving it from a point of presence near the user.
  > It also absorbs traffic spikes and offloads bandwidth cost, which is often the larger saving.
- Application correctness under load.
  > Correctness is unaffected.
- Write throughput.
  > CDNs cache reads.`}
/>

<MultipleChoice
  markdown={`How do you remove a single point of failure?

- Add monitoring so you know when it fails.
  > Monitoring shortens the outage; it does not prevent one.
- [o] Add redundancy with automatic failover, and make sure the failover path is exercised rather than assumed to work.
  > An untested standby is a single point of failure with extra steps.
- Scale the component vertically.
  > A bigger single machine is still single.
- Document a manual recovery procedure.
  > Useful, but it leaves the outage lasting as long as a human takes.`}
/>

<MultipleChoice
  markdown={`Which back-of-the-envelope figures are worth having memorized for a design interview?

- The exact price of each cloud instance type.
  > Pricing changes constantly and is rarely the crux.
- [o] Rough orders of magnitude: memory reads in nanoseconds, SSD in tens of microseconds, a cross-region round trip in the tens or hundreds of milliseconds, and how those turn into QPS and storage per day.
  > The numbers only need to be right to an order of magnitude, enough to say whether something fits in memory or needs a different design.
- The number of cores in the latest server CPUs.
  > Occasionally useful, rarely decisive.
- The default configuration values of your database.
  > Worth knowing on the job, not for sizing a design.`}
